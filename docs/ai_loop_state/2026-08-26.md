### 1-3. ローカルループ（Phase 4）— 計画書のサンプルを大きく超えた実装

`scripts/work_loop.sh`（364行、計画書のサンプルは約70行）。

**計画書に無い追加要素:**

| プリフライト4種 | `logs/` の gitignore 検査／`core.hooksPath` 検査／作業ツリーの汚れ検査／ブランチ検査。**いずれも警告ではなく中断する** |

さらに、この検出が `.gitignore` に依存していることを自覚し、`logs/` が ignore されて
いなければ**中断する**プリフライトを置いている。計画書 1-3 が「検査できないときは止まる側へ
倒せ」と書いた原則を、計画書が想定していない箇所に自力で適用した例である。

### 1-4. 権限設計 — 計画書に無い知見を実測で獲得

計画書 Phase 1-3 は `allow` と `deny` を両方書くサンプルを示しているが、本プロジェクトは
**`allow` を一切置かない**方針に変更した（ADR-008）。理由は実測で判明した以下の性質:

> `permissions.allow` は発生源（CLIフラグ／プロジェクト設定／ローカル設定）を問わず**加算**される。
> 対話セッション用の `.claude/settings.local.json` の広い allow が、非対話ループにも素通しで効く。

Issue #14 で実際に無許可 commit が発生して判明した。対処は「allow を絞る」ではなく
「deny で塞ぐ」で、`deny` は発生源を問わず常に `allow` より優先されるという公式ドキュメントの
記述を確認したうえで採用している。

併せて **複合コマンドでも deny が勝つ**ことを実測済み（`./scripts/verify.sh ; gh pr merge ...`
が全体として拒否され、`verify.sh` 自身も走らない）。「allow したコマンドの後ろに禁止コマンドを
繋ぐ」形の迂回ができないことを、推測ではなく実験で確認している。

**これは計画書に書かれていない知見である。** 計画書 Phase 1-4「ルールと権限は別物」の
一段深い層にあたる。

### A. ループ本体が事実上停止している ★最大の乖離

**実測:**

| 項目 | 値 |
|---|---|
| `work_loop.sh` 由来の PR | **1件のみ**（#74、Issue #38、2026-08-03 作成） |
| `logs/` の最終更新 | **2026-08-04 03:12** |
| `work_loop.sh` の最終コミット | 2026-08-04 |
| それ以降にマージされた PR | 約140件（**すべて対話セッション由来**） |
| 直近の作業ブランチ | `test/...`・`docs/...`（`loop/<issue>` ではない） |

計画書の中心（Phase 4 → Phase 5）は「対話で通す → ヘッドレスに落とす → CI に載せる」だが、
**現状は最初の段階に戻ったまま、そこで全作業が回っている。**

さらに、**最後の1回の実行結果自体に問題がある。**

```
logs/outcome_1.txt : success
logs/run_1.json    : is_error=true, terminal_reason=max_turns, num_turns=21
```

`success` と記録されているが、実際にはターン上限で打ち切られていた。この矛盾に対処する
Issue #75 の修正（outcome に `warning:` 行を追記する）は**このログの約10時間後**に
コミットされており、**修正後にループを1度も走らせていない。**

つまり `work_loop.sh` の現在の姿は、**一度も実運用で検証されていない版**である。

**対応の選択肢（決めない）:**

1. 修正後の版で1回走らせ、実測を取る（Issue #75 の修正が効くことの確認を兼ねる）
2. 「対話セッション運用を正とし、`work_loop.sh` は保守しない」と ADR で決定する
3. 現状維持（停止していることが記録されないまま残る）

**現状は 3 に近いが、それが判断の結果なのか放置なのかが記録から読み取れない。**
ADR-009 が Phase 5-3/5-4 について行ったのと同じ整理が、Phase 4 本体にも要る。

### B. 「理解の負債」が2回連続で赤信号だが、次の行動が決まっていない

計画書 Phase 7 の基準は「**3件中1件でも説明できないなら、マージが速すぎる**」。
2回とも 3件中3件が説明できておらず、しかもコード変更 PR に限定しても結果が変わらなかった
（「記録PRを覚えていないだけ」という説明が成立しないことを自分で確認済み）。

計画書はこの状態への対応を明示している。

> その場合の対応は **PR を小さくするか、本数を減らす**

`docs/runbook.md` にもこの一文がそのまま引用されている。**しかし実施した記録が無い。**

それが §3-B のとおり赤のまま止まっている。

`loop_metrics.sh` は「取得不能」と正直に出力する設計になっており（0件と表示して
「不具合が無かった」と誤読されるのを避けている）、**計測が成立しないことを計測できている**
点は評価できる。しかし、**成立しない計測を持ち続けるか、別の指標に置き換えるかが未決定。**

### H. 計画書自体が1か月更新されていない

- 計画書の最終更新: **2026-07-27**
- その後に決まった主要な設計変更: ADR-005（OAuth）・006（review 再設計）・008（deny only）・
  009（5-3/5-4 見送り）・010（採用率棄却）＝ **5本**

計画書を読んだだけでは、現在の設計が分からない状態になっている。ADR 側が実質的な最新版
だが、**計画書と ADR のどちらを正とするかが明示されていない。**

なお、計画書は `.gitignore` 対象（`ai-loop-implementation-plan_v*.md`）でバージョン管理
されていないため、更新履歴も追えない。

### I. 人間が実行役と指示役の間の伝送路になっている

現在、Claude Code（実行役）の出力を人間がコピーして別の Claude（指示役・監査役）に貼り、
その出力を人間がコピーして Claude Code へ戻す、という運用になっている。人間が判断せず
テキストを右から左へ運ぶだけの中継として介在している時間が構造上存在する。

**これは実装漏れではない。** `ai-loop-implementation-plan_v8.md` は Phase 8-2「実装と別
プロセスでレビューさせる」で複数プロセスによるレビューの価値を述べているが、その受け渡し
経路（誰が・何を介して・どういう形式で運ぶか）を一度もモデル化していない。計画書のどの
Phase にも「プロセス間の伝送」という項目自体が存在せず、対応表（§2）に挙げた9件の逸脱とは
性質が異なる——**計画書に無いから守れていない、のではなく、計画書がそもそも扱っていない
構造的な欠落**である。

対応方針は ADR-011（`docs/decisions/`）で決定した。詳細はそちらを参照。

## 5. 総評

**作り込みの質は計画書を上回っている。** no-op 検出、deny の加算問題、複合コマンドの
拒否実測、M6-B-4 ゲート、「壊して確認」の常設ルール化、`Verify a substantive review`
ステップ — いずれも計画書には無い、実測から得られた対処である。ADR 10本と `ERRORS.md`
1464行が、その経緯を追える形で残っている。

**一方で、作った仕組みの大半が使われていない。** ループは1件で停止し、Phase 5-5 は未着手、
Phase 7 の指標は3つとも機能せず、唯一機能している監視（抜き取り確認）は2回連続で赤のまま
次の行動が決まっていない。

計画書の言葉を借りるなら、**「信頼性が先、自律性は後」の前半だけが極端に進み、後半に
進んでいない状態**である。これは失敗ではなく、むしろ計画書 0 章が警告した順序（検証を
作らずに自動化する）の逆を徹底した結果だが、**その状態がいつまで続くのかが記録されて
いない**点だけが問題として残る。

優先度をつけるなら:

1. **§3-B**（理解の負債が赤のまま） — 唯一機能している指標が警告を出している
2. **§3-A**（ループの停止を ADR 化するか、1回走らせて実測を取るか） — 判断の記録が無い
3. **§3-C**（`ERRORS.md` の失効記述） — 実害のある矛盾。修正は数行
4. §3-H（計画書と ADR の関係整理） — どちらを正とするか
5. §3-D・E（肥大の剪定） — 月次項目の未実施

**1〜3 は「何をすべきか」が既に決まっている。** 4以降は方針判断が要る。
