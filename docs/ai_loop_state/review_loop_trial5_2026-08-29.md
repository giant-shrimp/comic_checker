## 8. 検出した欠陥

### 欠陥A: 未追跡ファイルがdiff.txtに現れない

round_1・round_2とも`diff.txt`は0バイト（`wc -c round_{1,2}/diff.txt`の
実測値）。対象ファイル`docs/ai_loop_state/review_loop_exit_codes.md`は
新規作成のため`git status`上`??`（未追跡）であり、`git diff`には現れない。

`scripts/review_loop.sh`のdiff取得箇所（`grep -n "git diff >"
scripts/review_loop.sh`の実測）:

```
git diff > "${ROUND_DIR}/diff.txt" || true
```

`git status --porcelain`は使われておらず、**追跡済みファイルの変更のみ
を捉える。** 新規（未追跡）ファイルの内容は監査役へ一切渡らない。

一方、no-op検出用の`snapshot()`は`git status --porcelain`を含んでいる
（`scripts/review_loop.sh`の該当関数を確認）。

```bash
snapshot() {
  {
    git status --porcelain
    git diff HEAD
    git ls-files --others --exclude-standard -z \
      | xargs -0 -r sha256sum 2>/dev/null || true
  } | sha256sum | cut -d' ' -f1
}
```

**したがって、no-op検出（`exit 12`）はこの欠陥の影響を受けない**（未
追跡ファイルの変更もハッシュに反映される）。**影響を受けるのは監査役へ
渡す`diff.txt`のみ**である。本試走では監査役が実ファイルを直接読んで
補い（`round_1/review.md`・`round_2/review.md`の補足に明記）、両ラウンド
とも実質的な判定への悪影響は無かったが、**渡された証拠自体は欠落して
いた。**

（Issue #227の修正（PR #230）で新設された`preserve_work_tree_state()`は
`git status --porcelain`も保存するが、これは`is_error=true`検出時のみ
呼ばれる別経路であり、通常の毎ラウンドの`diff.txt`生成には使われて
いない。）

### 欠陥B: 承認プロンプトが先行入力を人間の承認として受理していた（原因確定）

**事象**: round_1の承認プロンプト（`[c=続行 / q=終了]`、`scripts/
review_loop.sh:439`）に対し、ユーザは何も入力していないと報告されている。
にもかかわらずループはround_2へ進行した。本試走で人間が実際にキーを
押したのは、round_2の`q`限定プロンプト（`wait_for_quit_only()`、
`scripts/review_loop.sh:245`）での`q`一度のみである。画面に表示された
「c または q を入力してください」1回・「q のみ入力できます」7回は、
いずれも**ユーザの入力に起因しない**。

**意味**: `docs/decisions/ADR-011-review-loop-design.md`決定8は「段階0
（毎ラウンド人間が1キーで承認）から開始する」と定めている（同文書
`## 決定`8番）。round_1からround_2への進行が人間の入力を経ずに起きた
ということは、**段階0の唯一の人間ゲートが、本試走では成立していなかった**
ことを意味する。

### コードから読み取れる範囲

`scripts/review_loop.sh`の入力読み取り部分（`grep -n "read -n 1"
scripts/review_loop.sh`の実測、245行目・439行目）を再確認した。

```
245:    read -n 1 -r -p "${reason}のため続行できません。終了します [q]: " key
439:    read -n 1 -r -p "この指示で次ラウンドへ進みますか？ [c=続行 / q=終了]: " KEY
```

**確認済みの事実**:
- いずれの`read`呼び出しにも`< /dev/tty`のような明示的なリダイレクトは
  無い（`grep -n "/dev/tty\|read -t\|stty" scripts/review_loop.sh`で
  0件）。すなわち、この2箇所の`read`はスクリプトの標準入力をそのまま
  読む設計であり、直前の`read`が消費し損ねたバイトや、スクリプト内の
  他プロセス（`claude`呼び出し等）が標準入力へ書き込んだバイトを明示的に
  破棄・分離する処理は無い
- `read -n 1 -r`は、呼ばれた時点で入力バッファに既に存在するバイトを
  そのまま1文字として読む。人間のキー入力かどうかを区別する機構は無い

### 確定した原因: ループ起動直後の先行入力（type-ahead）

診断版（`scripts/review_loop_debug.sh`。`scripts/review_loop.sh`本体は
無変更のまま、標準入力バッファの内容を非破壊的に記録する診断コードだけを
追加した、未追跡の実験用スクリプト。詳細は本節末尾「実施した追加観測」
参照）による実測で原因が確定した。セッション`20260829-163046`の診断ログ
（`~/comic_checker-agent-notes/review_loop_debug_*.log`、抜粋）:

```
[16:30:46] round_start (round=1): 7 bytes
0000000   e   c   h   o       $   ?
[16:31:18] after_executor (round=1): (empty)
[16:32:11] after_audit (round=1): (empty)
[16:32:48] after_proposer (round=1): (empty)
[16:32:48] before_cq_prompt (round=1): (empty)
[16:33:52] read result (c/q prompt): rc=0 value= q
```

`round_start`の時点（ラウンド開始直後、実行役の`claude`呼び出しより前）
で、標準入力バッファに`echo $?`という7バイト（`e` `c` `h` `o` ` ` `$`
`?`）が既に残留していたことが判明した。これは、ユーザがループ起動直後に
`echo $?`というコマンドを端末へ打ち込み、それがループの標準入力へ
先行入力（type-ahead）として滞留したものである。`after_executor`・
`after_audit`・`after_proposer`のいずれの時点でも残留は無く（空）、
`claude`呼び出しの前後で新たにバイトが混入した形跡は無い。

診断版では`round_start`のprobe自体がこの7バイトを吸い出したため、
以降のプロンプトには何も残らず、`before_cq_prompt`は空、実際の承認
プロンプトはユーザが押した`q`（`read result (c/q prompt): rc=0 value=
q`）を正しく読み取って停止した。**同じ「ループ起動直後に`echo $?`を
打ち込む」という手順を踏んでも、probeが先にバッファを空にしたことで、
この回は承認プロンプトが正しく機能した。**

### 5回目試走（`20260829-154741`）での再構成

上記の実測を踏まえ、5回目試走で観測された回数（1節参照）をバイト単位で
再構成する。`echo $?`＋Enterは8バイト（`e` `c` `h` `o` ` ` `$` `?`
`\n`）。5回目試走の実行時には診断版のprobeが無かったため、この8バイトは
吸い出されずそのまま各プロンプトの`read -n 1`に順次読まれたと考えられる。

|---|---|---|---|

### 欠陥の性質

ADR-011決定8が本試走で不成立になったという事実は変わらない（7節参照）。
ただし、原因は`review_loop.sh`の実装バグではない。**承認プロンプトが、
先行入力（人間が別の目的で打ち込んだ、無関係なコマンド文字列）を人間の
承認として無条件に受理してしまう、という設計上の脆弱性である。**

`docs/ai_loop_state/`配下の既存の試走記録に「ループ終了直後に`echo $?`を
取る」旨の記述があるかを確認した（`grep -rn 'echo \$?' docs/ai_loop_state/`、
このファイル自体は変更していない）。
