# 欠陥B（承認プロンプトの先行入力受理）への対処選択肢（2026-08-29）

Issue #232（`scripts/review_loop.sh`の承認プロンプトが、ループ起動より前に
ユーザが打ち込んだ文字列＝先行入力／type-aheadを人間の承認として受理して
しまう）への対処選択肢を整理する。原因は`docs/ai_loop_state/
review_loop_trial5_2026-08-29.md`「8. 検出した欠陥」で確定済み（診断版
スクリプトによる実測で、`echo $?`という先行入力が標準入力バッファへ残留
し、`read -n 1`に1バイトずつ順に読まれたことをバイト単位で確認した）。

ADR-011決定8（段階0＝毎ラウンド人間が1キーで承認、から開始する）の成立に
直結するため、実装より先に選択肢を洗い出して比較する。**本文書は選択肢の
比較であり、決定ではない。5〜7つの選択肢のどれを採るかはここでは決めない。
`scripts/`・`tests/`配下は一切変更していない。**

## 1. 該当箇所の再確認（事実）

`scripts/review_loop.sh`の該当2箇所を、`read`直前のコードとともに再確認
した。

**245行目（`wait_for_quit_only()`内、q限定プロンプト）**:

```
241  wait_for_quit_only() {
242    local reason="$1"
243    local key
244    while true; do
245      read -n 1 -r -p "${reason}のため続行できません。終了します [q]: " key
246      echo
247      if [ "$key" = "q" ]; then
248        return 0
249      fi
250      echo "review_loop.sh: q のみ入力できます。"
251    done
252  }
```

`read`の直前（244行目`while true; do`から245行目まで）に、入力バッファの
状態を確認・破棄する処理は無い。

**439行目（`main()`内、`[c=続行 / q=終了]`プロンプト）**:

```
428    # 生成された次ラウンドのinstruction本文を、承認の判断材料として提示する
...
431    echo "--- 起案役が生成した次ラウンドのinstruction ---"
432    cat "$NEXT_INSTRUCTION_FILE"
433    echo
434    echo "  next instruction : ${NEXT_INSTRUCTION_FILE}"
435    echo "  proposer metrics : ${ROUND_DIR}/proposer/metrics.json"
436    echo
437
438    while true; do
439      read -n 1 -r -p "この指示で次ラウンドへ進みますか？ [c=続行 / q=終了]: " KEY
440      echo
...
```

`read`の直前（428〜438行目）は次ラウンドのinstruction本文とファイルパス
を画面へ表示するだけで、こちらにも入力バッファの状態を確認・破棄する
処理は無い。

両箇所とも構造は同じ（`while true; do read -n 1 -r -p ... done`）であり、
対処を検討する際は基本的に2箇所とも同じ変更が必要になる。

## 2. 対処の選択肢

### 選択肢A: プロンプト直前に入力バッファを無条件に破棄する（黙ってドレイン）

**機構**: `read`の直前に、`read -t 0`でバッファに読める内容があるかを
判定し、あれば`read -t 0.05 -n 1`のループで1バイトずつブロックせずに
読み捨てる。診断調査（`docs/ai_loop_state/review_loop_trial5_2026-08-29.md`
8節で参照した診断版の`_stdin_probe()`関数）で使われた非破壊確認と同種の
仕組みを、確認用ではなく破棄用に転用する形。

**利点**:
- 実装が最小（`read`の直前に数行追加するだけ）
- 診断調査で使ったのと同じ`read -t`ベースの手法であり、動作原理は
  実測で確認済み（バッファの読み出し自体は動く）

**欠点（明示すべき危険）**:
- **黙って捨てる設計であるため、たまたま人間がプロンプト表示の直前に
  正しい`c`/`q`を先回りしてタイプしていた場合、その正当な入力までもが
  無条件に捨てられる。** 人間から見ると「入力したのに無視された」という
  体験になり、原因不明の再入力を強いられる
- **先行入力があったこと自体が画面に一切表示されないため、人間は「何かが
  捨てられた」という事実に気づけない。** 今回のように意図しない先行入力が
  紛れ込んでいた場合、それが実際に危険な内容（例えば別のコマンド）
  だったとしても、気づく手がかりが無いまま握りつぶされる

**副作用の可能性**:
- ドレインに要する時間（読み捨てるバイト数×タイムアウト間隔）だけ
  プロンプト表示が遅延する
- 大量の先行入力（誤って大きな文字列やファイル内容を貼り付けた場合等）
  があると、ドレインが完了するまでプロンプトが出ない

### 選択肢B: 先行入力の有無を検査し、検出したら警告して再度プロンプトを出す

**機構**: `read`の直前に選択肢Aと同じ方法でバッファの内容を読み出すが、
読み出した内容を破棄する前に画面へ表示し、「先行入力を検出したため破棄
しました」という警告を出してから、あらためてプロンプトを表示する。

**利点**:
- 選択肢Aの最大の欠点（気づけない）を解消する。人間は「何かが起きた」
  ことを知った上で、あらためて`c`/`q`を入力できる
- 診断のためだけでなく、運用中の異常検知としても機能する（例えば別の
  未知の混入源が今後見つかった場合も、この警告が最初の手がかりになる）

**欠点**:
- 実装が選択肢Aよりやや複雑（検出→表示→破棄→再プロンプトの手順が
  増える）
- 先行入力の内容によっては、画面へそのまま表示すると読みにくい、
  あるいは制御文字を含む場合に端末表示が乱れる可能性がある（表示方法
  ―― 例えば`od -c`相当でエスケープするか等 ―― は本文書では決めない）
- 「本当に正当な先行入力だったのか、誤って紛れ込んだものか」を
  スクリプト側は区別できないため、正当な先行入力の場合でも常に警告が
  出る（誤検知ではないが、頻度によっては煩わしく感じられる可能性）

### 選択肢C: `read -n 1`をやめて行単位の入力（`read -r`、Enter必須）にする

**機構**: `read -n 1 -r -p ... KEY`を`read -r -p ... KEY`に変え、1文字
ではなく1行（Enterで確定）を読む形にする。ユーザは`c`または`q`を入力し
Enterを押す。

**利点**:
- `read -n 1`特有の「1文字だけ読んで残りをバッファに置き去りにする」
  という性質そのものを避けられる可能性がある。行単位であれば、
  少なくとも「先行入力の途中の1バイトだけを読んで即座に承認扱いにする」
  という今回と同型の事故は起きにくいと考えられる

**欠点**:
- **ADR-011決定8は「段階0（毎ラウンド人間が1キーで承認）」と明記して
  おり、これは1キー（Enter不要の即時入力）を前提とした文言である。**
  行単位入力へ変えることは、この決定の文言そのものを変えることになり、
  ADR側の見直し（決定8の再定義、または新しいADRでのsupersede）が
  必要になる可能性が高い
- **未確認**: 先行入力が複数行（複数のEnterを含む）だった場合、行単位に
  しても「1行分だけを消費し、残りの行が次のプロンプトへ渡る」という
  構造自体は変わらない可能性がある。今回のケース（`echo $?`、Enter1個）
  は解消できると考えられるが、より複雑な先行入力（例えば複数コマンドを
  まとめて先行入力していた場合）まで解消するかは検証していない

**副作用の可能性**:
- 既存のテスト（`tests/test_review_loop.py`の`_run_wait_for_quit_only`等、
  1文字入力を前提にしたテストヘルパー）の前提が変わるため、テスト側の
  書き換えが必要になる

### 選択肢D: `/dev/tty`から直接読む

**機構**: `read -n 1 -r -p "..." KEY < /dev/tty`のように、スクリプトの
標準入力ではなく、明示的に制御端末（`/dev/tty`）を開いて読む。

**利点**:
- 標準入力がパイプやファイルにリダイレクトされている非対話実行の
  ケースでも、常に実際の端末から入力を待てるという性質を持つ（一般に
  知られる`/dev/tty`の用途）

**欠点（重要、未確認であることを含む）**:
- **これは今回の事故の原因を解決しない可能性が高い。** 先行入力は
  ユーザが実際にキーボードから打ち込んだバイト列が端末デバイスの入力
  バッファに残っていたことが原因であり、`review_loop.sh`は元々対話的に
  端末から実行される前提（標準入力が既に端末そのもの）である。この
  条件下で`/dev/tty`へ切り替えても、参照先が同じ端末デバイスである
  可能性が高く、同じバッファを読むことになると考えられる。**ただし
  これは論理的な推測であり、実際に検証していない。未確認。**
- `/dev/tty`が存在しない環境（tty未割り当てのCI環境等）でスクリプトが
  失敗するという、新しい依存を追加することになる

**副作用の可能性**:
- 上記の「解決しない可能性」自体が最大のリスクである。効果が無いまま
  複雑さだけが増える恐れがある

### 選択肢E: 選択肢の組み合わせ（ドレイン＋警告、ADR文言は変更しない）

**機構**: 選択肢A（プロンプト直前のドレイン）と選択肢B（検出時の警告）を
組み合わせる。すなわち、先行入力を検出したら画面へ警告を表示したうえで
破棄し、あらためて1キーのプロンプトを表示する。選択肢Cのような1キーの
仕様変更は行わない。

**利点**:
- 選択肢Bとほぼ同じ（気づける・ADR決定8の文言を変えずに済む）
- 「ドレインする」という選択肢Aの機構と「警告する」という選択肢Bの機構は
  実装上ほぼ同じ処理（バッファを読み出す）を土台にしており、実質的には
  選択肢Bと同一の実装になる可能性が高い

**欠点**:
- 選択肢Bと同じ欠点を引き継ぐ
- 「組み合わせ」という名目だが、実質的に選択肢Bの言い換えに近く、
  独立した選択肢として扱う必要があるかは検討の余地がある

## 3. テスト可能性の評価

`tests/test_review_loop.py`は、既存のテスト（`test_wait_for_quit_only_
accepts_q`等）で`subprocess.run([...], input=keys, ...)`という形で
`bash -c 'source "$1"; wait_for_quit_only "テスト理由"'`にキー入力文字列
を`input=`引数として渡している。これはパイプ経由の標準入力であり、実際の
端末（tty）そのものではない。

| 選択肢 | pytestで検証できる範囲 | pytestで検証できない範囲 |
|---|---|---|
| A（黙ってドレイン） | `input=`に「先行入力相当のダミー文字列＋本来のキー」を連結して渡し、ダミー部分が無視され本来のキーだけが認識されることは検証できる（既存のパイプ経由テストと同じ手法の延長） | 実際の端末上でのタイミング（`read -t 0.05`のような時間依存の挙動）が、CI環境のパイプでも実端末と同じように機能するかは、本文書では未確認 |
| B（検出＋警告） | Aと同様に、ダミー入力＋本来のキーを渡し、戻り値・stdoutに警告メッセージが含まれること・最終的に本来のキーが認識されることの両方を検証できる | 同上（時間依存部分） |
| C（行単位入力） | 既存のテストヘルパーを「1文字」から「1行＋改行」に書き換えれば、通常のパイプ入力テストとして検証しやすい。tty特有の懸念が少なく、テスト可能性は他の案より高いと考えられる | 未確認。複数行の先行入力が絡む複雑なケースの網羅は、テストケースの設計次第 |
| D（`/dev/tty`） | **ほぼ検証できない。** pytestのsubprocessはCI・サンドボックス環境で制御端末を持たないことが多く、`/dev/tty`を開く行が存在するだけでテスト実行自体が失敗する、またはスキップが必要になる可能性が高い。本文書ではこの点を検証していないため「ほぼ検証できない」という評価自体、未確認の推測を含む | `/dev/tty`を使う分岐の実際の動作そのもの |
| E（A+Bの組み合わせ） | B相当のテストで代替できると考えられる | Aと同じ時間依存部分 |

**共通の限界**: いずれの案も、「実際の対話的な端末セッションで、先行入力
が起きた瞬間の挙動」そのものは、通常のpytest実行（パイプ経由の`input=`）
では完全には再現できない。今回の原因確定自体も、通常のpytestではなく
診断版スクリプトを使った実端末上での実測によって行われている
（`docs/ai_loop_state/review_loop_trial5_2026-08-29.md`8節参照）。対処を
実装する場合も、pytestによる自動テストに加えて、診断版と同様の実端末
での再現確認が必要になると考えられる。

## 4. 推奨案とその理由（採否はユーザが決める）

**推奨: 選択肢B（先行入力の有無を検査し、検出したら警告して再度プロンプト
を出す）。**

理由:
1. 選択肢Aの最大の危険（黙って捨てる、気づけない）を回避できる。本文書の
   制約で明示が求められたとおり、「本来の人間の入力まで捨てる危険」と
   「先行入力に気づけない危険」の両方は、選択肢Aのままでは解消しない
2. ADR-011決定8の「1キーで承認」という文言を変更せずに済む。選択肢C
   （行単位入力）はこの文言自体の見直しを要し、対処のスコープが
   「先行入力の混入を防ぐ」から「承認方式そのものの再設計」へ広がって
   しまう
3. 選択肢D（`/dev/tty`）は、今回の原因（同じ端末デバイスへの先行入力）を
   解決しない可能性が高いと考えられ（未確認だが論理的な懸念が強い）、
   複雑さに見合う効果が見込みにくい
4. テスト可能性の評価（3節）のとおり、選択肢Bはパイプ経由の既存テスト
   手法で戻り値・警告メッセージの両方を検証でき、他の案と比べて
   テストの土台を作りやすい

ただし、この推奨は本文書の中での比較に基づく判断であり、**実装するか
どうか、実装する場合の警告メッセージの文言やドレインのタイムアウト値
などの詳細は、別途決定・実装タスクで検討する必要がある。**
