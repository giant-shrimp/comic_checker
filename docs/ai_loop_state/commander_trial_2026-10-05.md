## 4. 分かったこと

### 4-1. 機能したこと

- 段取り（上流1で止める→確認→Issue 作成と全文の下書きで止める→全文確認→同意→実装役→照合で止める→上流2で止める→マージ→後始末）で、1 Issue を完走できた。
- ユーザの同意を AskUserQuestion の選択肢で取ると、「yes」で止まる問題（#413）が起きなかった。
- サブエージェントの操作による ask の承認画面は親のセッションに出て、通せた。
- 全文を司令塔が /tmp に確定し、実装役が cp し、司令塔が cmp で照合する形で、ask 対象の文書を反映できた。
- ローカルの REST で作った Issue・PR には帰属フッタが付かなかった（#416・#417）。

### 4-2. 実装役の report-self-check の拒否

- 実装役は、下書きファイルの書き出しが拒否されたと報告した。
- 拒否されたツール（Write か Bash か）、書き出し先のパス、拒否の別（権限設定・分類器・その他）は、最終応答に書かれておらず不明。
- report-self-check の手順1が指定する書き出し先は /tmp/report_draft.md だが、実装役が実際にそこへ書こうとしたかは観測していない。司令塔は実装役の途中経過の記録を読んでいない。

### 4-3. 受け入れ基準の grep の誤り

- 削除行数を `grep -c '^-[^-]'` で数えようとした。差分の見出し行 `---` を除くためだったが、削除される行が `- ` で始まる（Markdown の箇条書き）と差分では `--` で始まり、数えられない。numstat の削除数に改めた。
- 書き込みのメソッド指定を `-X` だけで数えようとした。長い形 `--method` を見逃す。`(-X|--method)` に改めた。
- どちらもチャット側の確認で見つけた。司令塔は、自分が作る受け入れ基準の grep の落とし穴を見落としうる。

### 4-4. 1回目の試走で起きた拒否（1回目の記録に未記載）

- 1回目の #391 で、実装役が push・cp・PR 作成・git log を1回の Bash 呼び出しにまとめると拒否された。
- その後、1回の Bash 呼び出しに1コマンドとする規則を実装役への依頼文に入れ、今回は起きなかった。

### 4-5. commander/SKILL.md で従いにくかった箇所（司令塔の申告）

- 「4. deny 対象の変更」は、ユーザが外のターミナルで cp・git add・git commit を行う方式だけを書いており、ask 対象の反映の流れがない。
- 「2. 下流」は、変更するファイルの全文を司令塔が確定する場合の扱い（/tmp に置いて cp させ、cmp で照合する）を書いていない。
- 「1. 上流1」は、変更後の全文を誰が書くかを Issue 作成の前に決める記述がない。また、完了条件を「verify.sh で確かめられる形」としているが、文書が対象のときは grep・wc・git diff の値で定めることになる。
- 「原則」の「分類器エラーは自動で回復しない」が、implementer.md・publish-github・diagnose-failure の「再試行は1回まで」と食い違う。
- 「3. 上流2」は、review の重さの表記（「中」）と分類（ブロッカー／軽微／提案）の対応、check-runs が failure のときに diagnose-failure を使うことを書いていない。
- 「2. 下流」は、実装役が report-self-check を実行できなかったと報告した場合の扱いを書いていない。
