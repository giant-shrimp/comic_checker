# レビュー役のモデル非対称化：試算（下書き）

計画書（`ai-loop-implementation-plan_v8.md`）Phase 7は「レビュー役を実装より
上位モデルにする」ことを品質向上の主要因の一つとして挙げているが、
`claude-review.yml`は現在も`--model sonnet`のままで実装と同じである。
本文書は変更の是非を判断するための材料であり、**結論は出さない。**
採用・不採用はユーザが判断する。

`.github/workflows/claude-review.yml`はADR-003によりAIが編集できないため、
本文書は下書き（差分形式）の提示までを行う。配置は人間が行う。

## 2. コスト試算

### 2-1. 料金情報の出所

**情報源**: `https://platform.claude.com/docs/en/about-claude/pricing`
（Anthropic公式ドキュメント、`WebFetch`で直接取得。取得日: 2026-08-25）

| モデル | Base Input | Output |
|---|---|---|
| Claude Sonnet 5 | $2 / MTok | $10 / MTok |
| Claude Opus 5 | $5 / MTok | $25 / MTok |

**倍率（Opus 5 / Sonnet 5）**: input 2.5倍、output 2.5倍（両方とも一致）。

この価格は取得日時点のものであり、計画書が繰り返し警告する通り**変動しうる**。
以降の試算は「上位モデルの単価が現行の**N**倍」という形で倍率を変数に
置いた形にし、参考値として実測で得たN=2.5を併記する。

### 2-2. 月額換算（参考値、倍率N使用）

```
月あたり実行回数 = 97件（直近30日実測、1-2節）
月あたりコスト（換算値） = 現行の月あたりコスト × N
```

N=2.5（実測した参考倍率）を当てはめると、**現行のコスト換算値の約2.5倍**に
なる。ただし「現行のコスト換算値」自体の絶対額（USD）は、本試算では
実測できていない（後述2-3）。

### 2-3. `--max-budget-usd`が機能しないことの影響

ADR-005（`docs/decisions/ADR-005-auth-oauth-token.md`）により、
`claude-review.yml`は`CLAUDE_CODE_OAUTH_TOKEN`（サブスク枠消費、追加課金
無し）で動作しており、`--max-budget-usd`はドル建ての予算上限であるため
**機能しない**（同ADR 57行目）。したがって：

- **金額上限による歯止めが無い。** モデルを上位に変更しても、それを理由に
  自動的に予算超過で止まる仕組みは存在しない
- ERRORS.mdアーカイブに記録されている`total_cost_usd`の値
  （例: PR #90で`1.0537520999999999`）は、OAuth経由の実行でも記録されて
  いるが、これが実際のドル建て請求額を意味するのか、内部的な換算値
  （サブスク枠消費量をAPI従量課金相当に換算したもの）なのかは、
  ADR-005の記述からは断定できない。**本試算ではこの点を「未確認」とし、
  換算値として参考にするに留める。**
- 上位モデルへの変更は、実際の請求額の増加ではなく、**サブスク枠の消費
  速度の増加**として現れる可能性が高い（ADR-005「`CLAUDE_CODE_OAUTH_TOKEN`
  はProプランでも...サブスク枠を消費する（追加課金は発生しない）」）。
  この消費速度が対話セッション側の利用枠を圧迫するリスクは、ADR-004が
  当初懸念していた論点と同種である

### 2-4. 代替の歯止め

`--max-budget-usd`が使えない以上、実質的な歯止めは次の3つに限られる。

| 歯止め | 現状 | 上位モデル変更時の影響 |
|---|---|---|
| `--max-turns` | 35 | **不確実性あり（後述2-5）** |
| `types: [opened]`限定 | 適用済み（`synchronize`は含めない） | 変更の影響なし |
| `concurrency` | 適用済み（PRごとに1本） | 変更の影響なし |

**ADR-006の未解決事項を踏まえた留保**: 1-3節で引用した通り、`--max-turns`が
正確に何を数えているかは未確定であり、PR #90の矛盾（上限を超えるツール
呼び出しを経ながら成功扱いになった事例）が解決していない。したがって
「`--max-turns`が歯止めとして確実に機能している」とは言えず、**この歯止めの
確実性を過大評価しない。**

### 2-5. 上位モデルでのターン数の不確実性

現行の`--max-turns 35`は、`--model sonnet`での実測（1-3節、12〜36ターンの
観測範囲）に基づいて決められた値である（`docs/archive/
ERRORS_archive_2026-08.md`「本番値適用runの結果（6点目）」参照）。上位
モデルに変更した場合、次のいずれの方向にもターン数が変化しうる。

- **減る可能性**: より高性能なモデルは、同じレビューをより少ない試行回数
  （裏取りの往復が減る等）で完了できるかもしれない
- **増える可能性**: より慎重なモデルは、裏取りの回数自体を増やすかもしれない
  （1-3節で引用した通り、ターン数は差分の行数ではなく「レビューがどれだけ
  裏取りを行うか」に左右されることが実測で分かっている）

**現行の35が上位モデルでも足りるかは未知である。** この不確実性を明記する。
変更する場合、当面は`--max-turns`を35のまま据え置き、実測してから調整する
方が安全側に倒れる（値も同時に変えると、レビューが失敗した場合にモデルの
問題かターン数上限の問題かを切り分けられなくなる）。

## 3. 効果の不確実性

### 3-1. 断定しないこと

「レビュー役を上位モデルにすると品質が上がる」は計画書 Phase 7 の主張
であり、**本プロジェクトで検証された事実ではない。** 本プロジェクトは
これまで一度もレビューモデルを変更したことがなく、比較対象となる実測
データが存在しない。

### 3-2. 変更後に効果を測れるか

**「効果測定不能」となる可能性が高い。** 理由：

- ADR-010（`docs/decisions/ADR-010-loop-adoption-rate-not-adopted.md`）に
  より、計画書 Phase 7 の定量3指標（採用率・コスト・不具合件数）は
  本プロジェクトではいずれも判定基準として機能しないことが既に確定して
  いる
- `scripts/pr_spot_check.sh`の抜き取り確認も、判定は人間の主観
  （「1行で説明できるか」）に依存する設計であり、レビューの見逃し率を
  定量的に測る指標ではない
- レビューコメントの「質」を測る指標（見逃した不具合の件数等）は、
  `bug`ラベルの運用実績が無いこと（`docs/runbook.md`参照）も含め、現状
  存在しない

したがって、モデルを変更しても「変更前後で品質がどう変わったか」を
本プロジェクトの既存の仕組みで測ることはできない可能性が高い。

### 3-3. 効果が測れないまま変更することの是非（賛否両論）

**賛成側の根拠**:
- 計画書という一つの参考情報が推奨している設計であり、実装より上位の
  モデルでレビューすること自体は一般的に妥当性のある方針と考えられる
- コストの絶対額が高額でなければ（2-2節参照、ただし絶対額は本試算では
  未確定）、効果を測れなくても「保険」として導入するコストは相対的に
  低い可能性がある
- 一度導入しておけば、将来効果測定の手段が整備されたときに、比較対象
  データが蓄積され始める

**反対側の根拠**:
- 効果を測れないまま変更コストだけを払うのは、本プロジェクトが
  Phase 7を通じて一貫して重視してきた「実測に基づく判断」（ADR-008〜
  ADR-010がいずれも実測を根拠にしている）の原則に反する
- サブスク枠の消費速度が上がることで対話セッション側を圧迫するリスク
  （2-3節）があるが、この影響も測る手段が無い
- `--max-turns`の意味論が未解明（2-5節）なまま2つの変数（モデルと
  ターン数上限の実効性）を同時に動かすことになり、問題が起きた際の
  原因切り分けが難しくなる

### 3-4. 参考情報（因果を結びつけない）

`docs/pr_spot_check_log.md`に記録されている通り、抜き取り確認は2回連続で
3件中0件しか「説明できた」PRが無かった（`docs/runbook.md`「マージ済みPR
の抜き取り確認」節参照）。**この事実とレビューモデルの性能は無関係であり、
因果関係は無い。** 抜き取り確認はマージ済みPRを人間があとから読んで
説明できるかを問うものであり、レビュー時点でのモデルの指摘の質とは
別の測定対象である。参考情報として言及するに留める。

## 5. 推奨（根拠と反対意見を併記、決定はしない）

**推奨案は示すが、決定はユーザが行う。**

推奨: **現時点では変更を見送り、`docs/pr_spot_check_log.md`にレビュー
起因と疑われる見逃し事例が実際に記録され始めてから再検討する。**

- 根拠: 3-2節の通り、変更しても効果を測る手段が本プロジェクトに存在
  しない。ADR-010で「定量指標が機能しない」という同種の状況に対し、
  本プロジェクトは指標を無理に使い続けるのではなく「見送り、見直し
  条件を明記する」という判断を繰り返してきた（ADR-009・ADR-010）。
  今回もその一貫性に沿う
- 反対意見: 「効果を測れないから変更しない」を厳密に適用すると、
  効果測定の仕組みが整うまで永久に変更できないことになる。計画書の
  推奨事項を試すこと自体に一定の価値があるという立場もあり得る。
  コストの絶対額が小さいなら「測れなくても試す」という判断も合理的
  でありうる（3-3節賛成側）
