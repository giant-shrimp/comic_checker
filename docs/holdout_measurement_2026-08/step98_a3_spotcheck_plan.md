# 作業98-A-3: ラベル抜き取り検証の実施計画（計画のみ、着手しない）

作業91-4で計画した抜き取り検証は実施されず、その結果R1・R3の欠陥を測定完了後まで
発見できなかった（作業97-6・97-7）。今回は検証を工程に必ず組み込む。

## 1. 「迷った」の定義（ラベル付け開始前に確定、判断者間で解釈が割れない客観基準）

主観的な自信の強弱（「なんとなく迷う」）ではなく、記事の構造的な客観条件でのみ判定する。
次のいずれか1つ以上に該当する行は「迷った」とフラグを立てる。いずれにも該当しなければ
「確信」とする。

| 条件 | 内容 | 対応するラベル規則 |
|---|---|---|
| (a) | 本文（リード＋最初の`==`セクション）に、入力タイトル自身の連載状況を直接述べる文が1つも無く、判断材料がインフォボックスの値のみである | R1' |
| (b) | 本文とインフォボックスの記述が一見矛盾する（例: 本文は連載継続を示唆するが、インフォボックス終了系フィールドが非null、またはその逆） | R3' |
| (c) | 本文中に、入力タイトル自身についての記述か、別作品（スピンオフ・原作・続編・派生作品等）についての記述かが紛らわしい箇所がある | R1'・R3'共通の前提（本文の主語特定） |
| (d) | 判断の根拠となる記述が3年以上前（2023-08-13以前）の基準時点のもの（現在形だが古い） | R2 |
| (e) | 「休載中」「再開不定」の記述があり、完結宣言が同じ記事中に無い | R4 |
| (f) | 「第1部完結」等、部分的な区切りの記述があり、作品全体としての完結/連載中の判断が構造的に難しい | R5 |

この定義表自体をラベル付け作業開始前（judge()実行はもちろん、ラベル付け開始そのものより
前）に確定させ、ラベル付け中に基準を変更しない。

## 2. ラベル付け時のフラグ記録手順

- 各行についてラベル（連載中/完結/判定不能）を確定させると同時に、上記(a)〜(f)のうち
  該当した条件をすべて記録する（0件なら「確信」、1件以上なら「迷った」）。
- **judge()の出力は一切参照しない**（作業90-4以来の一貫した方針）。
- (a)〜(f)のどれに該当したかを記録しておくことで、後日の欠陥調査（R1・R3で実際に
  起きたような）の際に、どの規則に対応する行だったかを機械的に追跡できるようにする
  （作業97-6・97-7で`rule_applied`/`status_before_rules`フィールドが調査に決定的に
  役立った教訓を踏まえる）。

## 3. 確信からのランダム15件抽出のseed固定

**seed=98**（作業41・85・90・93・134で既に使用済みのため、今回の作業番号98を採用。
未使用であることを`~/comic_checker-agent-notes/`内の既存ファイルをgrepして確認済み）。

抽出手続き: ラベル付け完了後、「確信」フラグが付いた行のタイトルを
`step98_a2_sample100_titles.json`内の元の並び順のまま抽出し、
`random.Random(98).sample(confident_titles, 15)`で15件を選ぶ
（`confident_titles`の件数が15件未満の場合は全件を対象とする）。

この抽出手続きとseed=98は、事前登録`step98_a2_preregistration.json`の
`10_spotcheck_sampling_procedure`フィールドに追記し、凍結済み（PR #147へ追加コミット）。
抽出時に人間・AIいずれの裁量も入らないこと（`random.Random(98).sample(...)`の実行結果を
そのまま採用し、事後の入れ替えを行わないこと）を`no_discretion_note`として明記した。
「確信」集合が15件未満の場合は全件を対象とする、という扱いも明記済み。

## 4. 検証者（ユーザ）への提示形式

盲検性を確保するため、次の順序で提示する。

1. **第1段階（AI側ラベル非開示）**: 対象記事の該当箇所（リード＋最初のセクションの
   関連文）と、インフォボックスの終了系フィールド・巻数フィールドの生値のみを提示する。
   AI側のラベル・根拠・judge()の出力はいずれもこの段階では一切開示しない。
   ユーザはこの材料だけを見て、独立に「連載中/完結/判定不能」を判断する。
2. **第2段階（突き合わせ）**: ユーザの判断が出そろった後に、AI側のラベル（および
   該当した(a)〜(f)条件）を開示し、一致/不一致を突き合わせる。
3. **judge()の出力は、検証完了・ラベル凍結の確認が取れるまで一切提示しない**
   （98-A-3の絶対条件そのもの。作業98-A全体の停止条件にも明記されている）。

提示は対象タイトルごとに1件ずつ独立したブロックとして用意し、他の行の判断結果が
ユーザの目に入って後続の判断に影響しない形（前の行の一致/不一致を都度明かさず、
全件の第1段階が終わってから一括で第2段階に進む）で行う。

## 5. 不一致時の扱い（事前に決める閾値と根拠）

| 条件 | 対応 | 根拠 |
|---|---|---|
| 確信15件中1件以上が不一致 | **全100件を再ラベルする。** | 確信ラベルは「規則上、疑いなく判断できた」行のはずであり、そこに誤りが見つかった場合は個別の行の誤りではなく、ラベル付け手順（読解・規則適用の一貫性）自体に系統的な問題がある可能性が高い。R1・R3の欠陥がまさに「機械的な規則適用が原ラベルの正しい判断を上書きしていた」という同種の問題だったこと（作業97-6・97-7）を踏まえ、確信集合での不一致は1件でも軽視しない。 |
| 迷った全件のうち、不一致率が30%超 | **全100件を再ラベルする。** | 「迷った」行は(a)〜(f)のいずれかに該当する、判断が割れやすいことを織り込んだ集合であるため、一定の不一致は許容範囲として想定している。しかし3割という閾値は、コイン投げ的な五分五分（50%）よりは十分低く、かつ少数の偶然のばらつき（1〜2件程度）よりは高い水準として設定した。3割を超える不一致は、(a)〜(f)の判断基準自体か、規則v3の適用そのものに問題がある可能性を示す統計的に無視できない兆候とみなす。 |
| 迷った全件のうち、不一致率が30%以下 | **不一致が出た行のみ再検証・修正する。** 残りの行はそのまま凍結する。 | 不一致が想定内の範囲に収まっており、個別の行の判断の割れとして扱ってよい。 |
| 確信15件・迷った全件とも不一致0件 | ラベルをそのまま凍結し、judge()実行へ進む。 | 抜き取り検証で欠陥が見つからなかったことを示す。 |

## 6. 人間側の想定作業量

- 「確信」からのランダム15件は確定（seed=98で固定）。
- 「迷った」の件数はラベル付け完了まで不明。参考値として、作業91の100件（規則v2）では
  100件中28件が「迷った（confused）」に該当した（`step92_0_labels_frozen.json`実測）。
  同程度の比率（およそ20〜30件）を見込む。
- 想定検証件数: 15件（確信）＋20〜30件（迷った、見込み）＝ **合計およそ35〜45件**。
- 1件あたりの所要目安: 記事の該当箇所（数文〜1段落程度）とインフォボックスの生値を
  読み、連載中/完結/判定不能を判断するのに **2〜3分程度**（`step93_3_blind_spotcheck.md`
  の資材形式を踏襲する想定）。
- **合計の想定所要時間: 70〜135分（およそ1〜2.5時間程度）。**

## 7. 検証作業の分割単位と中断・再開手順

想定70〜135分は1セッションで終わらない可能性が高い。中断して再開する際、第2段階
（AI側ラベル開示）を見た記憶が、未検証行の独立判断を汚染するリスクがある
（作業93-3で「盲検のつもりが実際は盲検でなかった」という同種の失敗が既に一度
起きている）。

### 7-1. 分割単位（両論併記のうえ推奨を示す）

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A: 第1段階を全件終えてから第2段階へ | 全35〜45件の独立判断（第1段階）をすべて終えるまで、いかなる行についても第2段階（AI側ラベル開示・突き合わせ）を行わない。第1段階自体は複数セッションに分けてよい。 | 汚染の可能性がゼロ。どの時点で中断しても、再開時に見るのは常に「未検証の第1段階材料」だけであり、判断基準がぶれない。 | 全件の判断結果が出そろうまで、ユーザは自分がどれだけ正しく判断できているかのフィードバックを一切得られない。 |
| B: 小バッチ（例: 5件）ごとに第1段階→第2段階を繰り返す | 5件ずつ独立判断→突き合わせ、を8〜9回繰り返す。 | 早期にフィードバックが得られ、提示形式自体の分かりにくさなどの問題を早期に発見できる。作業の区切りが付けやすく再開しやすい。 | 早いバッチでAI側ラベルを見た後、後続バッチの独立判断に無意識の影響（AIの傾向へのパターンマッチング・アンカリング）が及ぶ汚染リスクがある。 |

**推奨: 案A（第1段階を全件終えてから第2段階へ）。** 本プロジェクトは既に一度、
「盲検のつもりが実際には盲検でなかった」失敗（作業93-3、対話継続中のAIが92-5の
パターン分析を読んだ状態でレビューしていた）を経験しており、汚染回避を作業負荷の
軽減より優先する方針を維持する。中断・再開は案Aのまま複数セッションに分けて対応する
（7-2参照）ため、案Bの「早期フィードバックが無いと辛い」という欠点は、
セッションを分けること自体で一定程度緩和できる。

### 7-2. 中断時に保存するもの・再開時に見てよいもの／見てはいけないもの

- **保存するもの**: 第1段階で既にユーザが判断を下した行について、「タイトル」と
  「ユーザの判断（連載中/完結/判定不能/判断できない）」のペアのみを
  `step98_a3_verification_progress.json`（仮称）に追記する。この working file には
  AI側のラベル・根拠・(a)〜(f)条件のいずれも一切含めない。
- **再開時に見てよいもの**: 未検証（第1段階が未実施）の行の記事該当箇所・
  インフォボックス生値のみ。加えて「あと何件残っているか」という件数のみを
  進捗として提示してよい。
- **再開時に見てはいけないもの**: 既に判断済みの行の内容の再表示（自分の過去の
  判断を見て考え直す余地を与えない——一度下した判断は確定として扱う）。
  AI側のラベル・(a)〜(f)条件・judge()の出力は、全件の第1段階が終わるまで
  一切見せない。

### 7-3. 人間の判断結果の記録形式

- 1行＝1判定として、`{"title": ..., "user_judgment": "連載中|完結|判定不能|判断できない"}`
  の形で記録する。AI側ラベルへの参照・混在は無い、独立したファイルとする。
- 全件の第1段階が終わった時点で初めて、このファイルとAI側ラベルを突き合わせる
  第2段階のスクリプトを実行する。

### 7-4. 「判断できない」と答えた行の扱い

- 「判断できない」という回答は、AI側ラベルとの一致・不一致のどちらにも数えない。
  **別カテゴリ「判断保留」として集計する。**
- 不一致率の計算式は「不一致件数 / (総検証件数 − 判断保留件数)」とする
  （分母から判断保留を除外する。理由: 一致/不一致は『ユーザが判断を下せた場合の
  結果』を測るものであり、判断を下せなかった行を分母に含めると、判断保留が
  多いだけで見かけ上の不一致率が下がってしまい、閾値判定が歪む）。
- ただし判断保留件数自体も別途報告する。確信15件のうち1件でも判断保留が出た場合、
  または迷った全件のうち判断保留が20%を超えた場合は、それ自体を「検証資材の
  提示形式（記事該当箇所の切り出し方等）に問題がある」シグナルとして扱い、
  資材の設計を見直す（本プロジェクトのfail-closedの考え方——不確実な結果を
  安易に丸めて処理しない——を検証プロセス自体にも適用する）。
