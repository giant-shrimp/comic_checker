# ホールドアウトプール管理

## 目的

修正の発見材料となった標本で修正の効果を測ると過大評価になるため，
発見材料と評価標本を分離する目的で維持されているタイトルプールである．

## 構成

| ファイル | 内容 |
|---|---|
| `step93_2_holdout_pool.json` | プール全体（362件のタイトル） |
| `step90_1_used_titles.json` | 使用済みタイトル |
| `step98_a2_sample100_titles.json` | seed=93 で抽出された100件 |

消費記録は `docs/code_defects_2026-08/holdout_pool_consumption_ledger.json` に置く．

## 管理ルール

### 1. 抽出条件は結果を見る前に確定する

`judge()` の出力を見てから抽出対象を選ぶと選択バイアスが入り，
事前登録の意味が失われる．抽出条件（seed，件数，フィルタ）は
抽出実行前に事前登録文書へ記載し，コミットする．

### 2. 記事なしタイトルもプールから恒久的に除外される

抽出時点で Wikipedia 上に記事が存在しないと判明したタイトルも，
seed 消費済みとして扱いプールへ復帰させない．

過去の実績: 362件のプールから seed=93 で100件を抽出した際，
「ガッ活!」は記事が存在せず wikitext を取得できなかったが，
残数は 362 - 100 = 262 として扱われている．

したがって N 件を抽出しても実際に wikitext が得られる件数は N より少ない．
過去実績では約99%が有効であった．

### 3. 観測した標本は評価用標本ではなくなる

`judge()` の出力を観測した時点で，その標本は発見材料に転化する．

現行の holdout 99件は，系統1・案B・系統3・系統4-A・系統4-B の各検証フェーズが
毎回160件全件を走査する設計であったため，実質的に全件が観測済みである．
評価用標本としては既に機能していない．

真の有効性の証拠を得るには，未消費プールからの新規抽出が必要である．

### 4. プール実体はリポジトリ内に置く

事前登録の三値ロック（HEAD hash + 文書の md5sum + git log hash）の対象と
するため，プール実体はリポジトリ管理下に置く．
リポジトリ外にのみ存在する導出物は再現性を担保できない．
