# M6-D-3 期待値ラベルの判断根拠

**ラベルの値は `scripts/m6d3_labels.py` が正。このファイルはその「なぜ」を残すもの。**
両者は役割が違うので、片方だけを見ないこと。

- `scripts/m6d3_labels.py` … 72行＋22行のラベル（期待記事名・期待ステータス・記事実在・
  カテゴリ・マーク）と、件数の自己検算（`_self_check()`）
- **このファイル** … 各行をなぜその期待値にしたか、マーク体系がどう育ったか、
  **途中でどの判断を撤回したか**

測定の設計・指標・結果は Issue #47 にある。
https://github.com/giant-shrimp/comic_checker/issues/47

ラベルを将来見直すときは、まずこのファイルを読むこと。**判断根拠が無いと同じ議論を最初から
やり直すことになる。** 実例として、[57] のラベルを測定後に訂正できたのは、ラベル付け時に
「何を材料にして、何を材料にしなかったか」を残していたからである（§6）。

**⚠ このcensus（72行＋22行）を一般的な判定精度の測定に使ってはならない
（作業89-1・90で判明、Measured 2026-08-13）。** Issue #51（M6-A-2、
`_mentions_as_derivative_work()`）は、この拡張群72行を「失敗を探す検索空間」として
使い、実際に見つかった誤答（[23]彼女、人見知ります・[55]お隣の天使様に…件
after the rainがどちらもD＝確信を持った誤答）を根拠に機能を設計し、回帰群22行
（[105]バジリスク・[106]フラジャイル・[111]精霊の守り人を含む）で検証した
（`comic_checker/wikipedia_client.py`のDERIVATIVE_WORK_MARKERS前後のコメント、
および`ERRORS.md`「#51の`scripts/m6d3_labels.py`が先例で」を参照）。加えて
対照群の`日常`（[201]）は、Issue #38・Issue #41調査（作業62）双方の直接の
設計根拠として使われている。

**このため、census を測定してもIssue #51以降の変更の「効果」を測ることは
できない。** 効果測定に使うと、既に一度「炙り出されて直された」既知の失敗を
再確認するだけの循環的な測定になる。一般的な判定精度を測る場合は、この
census（および関連するIssue #35・Issue #53の各コーパス、旧30件・新30件・
Issue #41母集団等）のいずれとも重複しない独立標本を新規に用意すること
（作業90〜94で実施した`docs/accuracy_baseline_2026-08.md`の測定を参照。
既使用タイトルの棚卸しは`~/comic_checker-agent-notes/step93_1_used_titles_v2.json`
にある、リポジトリ外）。

**censusとして今も有効な用途**: Issue #51以前の変更（#36・#37・#45等）に対する
回帰確認、および回帰群22行によるIssue #35ベースライン（偽陰性率35.0%／
判定不能率36.4%／誤答率9.1%）との**同一母集団での直接比較**。この用途では
census自体が比較対象の定義そのものなので、独立性の問題は生じない。

## 1. 母集団の性質（結果を読む前に必ず読むこと）

拡張群の72タイトルは、M6-E-1（#30）で使った実運用 Excel（73行）から #35 の57件と重複する
1件（`一緒に暮らしていいですか?`）を NFKC 正規化後の完全一致で除外した**全数**である。
標本抽出ではない。

**全件が実際に発売されたコミックである**（e-hon https://www.e-hon.ne.jp/bec/EB/Top で確認）。
入力ミスや架空のタイトルは1件も含まれない。したがって:

1. 期待値 `記事なし` は「**Wikipedia に記事が無い**」という意味であり、「作品が存在しない」
   でも「入力が誤っている」でもない。
2. **`記事なし` が 32/72 = 44.4% を占めるのはツールの失敗ではなく母集団の性質である。**
   結果を読む人が「入力データが汚い」と誤読しないこと。
3. 実運用の入力には Web連載・成年向け・レーベル系など、**Wikipedia に記事が作られにくい
   作品が相当数含まれる**。#35 のサンプル（全件で記事が実在する前提で構成）とはこの点で
   決定的に性質が違う。

**実運用 Excel 本体はコミットしていない。** リポジトリに入っているのはタイトル文字列と
ラベルのみ。

## 2. カテゴリ体系（#35 との違い）

**#35 のカテゴリ1〜4・対照群は「サンプリング設計」の区分**である。failure mode を炙り出す
ために各カテゴリを意図的に構成し、対照群を正常系の分母として置いた。一方**拡張群は実分布
からの抽出なので、カテゴリは構成ではなく「記事選定の結果として観測された現象」**になる。

| 本記録での呼称 | 定義 | #35 との対応 |
|---|---|---|
| **正常系** | 入力に対応する作品記事へ正しく着地した | #35 の「対照群」に相当するが、**構成ではなく観測結果** |
| **記事なし（不在）** | 該当作品の記事もリダイレクトも存在しない | #35 に対応区分なし |
| **2（作者記事）** | 作品記事が無く、作者記事へのリダイレクトに着地 | #35 カテゴリ2 と同じ現象 |
| **3（親作品）** | スピンオフ／続編が親作品の記事に着地 | #35 カテゴリ3 と同じ現象 |
| **1（別ジャンル同名）** | 同名の別ジャンル記事に着地 | #35 カテゴリ1 と同じ現象 |
| **4（検索順位低）** | **本測定では判別しない** | #35 カテゴリ4 |

**「対照群相当」から「正常系」へ改称した。** 「対照群」は標本設計の用語（比較のために意図的に
置いた群）であり、実分布から偶然正しく着地した行を指す語としては不正確で、読む人が
「拡張群にも対照群を設けた」と誤読しかねないため。カテゴリ1〜4 は現象そのものを指す語なので
流用してよい。

**カテゴリ4 を判別しない理由**: 「記事は実在するが `list=search` の上位に出ない」は、
`_pick_article()` が直参照で解決してしまえば**正常系と見分けがつかない**。判別には検索順位の
別途取得が必要で、本測定の3指標には寄与しない。カテゴリ4 相当の行は正常系に含めて数える。

## 5. 回帰群（#35 のカテゴリ1＋対照群・22行）

**拡張群とは別物なので混ぜて集計しないこと。** 置いている目的は #35 のベースラインとの
**同一母集団での直接比較**のみ。ラベルは #35 当時の**旧定義**（本文のみ・インフォボックスを
見ない）のまま据え置いている。

**新定義で付け直さない理由**は3点。

1. **回帰群の存在理由は比較可能性のみ。** 20行しかなく実分布の率を出す群ではない。ラベル
   定義を変えると、測定された差分が「コード変更の効果」なのか「ラベル定義の変更」なのかを
   分離できなくなる。
2. **回帰群では旧定義のラベル誤りが確認されていない。** #35 §4 が挙げた期待値の設定誤り
   2件はどちらもカテゴリ4 で、回帰群には含まれない。
3. 付け直すと新規ラベル付けが 60 → 82 件に増え、作業量の上限を超える。

**据え置きの代償は実測で潰した。** 回帰群22行のインフォボックス終了系フィールドを機械取得
した結果、**新定義ならラベルが変わりうる行は 0 件**だった。旧定義で `判定不能` としている
[109] 墨攻・[110] 銀河英雄伝説 がどちらも「漫画インフォボックスなし」で判定材料を持たない
ことが決め手。**旧定義据え置きの判断に実害は無かった。**

ラベルは #35 本文の2つの表から**機械的にパースして取り込んだ**（手入力しない）。
`scripts/m6d3_labels.py` の `_self_check()` が、件数22行・期待ステータス分布・偽陰性率の
分母20・#35 段階1 の生データとの1対1対応を検算する。

## 6. 途中で訂正した判断（記録）

**訂正の事実も記録の一部である。** 同じ誤りを繰り返さないため、また「なぜ今の形なのか」を
辿れるようにするために残す。

### 6-1. 機械推定のカテゴリ判定基準を訂正した（ラウンド3）

ラウンド1〜2 では**「着地先タイトルが入力と不一致 → カテゴリ3」**という推定を使っていたが、
これは誤りだった。カテゴリ3 は「スピンオフ／続編が親作品にリダイレクトし、**別作品**の記事に
着地した」場合のみを指す。**入力側のノイズ**（`(特装版がない場合通常版）` 等）が除去されて
**同一作品**に着地したものはカテゴリ3ではない。

- **誤推定した行**: [5] わたしの幸せな結婚、[8] 姫騎士がクラスメート!（どちらも正しくは正常系）
- **訂正後の基準**: 着地先が `_title_variants()` の生成する変種（＋ ` (漫画)` 形）のいずれかと
  NFKC 一致するか

### 6-2. [57] リコリス・リコイルのラベルを `判定不能` → `連載中` に訂正した（測定後）

**ラウンド6 のラベル付け時点では `判定不能`（M-8）としていた。** 根拠は「一次分類が
アニメーション作品で、走査範囲に漫画版の連載状況が一切書かれておらず、人間が読んでも
断定できない」というものだった。

測定で **C（偽陽性）**として出たため精査した結果、**2点の理由で訂正した**。

1. **同一機構で5行が正答していた。** `地の文が判定不能 → インフォボックスの終了系が空欄 →
   連載中` というまったく同じ経路で [13][19][28][52][72] が A になっている。[57] だけ別基準を
   当てるのは測定として一貫しない。
2. **ラベル付け時に決定的な材料を欠いていた。** 提示したのは
   `終了号 =（空欄）/ 終了日 =（空欄）` だけで、**`巻数 = 既刊8巻（2026年1月現在）` を
   材料に含めていなかった**。「既刊」は空欄の消極的解釈ではなく**継続中であることの積極的な
   記録**である。

記事の実データも確認した。採用された本編ブロックは**入力作品（『リコリス・リコイル』の
漫画版・コミックフラッパー連載）そのもの**で、スピンオフ『リコレクト』（`終了日` あり）の
別ブロックとは正しく区別されている。

**影響**: 分母 38 → 39、判定ロジックの正答率 90.5% → 92.9%、誤答率 4.2% → 2.8%（**偽陽性 C は
0件になった**）、1件あたりの変動幅 2.63 → 2.56 ポイント。

**この訂正で消えなかったもの**: 「空欄 ⇒ 連載中」にゲートが無いという構造上の問題は、
[57] 個別ではなく上記6行すべてに関わる。`docs/known_limitations.md` に記録済み。

### 6-3. M-8 の定義を見直した（測定後）

当初は「判定に必要な情報が走査範囲に存在しない」＝「**分母外・分類Aの正解**」と定義して
いたが、[57] ではインフォボックスに情報があり、そこで `連載中` が決着した。
**走査範囲（地の文）に判定材料が無いのは事実**なのでマークは [57] に残し、効く指標だけを
**「インフォボックス経路への依存」**に改めた。

この見直しで M-2 と M-8 の関係が明確になった。

```
M-2（語形は無いが連載の記述はある）= [13][19][28][52][72]
M-8（記述自体が無い）              = [57]
→ 和集合が、インフォボックス経路で決着した6行と完全に一致する（6/42 = 14.3%）
```

`scripts/m6d3_labels.py` の `_self_check()` にこの対応を不変条件として固定した。

### 6-4. 「M-2 が全件 A だった理由」の分析を訂正した（測定後）

測定直後は「M-1・M-2 が全件 A だったのは**他の経路で救済されていた**ため」と曖昧に述べたが、
実際は**インフォボックス補助経路（#12）が決着させていた**。M-2 の5行は**地の文の語彙では
一切判定できておらず、全面的にインフォボックス経路に依存**している。「語彙が対応した」わけ
ではない。

### 6-5. 60件抽出 → 72件全数調査へ設計変更した（ラウンド4終了時点）

起票時は「NFKC 昇順ソート → `random.Random(20260728).sample(k=60)`」で60件を抽出する設計
だったが、ラウンド4終了時点（40件ラベル済み）で分母率が 60.0% で安定し、**60件時点の分母が
約36**と判明した。#47 の分岐「N が 40 を下回ったら検出力不足を明記」に該当することが確実に
なったため、**重複除外後の72件全数**に切り替えた。

- 標本抽出をやめるので抽出に伴う不確実性が消える
- **`random.sample` の Python バージョン依存という再現性の懸念も同時に解消**する
- 追加ラベルは12件のみ

**番号は 1〜72 で固定し、振り直していない**（確定済みラベルの番号がずれるのを避けるため）。
1〜60 は当初の抽出時の番号をそのまま維持し、61〜72 は末尾に追加した分である。

## 8. ラベル付けの運用（次回のために）

7ラウンド（10件×6＋12件×1）で完了した。当初見積り「60件・約1時間」を上回る72件を、
見積り内の時間で処理できた。効いたのは次の点。

1. **人手の判断を「期待ステータス」と「期待記事名の確定」の2項目に絞った。** 記事実在・
   カテゴリ・期待記事名の候補は機械が提案し、人間は確認するだけにした。
2. **記事の有無で提示形式を分けた。** 記事が無い行（32/72 = 44.4%）は「候補なし」と理由
   1行だけを出し、全文を出さない。判断は「期待値が `記事なし` でよいか」の確認で済む。
3. **セクション本文は提示せず、キーワードで機械判定した。** `== あらすじ ==` 等の本文は
   出さないが、**単純省略はしない**（実装が読む範囲と土俵をずらさないため）。省略部分に
   `連載 / 完結 / 終了 / 休載 / 打ち切り / 最終回` が含まれるかを機械判定して1行で報告し、
   含まれる場合は**該当文のみ抜粋**、省略したセクション名も明示する。
4. **`_fetch_extract()` を 2.5 秒間隔で逐次呼ぶ。** `generator=search` によるバッチ取得は
   この用途では使えない（必要なのは実装が読むのと同じ「リード＋最初の `==` セクション」で、
   `exintro` は導入部しか返さない）。詳細は `ERRORS.md`。
5. **インフォボックスの終了系フィールドを併記する。** #47 の新定義（期待ステータスは
   インフォボックスも見て決める）に対応するため。#35 §4 が申し送りとして記録したとおり、
   実装は既定でインフォボックス補助経路も使うので、地の文だけで期待値を決めると実装が
   正しいのにラベル側が誤る。

**再現性の注意**: 期待値は「その時点の記事本文」に対するものである。Wikipedia の記事は
更新されるため、ラベルと実挙動は時間とともに乖離しうる（`docs/known_limitations.md` の
「緑のテストスイートは実データでの正しさの証拠にならない」を参照）。測定日は 2026-07-28。
