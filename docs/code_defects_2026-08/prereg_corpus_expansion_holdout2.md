## 1. 目的

未観測の評価用標本を再構築する．

現行 holdout 99件は，系統1・案B・系統3・系統4-A・系統4-B の各検証が毎回160件全件を
走査する設計であったため，実質的に全件が観測済みであり，評価用標本として機能していない
（`docs/holdout_pool_2026-08/README.md` 管理ルール3）．

本作業の主目的は，現行 `judge()` の実力を未観測標本上で測定することであり，
特定の欠陥Issueの有効ヒット件数を基準（≥2）まで押し上げることではない．

### 1-1. 件数追跡型の拡張を目的としない理由

トリアージ調査の点推定によれば，#157・#156 の各案件が有効ヒット2件に到達するには
総母数320件（追加160件）が必要である．一方プール残数は262件であり，
全消費しても点推定では届かない．

したがって「特定案件のために拡張する」という設計は成立しない．
欠陥の新規発見は副次的成果として扱い，成否の判定基準には含めない．

## 2. 抽出条件

以下は結果を観測する前に確定し，本文書のコミットをもって固定する．

| 項目 | 値 |
|---|---|
| 抽出元 | `docs/holdout_pool_2026-08/step93_2_holdout_pool.json` の未消費262件 |
| seed | 158 |
| 抽出件数 | 120 |
| 抽出方法 | 未消費262件を昇順ソートし `random.Random(158).sample(pool, 120)` |
| 除外 | `step98_a2_sample100_titles.json` の100件（消費済み） |

抽出件数を262件全量ではなく120件とする理由は，次回以降の未観測標本を残すためである．
本作業後のプール残数は142件となる見込みである．

## 3. スナップショットの分離

新規取得分は既存コーパスに統合せず，独立したスナップショットとして保存する．

| 項目 | 値 |
|---|---|
| 格納先 | `docs/holdout2_measurement_2026-08/holdout2_wikitext.json` |
| 自動ラベル | `docs/holdout2_measurement_2026-08/holdout2_labels_auto.json` |
| スポットチェック結果 | `docs/holdout2_measurement_2026-08/holdout2_spotcheck.json` |
| 既存160件との関係 | 統合しない．別標本として並存させる |

統合しない理由は，既存160件が観測済みであるのに対し新規分は未観測であり，
両者を混ぜると再び「発見材料と評価標本の分離」が崩れるためである．

## 4. 予測

**以下の値は本文書のコミット後，一切変更しない．**

### 4(a) 分布に関する予測

現行 `judge()` を新規標本に適用したときの出力分布は，
既存160件での出力分布から **各カテゴリ ±10ポイント以内** に収まると予測する．

根拠: 新規標本は既存標本と同一プール・同一の抽出条件
（hastemplate による Infobox animanga/Manga 絞り込み）から得られるため．

### 4(b) 正解率に関する予測

新規標本での正解率（自動ラベルと `judge()` 出力の一致率）は，
既存160件での正解率より **低くなる** と予測する．

根拠: 既存160件は系統1〜4の修正が観測材料として使用してきた標本であり，
修正がこの標本に過剰適合している可能性がある．未観測標本ではその分だけ落ちる．

予測する低下幅: **5〜15ポイント**．

この予測が外れる（低下幅が5ポイント未満，または正解率が上がる）場合，
それは過剰適合が想定より小さかったことを意味し，記録に値する肯定的な結果である．

### 4(c) 自動ラベルの精度に関する予測

自動ラベルとスポットチェック（人手）の一致率は **85%以上** と予測する．

一致率が 85% を下回った場合，自動ラベルは正解率比較の基準として使用できない．
その場合は 9-3 の縮退手順に従う．

## 5. 判定基準

本作業は以下をもって完了とする．成否ではなく完了条件である．

1. 新規標本の wikitext 取得が完了し，スナップショットが保存されている
2. 全件に自動ラベルが付与されている
3. スポットチェックにより自動ラベルの誤り率が実測されている
4. 現行 `judge()` の出力と自動ラベルの照合結果が記録されている
5. 4(a)(b)(c) の予測と実測の対比が記録されている
6. ledger に seed=158 の消費が記録されている

予測が外れた場合も本作業は完了とする．予測の的中は完了条件ではない．

## 6. ラベル付与の手順（自動化）

期待ラベルは Claude Code が wikitext を読み，
`docs/holdout_measurement_2026-08/step98_a_labeling_rules_v3.json` の R1'〜R5 を
適用して付与する．人手による全件確認は行わない．

### 6-1. 自動ラベルが成立する条件

ラベル生成器（本文を読解して規則を適用する LLM）と被検査対象
（正規表現ベースの `judge()`）は別機構である．両者が独立しているため，
自動ラベルを `judge()` の評価基準として用いることは循環論法にあたらない．

ただし自動ラベル自体に誤り率があるため，9節のスポットチェックにより
その誤り率を実測しない限り，正解率の比較は成立しない．

### 6-2. ラベル生成時の制約

- `judge()` および `wikipedia_client.py` の関数を一切実行しないこと
- 正規表現による機械的な判定を行わないこと（`judge()` の模倣になり独立性が失われる）
- 各件に `evidence_summary`（判断根拠の自由記述）を必ず付与すること
- 判断に迷った件は `confused: true` を付与すること
- `confused_conditions` の記号 a〜f は定義文書が失われているため使用しない

### 6-3. 手順の順序（固定）

1. wikitext を取得する
2. 自動ラベルを付与する（`judge()` は実行しない）
3. 自動ラベルをコミットして固定する
4. スポットチェックを実施する
5. その後に `judge()` を実行し，照合する

ステップ3のコミット前にステップ5を実行した場合は，プロトコル違反として記録し停止する．

## 8. 想定されるリスク

- **自動ラベルの誤り**: 最大のリスク．9節のスポットチェックで実測する．
- **記事なしタイトルの混入**: 過去実績では約99%が有効．120件抽出で1〜2件の欠損を想定する．
- **プール枯渇**: 本作業後の残数は142件．次回120件規模を引く余地はあるが，その次は無い．

## 9. スポットチェック（人手作業）

### 9-1. 対象の選定

自動ラベル付与・コミット完了後に，`random.Random(1580).sample(labeled, 20)` により
20件を抽出する．抽出は自動ラベルの内容を見てから行うが，
**`judge()` の出力を見る前に**行う．

`judge()` の出力を見てからスポットチェック対象を選ぶと，
不一致箇所を狙って選ぶバイアスが入るため禁止する．

### 9-2. 実施内容

ユーザが20件それぞれについて，wikitext と自動ラベルを対照し，
ラベルが妥当かを判定する．判定は以下の3値とする．

| 判定 | 意味 |
|---|---|
| 一致 | 自動ラベルが妥当 |
| 不一致 | 自動ラベルが誤り．正しいラベルを記入する |
| 判断不能 | 人手でも判断がつかない |

一致率 = 一致件数 / (20 − 判断不能件数)

### 9-3. 一致率が 85% 未満だった場合の縮退手順

自動ラベルは正解率比較の基準として使用できない．以下に切り替える．

1. 4(b) の正解率予測は「検証不能」として記録する（予測を書き換えてはならない）
2. 4(a) の分布予測のみを検証対象とする（これは自動ラベルに依存しない）
3. 自動ラベルは参考値として保存するが，`_auto` のサフィックスを外さない
4. 全件人手ラベルへの切り替えは，別途あらためて判断する

一致率が低かったこと自体が，LLM によるラベル自動化の限界を示す記録として価値を持つ．
