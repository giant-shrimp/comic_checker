## 0. ミューテーションテスト設計の妥当性確認（作業0の結果）

### 0-1. 「書籍化された」の代替語共用は目的を達成するか

**問い**: 「書籍化された」を追加した状態で、代替語「掲載された」によるミューテーションが
陽性になったとして、それは「書籍化された」の追加が効いていることの証拠になるか。

**判断: ならない。** 理由は次のとおり。

- ミューテーションテスト（`verification_procedure.md`手順5）の目的は「検証系自体に
  判別力があることを示す」ことであり、**対象語彙固有の効果を証明することではない**。
  系統1が対象語彙「続編」自体ではなく別の頻出語「コミカライズ」を使ったのは、まさに
  この区別（母集団・ハーネスの一般的な感度 vs 対象語彙固有の効果）を明確にするため
  だった。
- 「掲載された」による陽性結果が示すのは「COMPLETED_WEAK_RE相当の機構に何らかの
  リテラルを追加すれば、この母集団・ハーネスは変化を検出できる」という**機構レベル
  の一般的な感度**であり、「書籍化された」という**特定のリテラルが正しく機能するか**
  （誤爆を起こさないか、意図した行に正しく効くか）は別の問題である。
- 「書籍化された」固有の効果は、手順4（ポジティブコントロール）が既に別途担う。
  実際、「書籍化された」自体の影響件数は**3件**（姫騎士がクラスメート！THE COMIC・
  うちのトコでは・ゴーストワールド (コミック)、`effective_hit_rate_analysis.md`実測）
  であり、これが「書籍化された」固有の効果を示す一次証拠である。

**結論**: `prereg_v2_effective_count_basis.md`の「個別の代替語再選定は不要と判断する」
という記述は、結論自体（代替語プールを共用してよい）は妥当だが、**その理由の書き方が
不十分**だった。正しい理由は「機構が同じだから」ではなく「『書籍化された』固有の
検証は手順4（実際の3件）が既に担っており、手順5はあくまで機構レベルの一般的な
感度チェックであって、対象語彙ごとに個別化する必要がそもそも無いから」である。

### 0-2. 「書籍化された」専用の負のコントロールは必要か

**判断**: 追加では不要。理由は0-1のとおり、「書籍化された」固有の検証は手順4
（実際の影響3件）が既に果たしており、手順5に固有の負のコントロールを追加で
求める必要はない。ただし手順5自体（機構レベルの感度チェック）は実施する
（4節参照、対象は「掲載された」等の共用候補でよい）。

### 0-3. 現コーパスに候補語が存在するか（静的走査で実測）

`~/comic_checker-agent-notes/step102...`作成時に実測済みの値をそのまま使う
（正規表現定義の書き写しによる機械的走査。`judge()`等は未使用）。「書籍化された」を
対象に追加した状態でも、候補語自体の出現・影響件数（掲載された21/4、刊行された
17/3、発売された20/3、発表された10/3、出版された5/2）は変わらない（候補語の
判定は「書籍化された」の有無に依存しない独立した走査のため）。存在は確認済み。

### 0-4. 同じ設計上の穴は案Bのミューテーション設計にも及ぶか

**及ぶ。** 案Bのミューテーションテストは「コミカライズ」を`_has_ongoing_signal()`の
SPINOFF除外機構へ一時追加し、フリップ候補7件を確認する設計である
（`prereg_v2_effective_count_basis.md`4節）。これも0-1と全く同じ構造の問題を持つ:
**「コミカライズ」でのフリップが陽性であることは、`_has_ongoing_signal()`への
SPINOFF_MARKERS除外という機構が一般に判別力を持つことを示すのみであり、対象語彙
「続編」自体が正しく機能する（陰陽師・バーテンダー à Tokyoの2件で正しい方向に
変化する）ことの証拠にはならない。** 「続編」固有の効果は、手順4（実際の影響
2件、本文書1〜3節）が別途担う。

**この文書（案Bの事前登録）ではこの区別を明示する**（2-5節参照）。系統1・
「書籍化された」・案Bのいずれについても、**ミューテーションテスト（手順5）は
機構レベルの一般的感度チェック、ポジティブコントロール（手順4）は対象語彙固有の
効果の証明、という役割分担を今後の事前登録・報告で明示的に区別すること**を、
今回の点検から得た運用上の教訓として記録する。

## 1. 変更案の確定

### 1-1. 対象箇所と正確なコード差分

`comic_checker/wikipedia_client.py` L632-634（現行）:

```python
def _has_ongoing_signal(extract):
    """走査範囲内に、明確な現在形の連載シグナルが1文でもあるか（M6-B-3）。"""
    return any(ONGOING_RE.search(sentence) for sentence in _split_sentences(extract))
```

案B適用後（想定差分。本体は編集しない。4節・2-4節のハーネスで切り替える）:

```python
def _has_ongoing_signal(extract):
    """走査範囲内に、明確な現在形の連載シグナルが1文でもあるか（M6-B-3）。

    Issue #154（案B）: SPINOFF_MARKERSに一致する文（番外編・スピンオフ・外伝・
    次世代編・続編についての文）は、本編ではなく派生作品の状況を述べている
    可能性があるため、走査対象から除外する。
    """
    return any(
        ONGOING_RE.search(sentence)
        for sentence in _split_sentences(extract)
        if not any(marker in sentence for marker in SPINOFF_MARKERS)
    )
```

### 1-2. 呼び出し箇所は2つあり、Issue #154の記述は1つしか説明していない

`grep`で実際に特定した呼び出し箇所は次の2つ。

- **L672（`_judge_extract()`内）**: `has_ongoing_elsewhere = _has_ongoing_signal(extract)`。
  M6-B-3（Issue #30）由来の、弱シグナル完結（`weak_completed`）を取り消すveto判定に使う。
- **L1255（`judge()`本体）**: `if infobox_status == "完結" and _has_ongoing_signal(extract):
  infobox_status = None`。インフォボックス経路の完結判定を無効化するveto判定に使う。

**Issue #154の本文が説明しているのはL1255（インフォボックスveto）のみである。**
L672（`_judge_extract()`内部のM6-B-3 veto）への影響はIssue本文に記述がない。
`_has_ongoing_signal()`は1つの関数であり、修正すれば両方の呼び出し箇所に同時に
影響する。**Issue本文の記述と実際の影響範囲は異なる。**

### 1-3. 両経路での期待される挙動変化

- **L672経路**: 対象extract内で、SPINOFF_MARKERSタグ付きの文だけがONGOING_RE
  に一致していた場合、`has_ongoing_elsewhere`がTrue→Falseに反転しうる。これにより、
  それまで取り消されていた別の文の`weak_completed`が有効に戻り、`_judge_extract()`
  自身が単独で決着（多くは「完結」）を返すようになる可能性がある。
- **L1255経路**: `_judge_extract()`がSTATUS_UNKNOWNを返し続ける行（L672経路の反転が
  `is_multimedia`等の別ゲートで決着に至らなかった行）についてのみ、インフォボックス
  フォールバックに到達する。そこで`_has_ongoing_signal(extract)`がFalseになれば、
  インフォボックスの「完結」判定がveto されずに採用されるようになる。

### 1-4. ハーネスでの切替方針

`docs/regression_corpus_2026-08/step98_judge_harness.py`の`run_judge_with_snapshot()`
は`_pick_article`・`_fetch_wikitext`のみを差し替える設計であり、これはそのまま使う。
これに加えて、検証スクリプト側で`wc._has_ongoing_signal`をプロセス内で1-1節の
修正後関数に差し替える（系統1が`wc.SPINOFF_MARKERS`をプロセス内で差し替えたのと
同じ方式）。`judge()`・`_judge_extract()`本体はいずれも`_has_ongoing_signal`を
モジュールのグローバル名として都度参照するため、`wc._has_ongoing_signal = <差替え版>`
とすれば`_judge_extract()`（L672）・`judge()`（L1255）の両方の呼び出しが同時に
切り替わる（`comic_checker/wikipedia_client.py`自体は変更しない）。

### 4-3. `test_strong_completion_is_not_vetoed_by_ongoing_elsewhere`（L655）— アサーションは変化しないが、テストの前提が空洞化する

extract内の唯一のONGOING_RE一致文「スピンオフ『例の終了作品外伝』は現在も連載中。」

- **アサーション自体**: 変化しないと予測する（`assert status == "完結"`は通り続ける）。
  このテストの本編決着文「本編は2020年に完結した。」はCOMPLETED_STRONG_RE一致であり、
  `has_ongoing_elsewhere`の値に関わらず取り消し対象外（strong signalはveto対象外の
  設計、L681「if weak_completed and...」の条件は`weak_completed`にしか掛からない）
  ため。
- **しかしテストの前提（docstring）が成立しなくなる**: このテストのdocstringは
  「走査範囲内に別の連載中シグナルがあっても無効化しない」ことを確認する意図だが、
  案B適用後は「スピンオフ」タグにより当該文が除外され、`has_ongoing_elsewhere`
  自体がFalseになるため、**veto判定が発火する機会がそもそも無くなる**。テストは
  合格し続けるが、「veto が発火してもstrong signalは無効化されない」ことを
  実際には検証しなくなる（除外により発火しないため）。
  **これはテストが検知不能な形で意図を失う例であり、CLAUDE.mdが定める
  「複数ガードが同じ値を返す場合、一つを除去しても出力が変わらない」問題の
  実例にあたる。過去のERRORS.md記載（「ゲート・検証機構が存在すること」と
  「実際に機能する条件で運用されていること」は別問題）とも同種の懸念として
  記録する。**
- **空洞化を検出するには何が必要か**: 現状のテストは「アサーションが通るか」
  しか見ておらず、`has_ongoing_elsewhere`が実際にveto判定へ到達したかどうか
  （＝strong signalの免除が実際に試された結果として通ったのか、単に免除を
  試す機会自体が無かったのかの区別）を確認する手段を持たない。検出には
  次のいずれかが必要と考えられる。
  1. **フィクスチャの設計変更**: extract内のongoing文をSPINOFF_MARKERSタグを
     含まない文に差し替える（例:「本編は2020年に完結した。『別冊誌』にて
     現在も連載中。」のように、無関係な語で決着させる）。これなら案B適用後も
     `has_ongoing_elsewhere`はTrueのまま維持され、strong signal免除のveto

## 8. ラベル汚染の扱い

`docs/holdout_measurement_2026-08/step98_a3_preregistration_addendum.md`
「併せて判明した、より重大な限界: ラベル付与者のコード知識による汚染」節が

**したがって、本検証で得られる「期待ラベルとの一致率」は、真の精度ではなく
その上界（楽観側の見積もり）として扱う。** 一致しなかった行（不一致行）は、
個別に精読すべき欠陥候補として、数値とは独立に診断的価値を持つ
（同アドンダム文書の整理を踏襲）。回帰群（regression61）の期待ラベルは

適用できるかは未確認（`m6d3_labels.py`のラベル付与経緯を本文書では調査していない）。
