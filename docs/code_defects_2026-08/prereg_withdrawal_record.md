## 2. 撤回の理由

**当初の想定（撤回に至った直接のきっかけ）**: N=50（seed=517）取得前の最終確認として、
影響件数（＝案Bおよび系統2〜5の対象機構に実際に到達し判定を左右する行数）に基づいて
必要母数を逆算したところ、点推定で全8語彙が残存プール262件（実行計画上限150件）でも
「最低10件」に到達しないことが判明した（`effective_hit_rate_analysis.md`）。

**実際の、より根本的な理由**: 必要母数が届かないこと自体は結果であり、根本原因は
「10件」という基準の立て方にある。

`corpus_expansion_design.md`自身が「10件」の由来として引用した実績——**系統1で
「続編」12件が出現し、そのうち実効的に影響したのは2件のみだった**——は、
`docs/code_defects_2026-08/verification_procedure.md`「系統1で確立した現コーパスの
判別力評価（実測値）」節にすでに明記されていた。

> 「続編」出現行のうち、実際に判定へ影響したのは既知の2件（バーテンダー à Tokyo・
> JESUS 砂塵航路）のみで、残りは`_is_novel_primary`ゲート・本編自身の完結文が先に
> 決着する等の理由で無害化されていた

つまり**基準の根拠となった数字（12件）は「出現件数」であり、実際に検証手順が
要求する量（「影響件数」）ではなかった**。この区別は`corpus_expansion_design.md`自身が
「10件」の由来を説明する文の中で明示的に述べており（上記引用の太字部分）、**知られて
いなかった事実ではなく、書かれていたのに基準の数値そのものには反映されなかった**。

具体的には、「12件の出現があれば個別追跡が可能な規模になる」という一文は、
**検証プロセスを実施するのに十分な生の追跡対象があるか（プロセスの実行可能性）**を
述べたものであり、**検証プロセスの結果として十分な判別力の証拠が得られるか（実質的な
充足性）**を述べたものではない。`corpus_expansion_design.md`「作業4」はこの2つを
区別せず、「12件」という出現件数を後者（判別力の証拠）の充足条件であるかのように扱い、
「案Bは着手可能」と結論した。実際の判別力（影響件数）は2件であり、
`verification_procedure.md`手順7が定める閾値（「現行コーパス160件中1〜2件程度と
判明した場合、その系統の安全性検証は完了したとみなさない」）に該当する。

## 4. 原因分析: なぜこの不整合はレビューを通過したか

**使った情報源**: `gh pr view 155 --json reviews,commits`・
`gh api repos/giant-shrimp/comic_checker/issues/155/comments`（PR #155の自動レビュー
コメント本文）・`git show --stat fd9b675629d9a87aed453ec31fccc2f38ca90ac8`（会話履歴・
エージェント作業ログ・記憶は使用していない）。

**PRの特定**: `gh pr list --state all --search "fd9b675629d9a87aed453ec31fccc2f38ca90ac8"`
により、コミット`fd9b675`を含むPRは**PR #155**（`docs: 系統2〜5・案Bの検証手順・
コーパス拡充設計・Issue草案を整備する`、MERGED）と特定できた。

**両ファイルの作成順序**: `git show --stat fd9b675`により、
`corpus_expansion_design.md`と`verification_procedure.md`は**同一コミット
（`fd9b675629d9a87aed453ec31fccc2f38ca90ac8`、2026-08-15 18:45:26 +0900）**で
同時に追加されたことを確認した。gitはコミット内のファイル間の執筆順序を記録しない
（コミットはアトミックな単位）ため、**「片方が先に書かれ、後から書かれた側が
先行文書の記述を見落とした」という順序は成立しない**。

**レビューの有無**: `gh pr view 155 --json reviews`は空配列（`{"reviews":[]}`）、
インラインレビューコメントも空配列。唯一の記録は`gh api .../issues/155/comments`で
取得した`github-actions[bot]`による自動レビューコメント1件
（`claude-review.yml`、2026-08-15T13:16:36Z〈`created_at`〉）。

**このレビューが何を見ていたか（実測）**: レビューコメント本文には次の記載がある。

> 判別力の実測値（PR本文中の件数、`verification_procedure.md`の表、
> `corpus_expansion_design.md`の表、`issue_draft_system{2,3,4,5}.md`の該当記述）は
> 相互に一致しており、母数160（holdout99+regression61）・262件プールの
> `462→362→262`の引き算・N=50の想定リクエスト数/所要時間の比例計算
> （前回実測160件・480リクエスト・873.8秒からの按分）もいずれも検算が合いました。

このレビューは**複数文書間で同じ数値（「12件」「160」等）が一致しているか**を
確認する検算だった。`corpus_expansion_design.md`の「12件」と`verification_procedure.md`
の「12件」は文字どおり一致しているため、この検算では不整合として検出されない。
**レビューが見ていなかったのは「その12件という数値が、参照先で果たしている役割
（出現件数の記録）と、引用元で使われている役割（判別力の充足証明）が同じかどうか」
という意味的な整合性であり、値の一致検算はこの種の誤りを構造的に検出できない。**

なお同じレビューは別件（「実測」と明記した日付がコミット日時より未来になっている
矛盾、`verification_procedure.md:132`等）を実際に指摘しており、レビュー自体は
機能していた。今回の不整合を見逃したのは「レビューの手抜き」ではなく、**その
レビューが採用していた検証方法（値の相互一致の検算）の射程の外にあった**という
方が正確である。

**結論**: 両文書は同一コミットで同時に追加されたため、「先に書かれた文書の主張を
後から書かれた文書が踏まえているか」を突き合わせる工程が構造として存在しなかった。
唯一存在したレビュー（自動レビュー）は数値の相互一致は確認したが、意味的な整合性
（出現件数と影響件数の区別）は確認の対象にしていなかった。**これは特定の個人・
セッションの見落としではなく、工程の欠落として記録する。**

## 5. seed=517のN=50抽出を実行しないという判断

**判断**: 実行しない。

**理由**: `effective_hit_rate_analysis.md`の実測（案B「続編」の影響率
2/160=0.0125、系統3〜4の各語彙も概ね1〜3/160の水準）をそのままN=50に適用すると、
50件から期待される影響件数は語彙あたり約0.6件程度（0.0125×50）にとどまり、
事前登録していた「10件」は元より、個別追跡やミューテーションテストが成立する規模には
遠く届かない。取得コスト（約150〜172リクエスト、約4.6〜5.1分、
`step99_retrieval_execution_plan_n50.md`参照）に見合う情報が得られないと判断した。

## 6. 残る安全網

この撤回によっても失われない防御層:

- **`verify.sh`・M6-B-4ゲート**: 案B・系統2〜5のいずれもコード修正に一切着手して
  おらず（`comic_checker/`は無変更）、これらのゲートは無傷のまま機能し続ける。
- **fail-closed原則**: 系統2〜5・案Bの対象コードはすべて未修正のままであるため、
  現状は判定不能側に倒れる既存の挙動が維持されている。今回の撤回によって新たに
  危険側（誤った「完結」「連載中」の断定）の挙動が増えることはない。
- **コード修正を行わない方針**: 今回のセッションを含め、系統2〜5・案Bはいずれも
  「検証手順の整備・見積もり」の段階にとどまっており、誤った基準に基づいて
  コードがマージされるという実害は発生していない。
- **Issue #53の原則（発見材料と評価材料の分離）**: まだ何も「着手」（コード修正・
  安全性検証の実施）していないため、この原則はまだ破られていない。撤回は
  「着手可能」という判断を差し戻すものであり、すでに行った検証をやり直す
  ものではない。

## 7. 失うもの

- **独立標本による判別力の裏付け**: N=50取得を中止したことで、案B・系統2〜4に
  ついて「発見に使っていない独立標本での確認」（Issue #53の原則が要求する
  「有効性の証拠」）を得る具体的な手段が、今回設計した方式（seed=517、N=50、
  上限150件）のままでは失われる。
- **明確な数値ゲート**: 「10件」という着手可否を機械的に判定できる基準が撤回された
  ことで、代替の基準が再登録されるまで、系統2〜5・案Bの着手可否判断は数値的な
  根拠を欠いた状態になる。
- **今後の開示義務**: 今後、系統2〜5・案Bのいずれかについて安全性検証の結果を
  報告する際は、「現コーパス（holdout99+regression61）由来の影響件数のみに基づく
  評価であり、独立標本による裏付けは無い」ことを限界として明記する必要がある
  （98-A-3のラベル汚染の扱いと同様、数値を無効化するのではなく、数値の性格
  ——上界なのか、独立性を欠くのか——を明示する形で開示する）。

## これは失敗ではない（目的と手続きの分離）

`step98_a3_withdrawal_record.md`の整理を踏襲する。「10件」という基準を事前登録した
こと自体、また`corpus_expansion_design.md`がその由来を「正直な記録」として書き残した
こと自体は、失敗ではない。むしろその記述（「実効的に影響したのは2件のみ」という
具体的な内訳を明記していたこと）が、今回`effective_hit_rate_analysis.md`で
影響件数を再計算する際の検証材料として機能した。**「10件」という基準そのものは
誤っていたが、その基準を導出した記録は誠実であり、誤りを事後に発見可能にした。**
手続き（出現件数を基準の充足条件として扱ったこと）は誤りだったが、目的
（系統2〜5・案Bの安全性検証を計画的に進めること）に向けた記録の透明性は機能した。
