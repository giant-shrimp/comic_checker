## AI Loop（`scripts/work_loop.sh`）の検証で分かったこと（Issue #14〜#16）

`/work`スキルを`claude -p`で非対話ループ実行するための`scripts/work_loop.sh`を試験導入し、
3段階の失敗を経て現在の設計（`scripts/work_loop.settings.json`によるdeny強制、`/work`の
リテラル呼び出し、no-op検出）に至った。将来また似た仕組みを作る／触るときのために経緯を残す。

1. **Issue #14（未追跡ファイルのgit管理化）で発覚: 許可の"加算"問題**。
   `--allowedTools`に`git add`/`git commit`を含めずに絞ったつもりだったが、実際には
   対話セッション用の`.claude/settings.local.json`（`permissions.allow`に
   `Bash(git add *)`/`Bash(git commit -m ' *)`を保持）がこの非対話実行にも素通しで効き、
   明示的な許可なくcommitが実行された（コミット内容自体は正しかったが、仕組みとして
   「絞ったつもりが絞れていない」状態だった）。Claude Codeの`permissions.allow`は
   発生源（CLIフラグ／プロジェクト設定／ローカル設定）を問わず**加算**される、という
   公式ドキュメント（`permissions.md`）の記載を確認して原因を特定した。
2. **対応: allowを絞るのではなくdenyで塞ぐ**。`permissions.md`には「denyは発生源を問わず
   常にallowより優先される」と明記されている。この性質を使い、`work_loop.sh`専用の
   `scripts/work_loop.settings.json`（`git commit`/`git push`/`git add`を常にdeny）を
   `--settings`で追加読み込みさせる方式に変更した。**プロンプト文面で「commitして」と
   明示してもdenyは緩まないことを実測で確認済み**（denyは権限システム側の強制であり、
   モデルへの指示ではないため）。**当時は**、commitを許可したい場合は`work_loop.sh`の
   呼び出し元が環境変数`ALLOW_COMMIT=1`を明示的に設定する必要がある（プロンプト文言
   ではなく、スクリプト起動時の帯域外の手段で許可する設計）**と考えていたが、この
   迂回路はオール・オア・ナッシング（`work_loop.settings.json`の読み込みを丸ごと止める）
   という設計上の問題があったため、導入から66分後に撤去された**（コミット3341902で
   導入、6d7ef64で撤去。根拠は`scripts/loop_git.sh`の該当コメント。
   `grep -n "ALLOW_COMMIT" scripts/loop_git.sh`で再取得できる）。現在の`work_loop.sh`に
   環境変数等による迂回路は無い。この過程で、`disable-model-invocation:
   true`のスキルは`-p`のプロンプト文字列にリテラルな`/skill-name`呼び出しが無い限り
   自動発火せず、SKILL.mdの内容が一度もコンテキストに読み込まれないことも判明したため、
   `work_loop.sh`のPROMPTを`/work ${ISSUE}`のリテラル呼び出しに修正した。
3. **Issue #16（判定不能率の計測）で発覚: `verify.sh`通過は成功の証拠にならない**。
   `scripts/measure_unknown_rate.py`の新規作成・実行を`work_loop.sh`に任せたところ、
   `ALLOWED`に任意の`python3`実行手段が無いため（`Bash(./scripts/verify.sh)`以外の
   コマンド実行が許可パターンに一致せず拒否され続け）、ターン数上限（`num_turns`が
   `MAX_TURNS`に到達）で何も実装できないまま終了した。ところが**何も変更していないのに
   既存テストは当然通るため、`work_loop.sh`は「verified — 停止します」と成功扱いで
   終了していた**。`is_error: true`・`stop_reason: "tool_use"`という`logs/run_N.json`の
   中身を見て初めて気づける状態で、放置していれば「何も進んでいないのに成功ログが残る」
   という誤検知になっていた。対応として、`verify.sh`通過後に`git status --porcelain`で
   実際に変更が発生したかを確認し、無変化なら`no-op`として明確に区別する
   （終了コード2、`logs/outcome_N.txt`に記録）よう`work_loop.sh`を修正した。
   合わせて、ネットワークI/Oや新規スクリプトの単体実行を要するタスクは`work_loop.sh`の
   対象外とし対話セッションで行う、という適用範囲を`.claude/skills/work/SKILL.md`に
   明文化した。
4. **教訓（一般化）**: 非対話ループの安全性は「プロンプトで何を指示したか」ではなく
   「権限システムが実際に何を許可・拒否するか」で決まる。同様に、ループの成否は
   「検証コマンドが通ったか」ではなく「意図した変更が実際に生じたか」で判定する必要が
   ある。どちらも、モデルへの指示（プロンプト・SKILL.md記載）だけでは強制力を持たず、
   実行環境側（`permissions.deny`・`git status`によるdiff確認）で裏付けを取って初めて
   信頼できる、という同じ構造の教訓である。

**併せて（2026-08-04 実測）: 複合コマンドでも deny が勝つ。** `Bash(./scripts/verify.sh)`
を allow した状態で `./scripts/verify.sh ; gh pr merge 99999 --merge` と
`./scripts/verify.sh && gh api repos/giant-shrimp/comic_checker --jq .full_name` を試すと、
**どちらもコマンド全体が実行前に拒否された**（`permission_denials` に記録。`verify.sh`
自身も走らない）。判定は「先頭が allow に一致するか」の前方一致ではなく、連結された各
コマンドを見ている。**したがって「allow したコマンドの後ろに禁止コマンドを繋ぐ」形の
迂回はできない。** ただしこれに安全を預けるより、そもそも入口を作らない方が確実である
（`scripts/loop_git.sh` を非対話ループの `--allowedTools` に入れていないのはその判断。
詳細は `docs/work_loop_testing.md` 5-f）。

## 落とし穴：定数を期待値と入力の両方に使うテストは、定数を変えても落ちない（Issue #40で踏んだ）

    sleeps, ... = _throttled_get([too_many] * API_MAX_ATTEMPTS)   # 入力
    ...
    assert sleeps.count(API_REQUEST_INTERVAL) == API_MAX_ATTEMPTS  # 期待値

**両辺が同じ定数なので、値を変えると期待値も一緒に動く。** `API_MAX_ATTEMPTS` を 6→3 に
変えても1件も落ちなかった。

Issue #40 で本番の定数8個を実際に変異させて `pytest tests/` を回したところ、**5個が1件も
落ちなかった**（`STATUS_UNKNOWN` / `STATUS_NOT_FOUND` / `MARKER_MAX_DISTANCE` /
`API_MAX_ATTEMPTS` / `API_REQUEST_INTERVAL`）。うち2個は #40 で修正し、3個は #62 に起票した。

**対策**：値を固定したいテストは**期待値をリテラルで書き**、定数値そのものを別途アサート
する。

    assert API_MAX_ATTEMPTS == 6, "上限を変えるなら、このテストの期待値も意図して更新すること"

**教訓**：新しい定数を導入したら、**その場で変異させて落ちることを確認する**。
`CLAUDE.md` の「`verify.sh` にゲートを足したら壊して確認する」と同じ話で、対象が定数に
広がっただけである。

## コマンド置換で呼んだシェル関数内の変数代入は、呼び出し元に伝わらない（Issue #75）

`scripts/work_loop.sh` の `checkpoint()` が `msg_file="$(compose_commit_message "$iter")"`
という形で `compose_commit_message()` を呼んでいた。この関数の中で
`COMMIT_MSG_WAS_FALLBACK=1` のようにグローバル変数へ代入し、呼び出し元で
その値を読むコードを書いたが、**実行するたびにこの変数が空のまま**だった。

原因は `$(...)` によるコマンド置換がbashにおいて**サブシェルを生成する**こと。
サブシェル内での変数代入は、そのサブシェルが終了すると失われ、親シェルには
一切伝播しない。`local` の付け忘れではなく、関数の**呼び出され方**そのものが
原因である。

**設計レビューでは気づけなかった。** コードは「関数内で変数に代入し、呼び出し元で
読む」という一見自然な流れに見え、静的に読むだけでは「この呼び出しがコマンド置換
経由でサブシェルを作るかどうか」を見落としやすい。`bash -n` の構文チェックでも
検出できない（構文としては正しいため）。実際に実行し、出力ファイル
（`logs/pr_note_N.txt`）の中身を確認して初めて欠落に気づいた。

対応: 変数ではなく、ファイル（`logs/commit_msg_fallback_N.txt` に `"0"`/`"1"`）
経由で受け渡す方式に変更した。ファイルはサブシェルをまたいでも確実に共有される。

**教訓（一般化）**: シェルスクリプトで「関数内グローバル変数代入→呼び出し元で参照」
というパターンを使う場合、その関数が `$(...)` や `` `...` ``（コマンド置換）、
`|`（パイプ）経由で呼ばれていないかを必ず確認する。経由していれば、変数ではなく
ファイルか標準出力の戻り値そのもので受け渡す設計に変える。

## コード変更の影響予測を評価コーパスだけを対象に行うと、テストスイート内の実データフィクスチャが対象外になる（Issue #144・#154、案B）

**観察**:

- 案B（`_has_ongoing_signal()`へのSPINOFF_MARKERS除外、Issue #154）の事前登録
  （`docs/code_defects_2026-08/prereg_planb_safety_verification.md`3-2節）は
  「この2件（陰陽師・バーテンダー à Tokyo）以外に変化しうる記事は無い」と予測
  していた。この予測は「holdout99+regression61の160行のみを対象とする」と
  範囲を明記しており、その範囲内では正しかった。
- しかし実際に`comic_checker/wikipedia_client.py`へdiff-1を適用した直後の
  `verify.sh`で、事前登録に記載の無い3件目の失敗
  （`test_judge_extract_skips_next_generation_spinoff_setogiwa_hanayome`、
  実データ「セトギワ花ヨメ」、Issue #144）が発生した。この記事は160行の
  保存済みスナップショット・コーパスには含まれておらず、`tests/test_wikipedia_
  client.py`内に過去のIssue調査で個別に保存された実データフィクスチャだった。
- `_has_ongoing_signal()`はモジュール内の全呼び出し元（`_judge_extract()`・
  `judge()`）に影響する関数であり、その実データでの挙動を左右しうる入力は
  160行のスナップショット・コーパスだけではなかった。詳細は
  `docs/code_defects_2026-08/planb_prediction_scope_defect.md`参照。

**推論（断定しない）**:

- 「予測の対象範囲を明記すること」と「予測の対象範囲が、変更の影響が及びうる
  範囲を包含していることを確認すること」は別の作業である。前者を行った
  （範囲を正直に書いた）だけで、後者を行った気になってしまうリスクがある。
- 評価コーパス（holdout・regression等、意図的に収集・凍結した標本）と、
  テストスイート内の実データフィクスチャ（過去のIssue調査の副産物として
  個別に埋め込まれた実データ）は、どちらも「実データ」という点で同じ性質を
  持つが、前者は一元管理された台帳（`holdout_pool_consumption_ledger.json`等）
  で把握できる一方、後者はコードベース全体に散在しており、意識的に洗い出さない
  限り見落とされる。

**教訓**:

- **コード変更の影響予測の対象は、「評価コーパス」ではなく「その関数を通る
  全ての入力元」で定義する。** 評価コーパスは影響予測の対象範囲の一部
  （多くの場合は主要な部分）でしかなく、それで全てだと暗黙に扱わない。
- **`comic_checker/`の判定ロジックに関わる変更を予測する際は、保存済み
  コーパスに加えて`tests/`内の実データフィクスチャ（コメントで「実データ」と
  明記されているもの）も対象に含める。** 変更前に、対象となる関数の全ての
  呼び出し元・全ての実データフィクスチャを機械的に洗い出してから予測を確定する。
- **予測範囲の限定を明記すること自体は誠実な行為であり、悪いことではない。**
  問題は限定そのものではなく、その限定が「変更の影響範囲」を包含しているかを
  別途確認しなかったことにある。範囲を明記した上で、その範囲が十分かを
  チェックする工程を追加する。
- 今回、この見落としは`verify.sh`（全テストスイートの実行）が機械的に検出した。
  **事前登録の予測範囲がどれだけ限定されていても、実装後のテストスイート全体の
  実行は必ず行う**——この手順自体は既に運用されており、実際に機能した。

`docs/code_defects_2026-08/planb_prediction_scope_defect.md`

## 明文化されていない運用ルールは、権限設定ファイルの確認だけでは発見できない（Issue #154、案B実装）

**観察**:

- 案B（`_has_ongoing_signal()`の実装、Issue #154）の適用に先立ち、AIが
  `comic_checker/**`・`tests/**`を直接編集できるかを`.claude/settings.local.json`・
  `scripts/work_loop.settings.json`・`CLAUDE.md`で確認した。
- **いずれにも、これらのパスに対する`Edit`/`Write`の`deny`エントリは無く、
  編集者（AIか人間か）を規定する記述も見つからなかった。** 技術的な権限設定
  だけを見れば、AIがいつでも自由にこれらのパスを編集できるように見える。
- しかし実際の運用では、`comic_checker/`の判定ロジック（`wikipedia_client.py`
  等）へのAIによる変更は、ユーザの明示的な承認（「今回限りの明示承認である」
  という形の申し送り）を経てから行われている。この運用は本セッション内の
  複数の作業回にわたって一貫しており、単発の思いつきではない。

**推論（断定しない）**:

- `.claude/settings.local.json`等の権限設定ファイルは、Claude Codeというツール
  自体が技術的に強制できる範囲（コマンド実行・ファイル書き込みの許可/拒否）を
  規定するものであり、**プロジェクトの運用ルール（人間の承認を要する対象範囲）
  の正本ではない**。両者は独立に存在しうる——技術的に許可されていることと、
  運用上望ましいとされていることは別の軸である。
- 今回のケースでは、運用ルール自体はCLAUDE.mdにも明文化されておらず、
  会話の中で申し送られる形でのみ存在していた。これは、他の同種のルール
  （例: `.github/workflows/**`はADR-003により明文化されている）と対照的である。

**教訓**:

- **「権限設定ファイルにdenyが無い」ことを「AIが自由に編集してよい」ことの
  根拠にしない。** 権限設定は技術的な下限（ツールが強制できる範囲）を示す
  だけであり、それを上回る運用上の制約（人間の承認を要する等）が明文化
  されずに存在しうる。
- **明文化されていない運用ルールが存在する場合、権限確認だけでは判断できない
  ことを前提に行動する。** 判断できない場合は、会話内の既存の申し送り・
  過去の運用実績（同種の変更が過去にどう扱われてきたか）を参照するか、
  それでも不明な場合はユーザに確認する。
- 逆に、重要な運用ルールは可能な限り明文化する（`.github/workflows/**`の
  ADR-003のように）ことが、この種の曖昧さを減らす根本的な対策になる。
  `comic_checker/`・`tests/**`について同様の明文化を行うかどうかは、
  この記録の範囲外の判断として残す。

Refs: Issue #154

## `--max-budget-usd` は支出の上限ではなく、ターン境界での打ち切りであり、上限を大きく超えて課金されうる

**実測値**: `claude -p --max-budget-usd 0.01`（他は最小構成、`--model sonnet`）を
実行したところ、`total_cost_usd`は**0.0831**（上限の約8.3倍）、`num_turns`は**1**、
`terminal_reason`は`budget_exhausted`、`subtype`は`error_max_budget_usd`、`errors`に
上限到達を示すメッセージ、終了コードは1だった。

**含意**: このフラグは「予算を超えたら**次のターンへ進まない**」という形で機能して
おり、「**1ターン内の支出**を上限で止める」形では機能していない。したがって、
1ターンあたりの支出が大きい場合（長い出力・大きな文脈でのcache creation等）、上限は
実効的な歯止めにならない。上限に**到達したかどうかの判定自体はターンの完了後に
行われる**ため、そのターンの支出そのものを遮ることはできない。

**限界（過度な一般化をしないこと）**: この実測時の認証は環境変数
（`ANTHROPIC_API_KEY`・`CLAUDE_CODE_OAUTH_TOKEN`）ではなく、native login
（ブラウザ認証）によるものだった。ADR-005が述べる、`CLAUDE_CODE_OAUTH_TOKEN`を
GitHub Actionsへ渡す経路と同一の認証経路かどうかは未確認である。**本記録は
ADR-005を反証するものではない。**別の認証文脈での観測として記録する。

**実務上の影響**: `scripts/work_loop.sh`は`--max-budget-usd 2.00`を渡している
（`ALLOWED`の直後、`claude`呼び出しの引数）。この実測が同じ挙動を持つとすれば、
支出上限としては期待どおりに働かない可能性がある。**本記録の時点では
`work_loop.sh`は変更しない。**

**分類の判断**: 本記録は`docs/errors_md_inventory.md`の分類基準でいう
**B（再発しうる・パターンとして有効）**に該当すると判断する。根拠:
`--max-budget-usd`というフラグ名から「支出の上限を保証する」という直感的な
期待が生まれやすく、その期待を裏切る形（ターン境界での打ち切り）で動作する
という性質自体は、今回1件の実測で解消されるものではない。今後このフラグに
支出上限としての役割を持たせようとするたびに（`work_loop.sh`の見直し時、
ADR-011の「review_loop」設計時等）、同じ誤解を避けるための確認が必要になる
ため。

## `review_loop.sh`: 次ラウンドのinstructionに監査役のFOLLOWUPSが混入する（ADR-011段階1の判断材料収集で発覚、未検証の経路）

**ADR-012（`docs/decisions/ADR-012-stage1-decision.md`）決定3により修正済み。**
`build_next_instruction()`関数を新設し、`c`選択時に`review.md`全体では
なく、FOLLOWUPS節を機械的に除去した内容（VERDICT行＋CONTRADICTIONS節）
を次のinstructionにするよう変更した。変異テスト2種（FOLLOWUPS除去を
無効化する変異、除去範囲を広げすぎてCONTRADICTIONSまで消す変異）で、
対応するテストが実際に落ちることを確認済み。以下は発見時の記録として
節ごと残す。

**発見の経緯**: ADR-011段階0の初回試走（`docs/ai_loop_state/
review_loop_trial_2026-08-26.md`）は1ラウンドで人間が`q`を選び終了した
ため、`c`を選んで次ラウンドへ進む経路は一度も通っていなかった。段階1
（指示文の生成をループに取り込む案）の判断材料を集める過程で
`scripts/review_loop.sh`の`c`選択時の処理を実測して初めて見つかった。
**verify.sh・テストのいずれもこの欠陥を検出しない**（該当コードパスに
到達する自動テストが存在しないため）。

**欠陥の内容**: `c`選択時、`CURRENT_INSTRUCTION_FILE`には
`"${ROUND_DIR}/review.md"`が代入される（`grep -n
'CURRENT_INSTRUCTION_FILE="\${ROUND_DIR}/review.md"' scripts/review_loop.sh`
で再取得できる）。`review.md`は監査役の出力全文であり、VERDICT行・
CONTRADICTIONS節に加えて**FOLLOWUPS節もそのまま含まれる**。つまり次
ラウンドの実行役は、監査役が出した品質改善の提案（FOLLOWUPS）を、
そのまま作業指示として受け取ることになる。

**ADR-011との関係**: ADR-011決定6は「監査役の出力形式はVERDICT /
CONTRADICTIONS / FOLLOWUPSの3節とし、**FOLLOWUPSの内容をVERDICTに
影響させない**」と定めている。これは監査役自身の判定（合否）における
分離を意図したものだが、`review_loop.sh`の実装では**FOLLOWUPSが
次ラウンドの実行役の作業指示に流れ込む**という、決定6が想定していな
かった別経路でFOLLOWUPSが影響力を持ってしまっている。決定6の文言
そのものには違反していない（VERDICTの値自体はFOLLOWUPSの影響を受けて
いない）が、決定6が達成しようとした「品質提案と合否判定の分離」という
趣旨は、次ラウンドの段階で骨抜きになる。

**現時点での実害**: 未確認。初回試走はこの経路を通っていない。

**分類の判断**: 本記録は`docs/errors_md_inventory.md`の分類基準でいう
**B（再発しうる・パターンとして有効）**に該当すると判断する。根拠:
個別の欠陥（`review.md`全体を渡す実装）自体は今後の修正で解消できるが、
「1ラウンドしか試走していない機能には、まだ通っていないコードパスに
未検出の欠陥が残っている」という一般化可能なパターンがここでも再現した
ため（`work_loop.sh`の検証履歴で記録された複数の同型の教訓と同じ構造）。
今後`review_loop.sh`に手を入れる、あるいは同種の複数ラウンド機構を作る
たびに、「実際に複数ラウンド回してからでないと分からない欠陥がある」
という前提で検証範囲を検討する必要がある。
