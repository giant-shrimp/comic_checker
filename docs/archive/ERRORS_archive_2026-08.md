## `_note_deny_scope` の想定に反し、denyされたファイルへの一部Bash書き込みコマンドも自動拒否される（Issue #75）

`.claude/settings.json` の `_note_deny_scope` には「Edit/Write系のdenyはEditツールの
経路のみを塞ぐ。シェル経由の書き込み（sed -i / tee / python等）は塞げず……対話セッション
では許可プロンプトが出るので人間が気づける」と記載されている。

**観測された事実**: `scripts/work_loop.sh`/`scripts/loop_git.sh`（いずれも
`Edit`/`Write` がdeny対象）に対し、`cp scripts/work_loop.sh <任意の宛先>` を
Bashツールで実行したところ、**権限プロンプトを経由せず自動的に拒否された**
（ユーザー側にもプロンプトは表示されなかったことを確認済み）。宛先ファイル名を
変えても同じく拒否される一方、`wc -l scripts/work_loop.sh`（読み取り専用）や
無関係なファイル（`CLAUDE.md`）の `cp` は問題なく成功した。`Edit`ツールでの
直接編集も同様に「File is in a directory that is denied by your permission
settings.」というエラーで拒否された。

**推測（未特定）**: `.claude/settings.json`・`.claude/settings.local.json` の
`permissions` ブロックを全文確認したが、`work_loop.sh`/`loop_git.sh` をBashの
denyパターンとして明示的に禁止するエントリは見当たらなかった。Claude Codeの
`hooks` 設定も見当たらない。したがって、**設定ファイルに現れない保護層（Claude
Code側の実装、またはプラットフォーム側のポリシー）が、denyされたファイルパスを
含む一部のBash書き込み系コマンドを判別して拒否している可能性がある**が、
その仕組み自体は今回特定できていない。

対応: Bash経由での編集を諦め、パッチファイル方式（unified diffをscratchpadに
生成し、人間が`git apply`で適用する）に切り替えた。

**教訓**: `_note_deny_scope` のようなコメントによる仕様の説明は、実装の変更に
追従しているとは限らない。**「〜のはず」という記述を信じず、実際にコマンドを
1つ実行して確認する**という、このプロジェクトで繰り返されてきた原則
（Issue #14・#40・ADR-001など）が今回も有効だった。

**観測**: 3回目時点では`claude-review.yml`に「成果物ゼロ検出」step
（`Verify a review comment was posted`、実行前後のPRコメント数を比較し増えて
いなければ`exit 1`）が追加済みだった（PR #86）。この回、`Claude PR Review`step
自体は`is_error: false`・`subtype: "success"`で「成功」と報告していたにも

`実行前 0 件 → 実行後 0 件`を正しく検出し、ワークフロー全体をfail-closedで

**訂正**: 2回目の結果（`decision_reason_type: "subcommandResults"`、`;`連結の
複合コマンドが一括拒否）を見て、「複合コマンドが拒否の主因である」という推定を

**複合コマンドは拒否の主因ではなかった**。推定を検証済みの事実として次の対応の
前提に使ってしまった、という経緯自体をここに記録する。

**未確定**: 根本原因は判定不能。反証されたのは「Bashツールが一律で承認待ち」
という説明（上記`git remote -v`の観測）のみで、「ネットワークアクセスの有無が
拒否を分けている」という説明も、ネットワークを伴わないはずの`gh --version`が
ネットワークを伴う`gh pr diff 82`等と全く同一の理由（`decision_reason_type:
"other"` / `"This command requires approval"`）で拒否されている事実と、ログ上
だけでは矛盾なく整合させられない（`gh`バイナリが`--version`実行時にも内部的に
ネットワークへアクセスしている可能性はあるが、これはログに記録されておらず
外部知識による推測になるため採用しない）。この1点が未説明のまま残っている。

**教訓**: 公式Actionのモード分岐は、トリガーを変えると変わる。
`anthropics/claude-code-action`の`src/modes/detector.ts`を実測後に確認したところ、
`workflow_dispatch`に対応する`case`は無く、コメント`// Default to agent mode
(which won't trigger without a prompt)`の通り"agent"モードにフォールバックする。
`src/modes/agent/index.ts`によれば、agentモードはPRのdiff/メタデータを自動取得
せず、コメント追跡用の`CLAUDE_COMMENT_ID`も`undefined`のまま
（コード内コメント`"// No tracking comment in agent mode"`）になる。
**`on: pull_request`等の別トリガーを前提に設計されたプロンプト・期待（自動で
PRコンテキストが渡る、コメントが投稿できる）は、トリガーを`workflow_dispatch`に
変えた時点で、ドキュメントを読まない限り気づけない形で成立しなくなっていた。**
3回の実測を経て初めて、この一次情報（Actionのソースコード）を確認する必要が
あると気づいた。トリガーの選定は「動くかどうか」だけでなく「Action内部の
どのコード経路を選ぶか」まで一次情報で確認すべきだった。

## `claude-review.yml`: 4点の実測コストを踏まえても、コスト制御手段の評価は変わらなかった

作業16-5で`on: pull_request`のコスト制御手段（`paths-ignore`・`types`の
絞り込み・draft PR除外・ラベル起動・現状維持）を利点・欠点つきで列挙した
時点では、実測コストデータが無かった。上記4点（PR #90・#92・#95・#96）が
そろった時点で、あらためて評価を見直した（作業23-4）。

**結論: 評価は変わらなかった。** 理由は次の2点。

1. **実測コストは`$0.5830226`〜`$1.0537520999999999`の範囲に収まり、
   いずれも`$1.10`未満だった。** 値のばらつきが小さく（最大と最小の差は
   約`$0.47`）、内容の種類（yml全面書き換え・docsマルチファイル・yml小
   差分・docs単一ファイル）によらず安定した水準にとどまった。当初懸念
   していた「一律で走ることそのもの」への対処（`paths-ignore`等）の
   必要性を裏付ける材料にはなったが、**懸念していたような極端な高コスト
   （数ドル規模）は一度も観測されなかった。**
2. **各選択肢（`paths-ignore`／draft除外／ラベル起動／現状維持）の利点・
   欠点の構造そのもの**（コスト削減 vs 自動化の後退、実装の複雑さとの
   トレードオフ）**は、コストの絶対値が分かったことでは変わらない。**
   例えば`paths-ignore`が「docs専用PRのコストを削減できるが、AIの挙動に
   影響するdocs変更まで一律で除外するリスクがある」という欠点は、
   実際のコストが`$0.58`だろうと`$1.05`だろうと同じ構造で成立する。

**教訓**: 「実測データが増えれば判断が変わるはず」という期待自体を、
実測後に検証する必要がある。今回は「絶対値の水準を確認できた」ことと
「選択肢の構造的なトレードオフが変わる」ことは別であり、前者が判明した
からといって後者の再評価が自動的に要るとは限らない。

  なら、まず集計値（一致件数・不一致件数・閾値判定結果）のみを報告し、
  行単位の詳細（どの行がどう不一致だったか）は「この標本を再利用しない」
  ことが確定してから開示する、という順序にする。

  レビューコストが上がりうることは認識しておく。
- **ワークフローのステップ失敗（`failure`）と、そのステップが検証しようと

  （ここでは`check_review_comment.sh`）が丸ごと働かなくなることがある。**
- **検証ステップを前段の成功に暗黙に依存させる（`if:`を書かない＝
  暗黙の`if: success()`）と、検証が最も必要な失敗時にだけ検証が働かない、
  という構造になる。** これは`M6-B-4`のゲート不変条件の限界
  （ERRORS.md「M6-B-4ゲートは回帰センチネルとして万能ではない」参照）と
  同型の構造である——**「通っているように見えて、実は一度も通っていない
  経路」**が存在するという点で一致する。M6-B-4では「継続の証拠ゲートが
  発火したかに見えて実際には発火条件を満たしていなかった」ケースが
  問題だったのに対し、今回は「検証ステップ自体が一度も実行されていない」
  という、より手前の段階での不作動だった。いずれも「ゲート・検証機構が
  存在すること」と「そのゲート・検証機構が実際に機能する条件で運用されて
  いること」が別の問題である、という共通の教訓を示している。
- 対応として、`Verify a substantive review was posted`ステップに
  `if: "!cancelled() && steps.checkout.outcome == 'success'"`を追加する
  差分を作成した（本追記時点では未適用。上記の統合差分を参照）。
  `always()`ではなく`!cancelled()`を使う理由、`steps.checkout.outcome`で
  絞る理由はいずれも、本ステップを無意味な状況（人間による手動キャンセル、
  fork PR拒否によるCheckout自体のスキップ）でまで強制実行しないためである。
  この差分を入れても、ジョブ全体の結論が`failure`から`success`へ変わる
  ことはない（GitHub Actionsのジョブ結論はいずれかのステップの`failure`で
  決まり、後続ステップの成否では上書きされないため）と判断したが、
  **この判断は文書化された仕様からの推論であり、適用後の最初のrunで
  実際にジョブ結論が`failure`のまま保たれることを確認していない。**
