# ADR-007: リリース自動化の範囲（タグ付け・GitHub Releases公開）

- 日付：2026-08-11
- 状態：採用
- 関連：[ADR-001](ADR-001-main-protection.md)、[ADR-002](ADR-002-windows-build-on-ci.md)、
  [ADR-003](ADR-003-workflows-deny-ai-write.md)、
  [ADR-004](ADR-004-phase5-preconditions.md)

## 背景

作業72〜74で、配布物にバージョン識別情報（`comic_checker.__version__`・
`version_string()`）を導入し、`build-windows.yml`のビルド時に
コミットハッシュ・UTC日時を`comic_checker/_build_info.py`へ埋め込む仕組みを
実機で確認した（Windows実機ビルド run 31471282705、EXE起動でウィンドウ
タイトル・フッタに`0.1.0 (e8f85df, 2026-08-11T08:00:29Z)`と表示されることを
目視確認、`e8f85df`は当該コミットの`git rev-parse --short HEAD`と完全一致）。

これにより「バージョンを識別できない」という問題は解消したが、71-4(c)で
指摘したもう一方の製品ギャップ「配布・リリース管理が存在しない」は残っている。
`gh release list`は0件、gitタグは`v0.1.0-m4-test`（試験目的、後述）が1件
のみである。

ADR-002は「リリース時...GitHub Releasesへ添付する選択肢もあるが、現時点では
不要と判断した。必要になった時点で本ADRを見直す」（受け入れたリスク1）
と明記しており、同じくADR-002は「このワークフローにpushを伴う仕事を
させない。リリースノート生成・タグ付け・バージョン更新のコミット等を
ここに足したくなった場合は、ADR-001『受け入れたリスク』3に戻って再検討
すること」（この決定が縛るもの）とも明記している。本ADRはこの2点の再検討
にあたる。

## 決定1: タグ付けは人間のみが行う

**AIはgitタグを作成・削除しない。**

**理由**: 「このコミットを正式リリースとして配布してよいか」は製品判断
であり、`verify.sh`が通るか・テストが緑かというコード品質の判断とは性質が
異なる。ADR-001が確立した「`main`への統合は人間が最終判断する」という
原則（PRのマージは常にGitHub GUIで人間が行う）を、リリースというさらに
下流の意思決定にも一貫して適用する。

## 決定2: GitHub Releasesへの公開は自動化しない

**CIはビルドとartifact生成までとし、GitHub Releaseの作成・EXEアセットの
添付は人間が`gh release create`で手動実行する（半自動運用）。**

具体的な手順は`docs/release_runbook.md`に記録した。

## 決定3: `build-windows.yml`の`permissions`は`contents: read`のまま維持する

**`contents: write`への昇格は行わない。**

GitHub Releasesの作成・アセットのアップロードには`contents: write`権限が
要る。これを`build-windows.yml`に与えることは、ADR-002が明記した
「このワークフローにpushを伴う仕事をさせない」という設計と正面から衝突する。
決定2（人間が手動でRelease作成）を選んだことで、この権限昇格自体が不要になる。

## 却下した案

### 1. タグpush → 即Release公開の完全自動化

`on: push: tags: ["v*"]`をトリガーに、ビルド後そのままGitHub Releaseを
作成しEXEを添付する案。

**却下理由**:

- ADR-001「受け入れたリスク」3（「CI（GitHub Actions）や他マシンからの
  pushには効かない。クライアントサイドフックである以上、原理的に
  カバーできない」）が指摘する通り、CIからのpush（Release作成もAPI経由の
  書き込みという意味で同種）は`.githooks/pre-push`では止められない
- `build-windows.yml`冒頭コメント（7-9行目）が明記する「このワークフローは
  ビルドとartifact生成のみを行い、一切pushしない...CIにpush権限を伴う
  仕事をさせない方針である」という既存の設計方針と正面から衝突する
- タグをpushした瞬間に、人間の最終確認なしで一般公開される。ビルド自体は
  `Verify build output`ステップでゲートされている（(a)(b)(c)の3項目）が、
  「動くEXEであること」と「今公開してよいタイミングか」は別の判断軸であり、
  後者を機械的に自動化する理由が無い

### 2. `contents: write`を与えるが、Release作成は`workflow_dispatch`の
　　手動トリガーに限定する

タグpushでの自動公開は避けつつ、「ボタンを押せばRelease化される」という
半自動よりさらに一段階自動化した案。

**却下理由**: 権限を`contents: write`へ昇格させること自体が決定3と矛盾する。
`gh release create`は人間のローカル環境・GitHub CLIの認証（人間自身の
GitHubアカウント権限）で実行すれば、リポジトリのワークフロー権限を一切
変更せずに同じ結果（Release作成・アセット添付）が得られる。ワークフロー側の
権限昇格という恒久的なリスクを、実行のたびに数分のコマンド入力と引き換えに
避けられるなら、後者を選ぶのが決定3の理由と整合する。

## 受け入れたリスク

半自動運用（決定2）のため、以下を承知の上で受け入れる。

1. **リリース作業に人間の手間がかかる。** `docs/release_runbook.md`の
   手順（artifactダウンロード → `gh release create`）を毎回手で実行する
   必要がある。
2. **実行を忘れる、または手順を誤る可能性が残る。** 例えば`__version__`の
   更新を忘れたままタグを打つ、逆にタグだけ打って`__version__`を上げ忘れる、
   といった事故。74-4(b)で提案した「タグと`__version__`の不一致検出」を
   `build-windows.yml`へ追加するパッチ案（`~/comic_checker-agent-notes/
   0003-*.patch`、作業75-4で生成、未適用）で軽減できるが、根絶はしない。
3. **それでも権限最小化を優先する。** 上記2点のコストは、`contents: write`
   をCIに常設することで生じる「ワークフローの実装ミス・第三者による
   ワークフロー改変（GitHub Web UIからは誰でも編集できる、ADR-003
   「受け入れたリスク」4）が即座にリポジトリへの書き込みに直結する」
   というリスクより小さいと判断した。

## この決定を見直す条件

以下のいずれかが起きた場合、本ADRの決定2・3を再検討する。

- **リリース頻度が明確に増え、手動手順のコストが無視できなくなったとき。**
  月1回未満の想定であれば半自動で十分だが、週次以上になった場合は
  自動化の再検討に値する。
- **GitHub Proへの移行、またはリポジトリのpublic化により、ブランチ保護
  （ADR-004決定2が言及するrulesets）が使えるようになったとき。** この場合
  `main`保護の前提が変わり、`contents: write`昇格のリスク評価も変わる
  可能性がある。
- **Phase 5 Step 2（Actionsからブランチを切りPRを作る、`contents: write`が
  必要になる）へ実際に進む判断をしたとき。** ADR-004が既にこの時点での
  再検討を予告しており、本ADRの決定3もその再検討に合流させるべきである。

## 初回リリース番号について（決定は保留）

既存タグ`v0.1.0-m4-test`は**残す**（削除しない）。「ビルド検証マイルストーン」
という当時の目的の記録として保持する。

**判断材料（実測、2026-08-11）**: `v0.1.0-m4-test`は`build-windows.yml`の
ビルドを一度も実際にトリガーしていない。`gh run list --workflow=build-
windows.yml`で確認できる全4件のrunのうち、`event: "push"`のものは1件
（`headBranch: "v0.0.0-ci-test"`、2026-07-24T16:29:33Z）のみで、これは
`v0.1.0-m4-test`とは別の、既に削除された試験タグである（`git tag -l`に
`v0.0.0-ci-test`は存在しない）。`v0.1.0-m4-test`のコミット日時
（2026-07-23T18:29:50+09:00）は`build-windows.yml`の追加日（ADR-002、
2026-07-25）より前であり、ワークフロー導入前に打たれたタグである以上、
これを起点とした自動ビルドが発生していないのは整合する。**つまり
`v0.1.0-m4-test`は実際のリリース成果物を1つも生んでいない、純粋な記録
専用のタグである。**

この事実を踏まえても、初回の正式リリース番号を

- **案A**: `v0.1.0`（`__version__`の現在値と一致させる。試験タグとの
  文字列上の類似は、`-m4-test`という接尾辞で見分けがつくため実害は
  小さいという考え方）
- **案B**: `v0.1.1`（試験タグと数字部分から紛らわしくないよう区別する）

のどちらにするかは、**本ADRでは決定しない**。次回リリース準備時
（`docs/release_runbook.md`の手順に入る直前）に遥哉が判断すること。

## この決定が縛るもの

- `build-windows.yml`の`permissions`を`contents: write`へ変更したくなった
  場合は、本ADRの決定3を再検討する判断になる。ADRを更新すること
- リリース手順は`docs/release_runbook.md`を正とする。手順を変えた場合は
  同ファイルを更新すること
- AIはgitタグを作成・削除しない（決定1）。GitHub Releasesの作成も行わない
  （決定2）。作業75-5の停止条件と同じ制約を、今後の全作業回に対する
  恒久ルールとしてここに固定する
