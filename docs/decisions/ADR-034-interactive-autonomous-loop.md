# ADR-034: 対話型の自律ループ（opus の司令塔＋sonnet の実装役）へ移行し、スクリプト起動のループを廃止する

- 日付：2026-09-30
- 状態：採用

## 背景
- ユーザの目的：(1) 案を渡せば、なるべく AI で完結して開発が進むこと。(2) 上流工程を opus、下流工程を sonnet が担うこと。(3) ターミナル1枚で完結し、ユーザがスクリプトを手で起動しないこと。
- 現状の実作業は、claude.ai のチャット（設計・指示の作成・報告の確認）と Claude Code（実行）の間を、人が中継する方式である（ADR-030）。
- scripts/work_loop.sh の最終実行は 2026-08-04。実運用は PR 1件で止まり、失敗（is_error=true）を success と記録していた（docs/ai_loop_state/2026-08-26.md §3-A）。
- scripts/review_loop.sh は試走8回（2026-08-26〜09-01）。監査役が承認した成果物に、後日の人間のレビューで誤検出7件が見つかった（docs/ai_loop_state/review_loop_trial8_2026-09-01.md）。
- どちらも人が手で起動する方式で、停止・廃止を決めた ADR はない。

## 決定
1. ユーザは `claude --model opus` の対話セッション（以下「司令塔」）を1つ起動する。上流工程は司令塔が、下流工程は sonnet のサブエージェントが担う。
2. 上流1（司令塔）：ユーザの案を要件と受け入れ基準にまとめ、Issue に分解する。判定ロジックの変更は事前登録を含める。ここでユーザの承認を1回受ける。
3. 下流（実装役。model: sonnet のサブエージェント）：Issue ごとに、ブランチ作成・実装・verify.sh・pre-push-check・PR 作成までを行う。
4. 一次レビューは Claude PR Review（sonnet、GitHub 側で自動）が行う。
5. 上流2（司令塔）：CI と review の結果を読み、指摘の採否を判断する。差し戻しは1 Issue あたり2回まで。超えたら停止し、ユーザに報告する。
6. 合否の最終的な根拠は、verify.sh と CI の終了コードとする。司令塔や review の承認だけを合格の根拠にしない。
7. 人が行うのは、上流1の承認・PR のマージ・deny 対象の編集の3つ。deny 対象の変更が要るときは、司令塔が全文と sha256 を用意してユーザに依頼する。
8. スクリプトで起動するループ（work_loop.sh・loop_git.sh・review_loop.sh・review_audit.sh・review_proposer.sh と、その設定・プロンプト・テスト）は廃止し、削除する。削除は別の PR で行う。記録（docs/ai_loop_state/）は残す。scripts/setup_hooks.sh と .githooks/pre-push はループと無関係の安全装置なので残す。
9. 本 ADR は次の決定を置き換える。ADR-030 の中継方式と「マネジメント役のエージェントは置かない」。ADR-011〜014・016 のスクリプト方式のループ。ADR-032 の「サブエージェントは読み取り専用」（実装役に限る。調査役・監査役は読み取り専用のまま）。

## 実装の順序（それぞれ別の Issue とする）
1. 本 ADR
2. スクリプト方式のループの削除（CLAUDE.md の自律ループの規則、runbook の関連節、剪定基準2の前提の更新を含む）
3. 実装役サブエージェントの定義と、司令塔の手順スキル（現在 claude.ai 側で行っている、指示の作成と報告の確認の規則を移す）
4. 失敗の診断スキル（読み取り専用。まず CI の失敗と review の失敗を対象にする）
5. 小さな Issue 1件で試走し、結果を記録する

## 未決定
- 司令塔のセッションの単位（1案＝1セッションとするか）と、コンテキストの管理の方法。
- 費用の歯止め。対話セッションには --max-turns がない（ADR-030）。
- 追加コミットのときに review を再実行するか（ADR-006）。
