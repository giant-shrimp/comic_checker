# ADR-019: select_review_comment.sh の2次経路を削除し、fail-closedの単一経路を採用する

- 日付：2026-09-11
- 状態：採用

## 背景

`scripts/select_review_comment.sh`は、`claude-review.yml`のトラッキングコメントを
PRのコメント一覧から特定するスクリプトで、当初は2段階の特定方法を持っていた。

1. 1次経路: 本文に`actions/runs/<run_id>`を含む最新コメント
2. 2次経路（フォールバック）: `author.login`が`"github-actions[bot]"`である最新コメント

Issue #93の調査で、実運用のワークフロー実行では対象コメントが常に1次経路で
特定できており、2次経路が実際に発火したケースは一度も観測されていないことが
判明した。PR #206（Refs #93）でこれをさらに実測した結果、以下が判明した。

- 呼び出し元`.github/workflows/claude-review.yml`は`gh pr view --json comments`
  でコメントを取得しており、この出力の`author.login`は`"github-actions"`
  （`"[bot]"`サフィックス無し）である。
- 一方`gh api repos/.../issues/.../comments`（REST）経由で同じコメントを取得すると
  `"github-actions[bot]"`になる。サフィックスの有無は同一コメントの属性ではなく、
  取得コマンド（GraphQL経由の`gh pr view` / REST経由の`gh api`）依存で変わる。
- 2次経路の条件は`.author.login == "github-actions[bot]"`という完全一致であるため、
  呼び出し元が実際に使う`gh pr view`の出力とは一致しない。
- 実測範囲: 保存済み実データ19件（過去の`claude-review.yml`実行時に`gh pr view`で
  取得した実データ）および現行の`gh pr view`出力。いずれも例外なし。

結果として、1次経路が失敗した時点で2次経路の対象は常に0件になり、必ず
fail-closed（exit 2）になることが確認された。この設計判断はIssue #207に
切り出された。

## 決定

1. **2次経路を削除し、1次経路（run_id一致）の単一経路＋fail-closedを明示的な
   設計とする。**
2. 削除に伴い、`tests/test_select_review_comment.py`から2次経路固有のテストを
   除去し、代わりに「run_id不一致時は`author.login`の値に関わらずexit 2になる」
   ことを固定するネガティブコントロールを追加する。

## 決定の理由

- **削除は実行時の挙動を変えない。** 1次経路が失敗した場合、削除前も削除後も
  結果はexit 2で同一である（2次経路は実運用では一度も一致しないことが
  実測済みのため）。
- したがって、Issue #207が「判断に必要な未取得の材料」として挙げていた
  「1次経路の失敗頻度」「2次経路が救済すべき具体的な失敗シナリオの有無」は、
  本決定の前提にはならない。挙動を変えない削除であるため、これらの材料が
  無くても判断できる。
- コードの見た目（2次経路が存在する）と実態（不発）の乖離を解消できる。

## 検討した案と棄却理由

- **案1（条件を`"github-actions"`にも緩める）**: 棄却。これは実行時の挙動を
  変える唯一の案であり、ADR-006が既に「未検証」として指摘している「他のワーク
  フローが同じトークンで別のコメントを投稿していないか」という懸念を、潜在的な
  リスクから現実のリスクへ転じさせうる。また、1次経路の失敗頻度が未観測のまま
  fail-closedを緩める根拠が無い。
- **案3（現状維持）**: 棄却。コードの見た目（2次経路が存在する）と実態
  （実運用では不発）の乖離が残り続ける。

## 受け入れたリスク

1次経路が将来失敗しやすくなった場合、救済手段（2次経路）が無いため、
レビュー確認自体が失敗し続けるリスクを受け入れる。

## 見直す条件

1次経路の失敗が実際に観測された場合。その時点で得られる観測データ
（失敗頻度・失敗の原因）を根拠に、救済設計を再検討する。
