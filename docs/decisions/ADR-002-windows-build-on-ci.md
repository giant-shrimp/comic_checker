# ADR-002: Windows向けEXEのビルドを GitHub Actions（windows-latest）へ移す

- 日付：2026-07-25
- 状態：採用
- 関連：Issue #20（M4-1）、Issue #21（M4-2）、[ADR-001](ADR-001-main-protection.md)

## 背景

「最終目的」は、Pythonをインストールしていないwindows PCで、EXEをダブルクリックする
だけで動作するGUIツールにすることである。M3でPyInstallerによる軽量ビルド
（`comic_checker.spec`）を確立し、Windows実機で `dist\comic_checker.exe` 14.1MB の
生成と動作を確認済み。

ここで残っていた制約が「PyInstallerはクロスコンパイル不可」である。この事実自体は
正しいが、**そこから「人間がWindows機を操作する必要がある」を導いていたのが誤り**
だった。必要なのは「Windows上でビルドすること」であって、「人間がWindows上で
ビルドすること」ではない。

`windows-latest` ランナーでビルドすれば、開発フローから「WindowsのPython環境で
EXEを作る」工程が消える。その結果、M4に残る人手は「クリーンなWindows PCでの
実行確認」（Issue #21 / M4-2）だけになる。

## 決定

**`.github/workflows/build-windows.yml` を追加し、`windows-latest` ランナー上で
`pyinstaller comic_checker.spec` を実行して、`dist/comic_checker.exe` を
artifact としてアップロードする。**

- トリガー：`workflow_dispatch`（手動）と、タグ `v*` のpush
- `actions/setup-python` で `requirements.txt`（軽量ビルド用）＋ `pyinstaller` を導入
- `comic_checker.spec` は**変更しない**。M3で実機検証済みの設定をそのまま使う
- `actions/upload-artifact` で `dist/comic_checker.exe` をアップロード
  （`retention-days: 14`）
- **このワークフローはビルドとartifact生成のみを行い、一切pushしない**

### 生成物の自動検証をジョブ内で行う

ビルドが「成功した」ことと、**正しいものが出来た**ことは別である。M3で人間が目視して
いた確認項目を、そのままジョブ内のゲートにする。満たさなければジョブを失敗させる。

| # | 検証内容 | 根拠 |
|---|---|---|
| (a) | `build/comic_checker/warn-comic_checker.txt` に `excluded module named comic_checker.manba_client` が含まれること | `main.py` の `_import_manba_client()` による遅延importが壊れていないことの直接的な証拠。モジュール先頭のimportに戻ると、この行が消えると同時に軽量ビルドが起動時クラッシュするようになる |
| (b) | 同ファイルに `playwright` への言及が無いこと | `manba_client` が除外されていれば `playwright` は依存グラフに到達しない。言及があれば、除外が効かず同梱を試みている兆候 |
| (c) | `dist/comic_checker.exe` のサイズが 100MB 未満であること | M3実測は14.1MB。Chromium同梱なら数百MBになる。大幅超過は除外設定が効いていない兆候 |

閾値の100MBは14.1MBに対して余裕を持たせてある。**これは「サイズを14MBに保つ」ための
回帰テストではなく、「Playwright/Chromiumが混入していない」ことの粗い検出器**である。

### pushしない理由

ADR-001「受け入れたリスク」3 の通り、`main` への直push防止は
`.githooks/pre-push`（クライアントサイドフック）で実現しており、**CIからのpushには
原理的に効かない**。したがってCIにpush権限を伴う仕事をさせない。このワークフローの
出力はartifactだけであり、リポジトリの内容を書き換えない。ワークフローの
`permissions` も `contents: read` に絞る。

## 却下した案

### 1. ローカルWindows機での手動ビルドを継続する（現行 = M3の手順）

**理由：毎回人手が必要。**

リリースのたびにWindows機を立ち上げ、`git pull` し、仮想環境を有効化し、
`pyinstaller` を叩く工程が発生する。この工程自体には判断が要らず、失敗しても
「やり直す」以外の選択肢が無い。人間が判断する価値があるのは M4-2（実機での
動作確認）だけであり、そこに人手を集中させるべきである。

なお**この手順は削除しない**。`docs/build_windows.md` に「CIが使えない場合の代替」
として残す（Actions障害時・Freeプランの実行時間を使い切った場合・CI以前の挙動を
再現して切り分けたい場合に必要になるため）。

### 2. Webアプリ化（ローカルサーバ方式）

**理由：Python処理系が必要という制約が解消されないうえ、失敗経路が増える。**

「ブラウザで開くだけ」に見えるが、サーバと判定ロジックが利用者PC上で動く以上、
利用者PCにPython処理系が必要である。結局それをEXE化するためにPyInstallerが要る。
つまり**現行の制約を1つも取り除かないまま**、次の失敗経路が増える。

- ポート衝突（既に使われているポートを掴めない）
- ファイアウォールの許可ダイアログ（利用者に判断を求める。「最終目的」の
  「ダブルクリックするだけ」から遠ざかる）
- プロセス残留（ブラウザのタブを閉じてもサーバプロセスが生き続ける）

GUIをtkinterからブラウザに置き換えるだけの変更に対して、割に合わない。

### 3. ブラウザ完結型（判定ロジックをJSへ移植 / Pyodide）

**理由：判定ロジックが二重実装になり、テストと計測の資産が分岐する。**

Wikipedia経路はCORS的には成立する（MediaWiki APIは `origin=*` を受け付けるため、
ブラウザから直接叩ける）。技術的に不可能なわけではない。

問題は`wikipedia_client.py`の中身である。`COMPLETED_STRONG_RE` /
`COMPLETED_WEAK_RE` / `CONTINUATION_VETO_RE` の二層構造、メディアミックス判定、
infobox解析は、いずれもIssue #8〜#12で**実在の誤判定を踏んで**作り込んだものであり、
その正しさは `tests/test_wikipedia_client.py` の回帰テスト群に固定されている。
これをJSへ移植すると：

- 同じ判定ロジックがPythonとJSの2箇所に存在し、片方だけ直る事故が起きる
- `tests/test_wikipedia_client.py` と `scripts/measure_unknown_rate.py`
  （判定不能率の計測資産）はPython側にしか無く、JS側の品質が測れなくなる

Pyodideを使えば移植は不要だが、初回ロードで数十MBのwasmランタイムを取得する
必要があり、「配布物が軽い」という利点も失われる。

加えて、**manba経路は原理的に不可能**である。Cloudflareのボット対策下にあるサイトへ
ブラウザから直接fetchすることはCORS的に成立せず、フォールバック機能そのものが
失われる。

### 4. ホスティング型Webアプリ（サーバ側で判定して結果を返す）

**理由：条件は満たすが、利用者のExcelを外部へ送る構成になり、運用コストが常時発生する。**

利用者PCにPythonが不要という条件は確かに満たす。しかし：

- 利用者のExcelファイルを外部サーバへアップロードする構成になる。個人の蔵書リストで
  あっても、ローカル完結だったものをネットワーク越しにする判断は、得られる利便性に
  見合わない
- サーバの維持（ホスティング費用・稼働監視・依存の更新）が**使っていない期間も**
  発生する。個人利用ツールには過剰である

## 受け入れたリスク

いずれも承知の上で受け入れる。

1. **privateリポジトリのartifactダウンロードには、リポジトリのアクセス権が必要。**
   第三者へ配布する場合は、開発者が自分でダウンロードして受け渡す。
   artifactのURLを共有しても、権限の無い相手はダウンロードできない。
   （リポジトリをpublicにする、またはGitHub Releasesへ添付する選択肢もあるが、
   現時点では不要と判断した。必要になった時点で本ADRを見直す。）

2. **GitHub Free の実行時間の消費。**
   privateリポジトリのFreeプランは月2,000分（Linux換算）で、**Windowsランナーは
   2倍換算**のため、実質1,000分である。1ビルド約5分＝**10分消費**の想定。
   月100回ビルドすると上限に達する計算だが、リリース時と手動確認時にしか回さない
   運用であれば十分に収まる。トリガーを `workflow_dispatch` とタグpushに限定し、
   `push`（全ブランチ）や `pull_request` を対象にしていないのはこのためである。
   併せて、Freeプランのartifactストレージは500MBのため `retention-days: 14` とする
   （14.1MB × 保持期間分。毎日ビルドしても約200MBに収まる）。

3. **SmartScreen警告が発生しうる。**
   M3の実機ビルドではSmartScreen警告は出なかったが、これは `git clone` したソースから
   自分でビルドしたため、ダウンロードファイルに付与される「ゾーン識別子」が
   無かったことが影響している可能性が高い。**ランナー上のビルドはダウンロード経由の
   配布になるため、M3では出なかった警告が発生しうる。**
   Issue #21（M4-2）の実機検証で**必ず確認する**こと。出た場合の対応の選択肢
   （onedir化 / コード署名 / 許容）は `docs/build_windows.md` の該当節に記載済み。

## この決定が縛るもの

- **EXEの標準的な入手経路は GitHub Actions の artifact とする。** ローカルビルドは
  代替手段として残すが、既定ではない。
- **このワークフローにpushを伴う仕事をさせない。** リリースノート生成・タグ付け・
  バージョン更新のコミット等をここに足したくなった場合は、ADR-001「受け入れた
  リスク」3 に戻って再検討すること。CIからのpushはpre-pushフックでは止まらない。
- `comic_checker.spec` を変更した場合は、(a)(b)(c) の検証が通ることをCIのログで
  確認してから、M4-2の実機検証をやり直す。
