# ADR-010: 計画書 Phase 7 の採用率指標を判定基準としては採らない

- 日付：2026-08-25
- 状態：採用

## 背景

`ai-loop-implementation-plan_v8.md`（AI Loop実装計画書）Phase 7は、月次で
3指標（採用率・受け入れ1件あたりのコスト・verify.shをすり抜けた不具合の
件数）を取ることを推奨し、採用率について次の目安を示している。

> 採用率50%を下回ったら赤信号

この指標が前提としている運用は、**AIが提案（PR）を出し、人間がその中から
取捨選択してマージする**という構図である。10件のPRが出て6件が却下されるなら
採用率は40%になり、赤信号として検知される、という設計になっている。

本プロジェクトの運用はこれと異なる。CLAUDE.mdの作業ルール106行目は次のように
明記している。

```
- 変更後は必ず ./scripts/verify.sh を実行してから完了報告する
```

（`CLAUDE.md` 106行目、本ADR作成時点で実測確認済み）

この「完了報告」は、対話セッションではPR作成の提案・実行のタイミングと
一致する。つまり本プロジェクトでは、**`verify.sh` を通してからでなければ
「完了」として報告されず、PRも作られない**。取捨選択が起きるのはPRが
作られる前（対話セッション内での検証）であり、PRが作られた後ではない。
`scripts/work_loop.sh`（非対話ループ）も同様に、`verify.sh` が通り、かつ
実際に変更が生じた場合にのみコミット・push・PR作成へ進む設計になっている
（`ERRORS.md`「AI Loop（`scripts/work_loop.sh`）の検証で分かったこと
（Issue #14〜#16）」のno-op検出の記述、および`scripts/work_loop.sh`本体の
該当ロジック）。

**実測値**（`./scripts/loop_metrics.sh` の生の出力。両期間とも本ADR作成日に
実行）:

```
$ ./scripts/loop_metrics.sh 30
作成されたPR数（全体）  | 128
MERGEDされたPR数（全体） | 128
採用率（MERGED/作成、全PR対象） | 100.0%
ai-authoredラベル付きPR数（作成、期間内） | 2
AI製PR限定の採用率 | 100.0%

$ ./scripts/loop_metrics.sh 90
作成されたPR数（全体）  | 137
MERGEDされたPR数（全体） | 137
採用率（MERGED/作成、全PR対象） | 100.0%
ai-authoredラベル付きPR数（作成、期間内） | 2
AI製PR限定の採用率 | 100.0%
```

直近30日・90日のいずれも、全PR対象・`ai-authored`ラベルによるAI製PR限定の
いずれの採用率も**100.0%**だった。`ai-authored`ラベルの全期間での付与件数は
2件（実測: `gh pr list --state all --label "ai-authored" --limit 500 --json
number | jq 'length'` の出力が`2`）。

この事実（欠陥2）はPR #198（`fix/loop-metrics-note`）で既にスクリプトの出力と
`docs/runbook.md`への注記として記録済みである。本ADRは、その事実に基づいて
「この指標を判定基準として採らない」という**決定**を残すものである
（前回はあくまで実測結果の記録であり、決定ではなかった）。

## 決定

1. **計画書 Phase 7 の採用率（全PR対象・AI製PR限定のいずれも）を、
   ループの品質を判定する基準としては採らない。** 「50%を下回ったら赤信号」
   という計画書の判定式は、本プロジェクトの運用（PR作成前に`verify.sh`を
   通す）のもとでは機能しない。
2. **`scripts/loop_metrics.sh` は採用率の数値を出し続ける。** 削除・非表示
   にはしない。理由は、この値がゼロになった場合（`verify.sh`を通さずに
   PRが作られた、または大量にマージされずに残っている場合）には、それ自体が
   運用ルールからの逸脱を示す異常値として意味を持ちうるためである。ただし、
   100%が「良好」を意味しないのと同様に、100%未満になったことも直ちに
   「悪化」を意味しない（分母が極端に小さい場合に単発のCLOSED PRで大きく
   動きうる）。数値の解釈は本ADRの範囲外とし、都度確認する。

**見直し条件**（次のいずれかが起きたら、採用率を判定基準に戻すか、別の設計を
検討する）:

- 非対話ループ（`loop/<issue>`ブランチ）由来のPRが一定数を超える
  （目安: 直近30日で10件以上。現状は実測1件〔`./scripts/loop_metrics.sh 30`
  の「参考: loop/<issue> ブランチ由来PR数」〕であり、この目安には遠く及ばない）。
  非対話ループは人間による都度の検証を介さないため、この経路のPRが増えれば
  「作られたPR」の中に本当に不採用となりうるものが混ざり始める可能性がある
- PR作成前に`verify.sh`を通す運用（CLAUDE.md106行目）自体が変更される
- 対話セッション中に生成されたが人間が明示的に却下し、PR化されずに終わった
  提案を記録・カウントする仕組みが別途整備される（後述「却下した案」参照）

## 却下した案

### 案B: 分母を「AIが提案した実装案の数」に変える

却下。対話セッション中にAIが提示した実装方針・提案の総数を機械的に数える
手段が本リポジトリには無い。会話ログを構造化して「これは1つの提案だった」
と識別する基準を新たに定義し、かつ継続的に記録する仕組み（提案のたびに
何らかのログを残す運用）を新設する必要があり、記録コストが指標の価値に対して
過大である。加えて、「提案」の単位（1ターン単位か、1つの設計判断単位か）が
曖昧で、恣意的に数えやすい・数えにくい形に振れるリスクがある。

### 案C: 「PR作成後の修正コミット数」に置き換える

却下。これは計画書が定義する採用率（受け入れられた成果物の割合）とは
**別の指標**であり、代替にならない。修正コミット数は「一度で正しく書けたか」
という別の性質（実装の初回品質）を測るものであり、「不採用がどれだけ
発生したか」という採用率の意図には答えない。また、この値を測って何を
判断するのか（閾値をどこに置くか、修正が多いことが常に悪いのか）が
本ADR作成時点で定まっておらず、指標として導入する前提が整っていない。

## 影響

計画書 Phase 7 の3指標のうち、本プロジェクトで判定基準として機能する
ものは**0個**である。

- 採用率: 構造的に100%へ張り付くため機能しない（本ADRの決定）
- 受け入れ1件あたりのコスト: 取得不能（`scripts/loop_metrics.sh`実測、
  対話セッションのコストを機械的に集計する手段が無い）
- verify.shをすり抜けた不具合の件数: 取得不能（`bug`ラベルの運用実績が
  無い）

**Phase 7が想定する定量指標による「ループが元を取れているか」の判断は、
現状では行えない。** 隠さず記録する。3指標のうち採用率とコストは構造的・
運用的な理由により今後も改善の見込みが薄く、不具合件数のみ`bug`ラベルの
運用を始めれば取得可能になる（`scripts/loop_metrics.sh`の該当行に既に
その旨の提案が出力される）。

## 欠点

- **品質低下を定量的に検知する手段が無い状態が続く。** 3指標がいずれも
  機能しない以上、実装の質が徐々に落ちていても、数値の上ではそれを検知
  できない。計画書Phase 7が指摘する「理解の負債」（トークンより高くつく
  コスト。自分の理解がコードベースに追い越されること）が進行しても、
  本ADRが対象とする定量指標には一切現れない。
- **代替の定性的な確認手段は、本ADRでは導入を決定しない。** 計画書
  Phase 7「理解の負債」節は、マージ済みPRを月に3件抜き取り「なぜこの
  変更が必要だったか」を1行で説明できるかを自問する方法を挙げている。
  これは本ADRの決定と両立しうる対策候補ではあるが、**本ADRはこれを
  採用するとは決定しない**。導入の要否・実施主体・頻度は別途検討する。
- **見直し条件（非対話ループ由来PRが10件を超える等）の監視自体が
  自動化されていない。** `scripts/loop_metrics.sh`は該当件数を出力するが、
  それを見て「見直し条件に達したか」を判断するのは人間であり、この判断が
  行われないまま条件を超過し続けるリスクがある。
