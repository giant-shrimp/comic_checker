# ADR-004: Phase 5（GitHub Actions常時稼働）着手にあたっての前提条件

- 日付：2026-08-06
- 状態：採用

## 背景

`ai-loop-implementation-plan_v8.md`（AI Loop実装計画書）に対する現状の到達度を
精査したところ、Phase 1〜4はほぼ達成済み（一部は計画を上回る拡張あり）だが、
Phase 5（GitHub Actions常時稼働）には未着手であることが分かった。着手可能かを
判定するための読み取り専用調査を行い、次の事実を実測で確認した。

- `main`のブランチ保護は403 `Upgrade to GitHub Pro or make this repository public`
  で設定不可（GitHub Free + privateリポジトリの制約）
- Actionsのワークフロー権限は `default_workflow_permissions: read`・
  `can_approve_pull_request_reviews: false`（計画Phase 5-5が要求する
  「Allow GitHub Actions to create and approve pull requests」が無効のまま）
- `ANTHROPIC_API_KEY`・`CLAUDE_CODE_OAUTH_TOKEN`いずれのシークレットも未登録
- `.github/CODEOWNERS`は存在しない
- `.github/workflows/`には`verify.yml`（Phase 2-4のCIゲート）と
  `build-windows.yml`（EXEビルド、AI Loopとは無関係）のみが存在し、
  Claude関連の常時稼働ワークフローは1つも無い

これらのうち、着手前に方針を決めておく必要がある3点について、ここで決定する。

## 決定1: 認証は `ANTHROPIC_API_KEY` を使う（`CLAUDE_CODE_OAUTH_TOKEN`は使わない）

計画Phase 5-1が挙げる2方式のうち、API従量課金の`ANTHROPIC_API_KEY`を採用する。

**理由**

- `--max-budget-usd`はドル建ての上限であり、従量課金でなければ機能しない。
  v8計画Phase 7の月額上限の見積もり（「PRレビュー $1.00×20件＝$20」等）は、
  この上限が実際に効くことを前提にしている。サブスク枠（OAuthトークン）を
  使った場合、この上限が同じ意味を持つかどうかは保証されない
- 自動実行がサブスク枠を消費する場合、対話セッション側の利用枠を圧迫する
  おそれがある。人間が対話でClaude Codeを使う枠と、Actionsが自律的に消費する
  枠を、同じプールで奪い合う構成は避けたい

**未確認事項として明記する**: サブスク枠とプログラマティック利用の分離は
2026年6月15日実施が一度公表された後に撤回された経緯があり、現在の状態は
本ADR作成時点で確認できていない。ただし上記2つの理由は、分離の有無が
どちらの状態であっても成立する（分離されていなければ対話枠を直接圧迫し、
分離されていても`--max-budget-usd`がドル建て前提である点は変わらない）ため、
決定そのものは変えない。着手時に公式ドキュメントで最新の状態を確認すること。

**却下した案**

- `CLAUDE_CODE_OAUTH_TOKEN`（Pro/Maxのサブスク枠）: 上記2つの理由により却下。
  費用面では有利に見えるが、上限の実効性と対話セッションへの影響という
  2つの不確実性を抱えたまま常時稼働させることになる

## 決定2: `main`のサーバサイド保護は Step 1 の間は導入しない

**前提**: GitHub Free + privateリポジトリではブランチ保護が設定不可（403を実測）。

**決定**: v8計画5-6の**Step 1（PRにコメントするのみ、コード変更なし）に限り**、
ワークフローに`contents: write`を与えないことで、サーバサイド保護の不在を
設計そのもので回避する。`contents: write`が無ければ、ワークフローの実装に
バグがあっても`main`（あるいはどのブランチも）に書き込む経路自体が存在しない。

Step 2（Actionsからブランチを切りPRを作る。`contents: write`が必要になる）へ
進む時点で、本決定を再検討する。その時点で取りうる選択肢は次の3つ：

- リポジトリをpublicにしてrulesetsを使う
- GitHub Proへ課金してブランチ保護を有効化する
- Step 1に留まり、Step 2以降には進まない

**ADR-001「受け入れたリスク」3との関係**: ADR-001は「クライアントサイドフック
（`.githooks/pre-push`）はCIには効かない」ことを既に受け入れたリスクとして
記録している。これはこれまで**仮定の話**だったが、Step 2でActionsから
`contents: write`を与えて`main`以外のブランチへ書き込むワークフローを追加した
時点で、**この受け入れ済みリスクが実際に露出する対象を持つ状態に変わる**。
計画のテンプレート通り実装する限り（`main`へは直接pushせずブランチを切って
PRを作るだけ）実害は生じないはずだが、「ワークフローの実装ミスで`main`向けに
pushコマンドが誤発行される」経路を止める手段は、Step 2に進んだ時点で
存在しないことになる。Step 1に留めることで、この露出そのものを先送りする。

**却下した案**

- Step 1の時点で`contents: write`相当の権限を先取りして与えておく:
  却下。Step 1は「コメントのみ」で完結する設計であり、書き込み権限を
  持たせる理由が無い。不要な権限を持たせないという計画1-3の原則（権限は
  最初は狭く、運用しながら広げる）とも整合しない

## 決定3: `.github/workflows/`の`deny`は維持する

ADR-003（CI定義をAIの書き込み対象から外す）の決定を、Phase 5着手後も維持する。

**理由**

- ワークフロー定義は`secrets`へのアクセスと`contents`/`pull-requests`等の
  実行権限を持つ特権的な定義であり、`scripts/verify.sh`・
  `.claude/settings.json`と同じ「採点者を書き換えさせない」対象である
  （ADR-003の非対称性の論理がそのまま適用される：検査される側〔AIが実装する
  ワークフロー〕が検査の定義自体を書き換えられる状態は、`verify.sh`を
  denyしている理由と同じ構造で崩れる）
- Phase 5はワークフロー追加が作業の本体であり、この決定により作業量は
  増えるが、ADR-003が既に「AIが全文提示 → 人間が保存 → AIがdiffで照合 →
  commit・push・PR作成 → 実行結果の実測報告」という手順で実運用できることを
  PR #69で確認済みである。Phase 5でも同じ手順をそのまま使う

**運用**: Claude Codeはワークフローの**下書き**をリポジトリ外の scratchpad
（このセッションの慣習に倣う。あるいはADR-003の手順どおり全文提示でもよい）に
書き、`.github/workflows/`への実際の配置は人間が行う。配置後は`diff`による
一致確認をAIが行う（目視で済ませない。ADR-003 PR #69で末尾改行の写し間違いが
実際に検出された実績があるため）。

**却下した案**

- `deny`を緩める: ADR-003の決定を覆すことになる。却下理由はADR-003と同一
  （検査される側が検査の定義を書き換えられる非対称性の崩れ）

## 影響

この決定が縛るもの：

- Phase 5に着手する場合、認証は`ANTHROPIC_API_KEY`で行う（環境変数・シークレット名を
  `CLAUDE_CODE_OAUTH_TOKEN`前提で設計しない）
- 新設するワークフローには、Step 1の間は`contents: write`を与えない
  （PRコメントのみ・`pull-requests: write`と`contents: read`にとどめる）
- ワークフローファイルの追加・変更は、ADR-003の手順（AI提示 → 人間保存 →
  diff照合 → commit/push/PR → 実行結果の実測報告）を継続する
- Step 2（`contents: write`が必要な自動PR作成）へ進む判断をするときは、
  本ADRの決定2を再検討し、`main`保護の選択肢（public化／Pro移行／Step 1据え置き）
  を選び直すこと。その際は本ADRを更新するか、新しいADRの「背景」から参照すること
