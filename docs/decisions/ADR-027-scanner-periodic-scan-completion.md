# ADR-027: 走査器の定期走査（ADR-024決定3）の完了と、ADR-017との関係の整理

- 日付：2026-09-20
- 状態：採用

## 文脈

ADR-024決定3は「全追跡ファイルへの走査を定期的に行う運用を設ける」と決定し、
設計要件として次の3点を挙げ、実装は別途とした。

- 実行契機（定期・リリース前・PR前のいずれか）は本ADRでは決めない。
- 対象はgit追跡ファイル全件とする。
- 実行結果の件数を記録し、前回からの増減が分かる形にする。

ADR-026（走査器の偽陽性事前登録簿の実装）で`scripts/check_scanner_registry.sh`
（抑制層）を追加したのち、この決定3の実行契機が既に満たされているかを実測で
調査した。

**実測（本ADR作成のために実施した調査ラウンドで確認）**: 抑制層を実リポジトリに
対して実行する`tests/test_check_scanner_registry.py::test_repo_registry_matches_current_scan`
（引数なし、実リポジトリ入力）が存在する。`scripts/verify.sh`は
`python -m pytest -q`をpytest.ini等による対象範囲の限定なしに実行しており、
デフォルト探索でこのテストを収集・実行する。`.github/workflows/verify.yml`は
PRとmainへのpushのたびに`./scripts/verify.sh`を実行する。すなわち、
**追加の実装なしに、抑制層（登録簿との一致確認）は既にPRごと・mainへの
pushごとに実行されている。** この経路は「登録簿に無い検出（未登録検出）」
「登録簿にあるが検出されない項目（陳腐化登録）」のいずれかが1件でもあれば
このテストが失敗し、`verify.sh`全体が失敗し、CIのチェックが失敗する形で
機能する。

これによりADR-024決定3の「実行契機」要件は追加実装なしに満たされていることが
判明した。残る要件は「実行結果の件数を記録し、前回からの増減が分かる形にする」
のみである。

## 決定

1. **ADR-024決定3の実行契機の要件は、追加の実装を行わず、既存の経路
   （`tests/test_check_scanner_registry.py::test_repo_registry_matches_current_scan`
   →pytestのデフォルト探索→`scripts/verify.sh`→`.github/workflows/verify.yml`）
   で満たされているものとして扱う。** `scripts/verify.sh`への明示的な呼び出し
   行の追加、`.github/workflows/**`への独立ステップの追加は、いずれも行わない。
2. **走査結果の記録簿を`docs/scanner_scan_history.md`として新設する。**
   各行は日付・検出のあったファイル数・検出総件数・型ごとの件数
   （home-path/email/honorific）・登録簿の登録件数・前回比（検出総件数）を
   持つ表とする。
3. **値の計算を`scripts/scanner_scan_summary.sh`で機械化する。** 走査器を
   Python APIとして呼び出すだけで、走査器のファイル自体は変更しない。出力は
   記録簿へ追記する1行分のMarkdown表記であり、ファイルへの書き込みは行わない
   （追記自体は人間またはAIが手で行う）。実行権限は付与せず、
   `bash scripts/scanner_scan_summary.sh`として呼ぶ運用とする。
4. **記録簿の陳腐化を検出する機械的な手段は設けない。** 登録簿・棚卸し表とは
   異なり、記録簿の各行は特定日時に実測した値の記録であり、後から内容が
   変わって「古くなる」性質の主張ではないため（「限界」節を参照）。

## ADR-017との関係

- ADR-017の決定1（個人情報走査の**CLI**を`verify.sh`のゲートに組み込まない）
  は、今も覆さない。**抑制層（`scripts/check_scanner_registry.sh`）は走査器
  CLI（`scripts/check_no_personal_info.py`）そのものではなく、その検出結果を
  登録簿と突き合わせる別のプログラムである。** ADR-017が決定1で対象とした
  「走査器CLIを直接ゲートに組み込む」ことは、本ADRでも決定2・3のいずれでも
  行っていない。
- ADR-017が挙げた3つの決定の理由のうち、根拠2（「常時失敗する検査を常時
  実行のゲートに置くと、失敗が常態化して検査が形骸化する」）は、実測で崩れて
  いる。抑制層は実リポジトリに対してOK・終了コード0で通っており（本ADR作成
  時点で確認済み、`docs/scanner_scan_history.md`の初回記録が示す799件の検出
  すべてが登録簿でカバーされている状態）、「常時失敗する」という前提が現状
  成立しない。
- 根拠1（「誤検出と検出漏れがパターン側では分離できない」）は今も成立する。
  ただし抑制層はパターンそのものを変更せず、検出後に既知の偽陽性だけを
  突き合わせで抑制する設計（ADR-026決定1「走査器のパターンと除外語彙は
  変更しない」）であるため、この根拠は抑制層の導入・常時実行の障害にならない。
  検出漏れの危険を増やす操作（パターンを絞る等）を一切行っていないため。
- したがって、ADR-017の決定1自体（走査器CLIを直接ゲートに組み込まない）は
  維持しつつ、走査器CLIとは別のプログラムである抑制層が既に常時実行の経路に
  乗っているという事実は、ADR-017の決定と矛盾しない。

## 採らなかった案

- **`scripts/verify.sh`へ抑制層の呼び出し行を明示的に追加する案**: 却下。
  文脈節の実測が示すとおり、pytest経由で既に実質的に同等の効果（未登録検出・
  陳腐化登録があれば`verify.sh`が失敗する）が得られており、追加する利益が
  乏しい。加えて`verify.sh`は`.claude/settings.json`でEdit/Writeがdeny
  対象になっている（`.github/workflows/verify.yml`のコメントに記載）ため、
  AIによる直接編集は運用上の障害になりうる。
- **`.github/workflows/**`へ独立したステップを追加する案**: 却下。同様に
  pytest経由で既に効果を得られているうえ、`.github/workflows/**`はADR-003
  によりAIが編集しない対象であり、実装は人間が手で行う必要がある。追加の
  利益に対して要する調整コストが見合わない。
- **手動実行の運用化のみとする案**: 却下。ADR-017決定2（投稿前の手動実行）
  は既に別途運用されている。定期走査という決定3の趣旨は「投稿前」に限らない
  継続的な確認であり、手動運用だけに頼ると実行を忘れるリスクが機械的な
  ゲートより高い。文脈節の実測で機械的なゲートが既に機能していることが
  判明した以上、それに頼らず手動運用のみへ後退する理由がない。

## 代償

- 記録簿への追記自体（表の1行の追加）は人間またはAIが手作業で行う必要があり、
  自動化していない。追記を忘れれば記録が途切れる。
- `scripts/scanner_scan_summary.sh`は値の計算とMarkdown行の整形のみを行い、
  ファイルへの書き込みは行わない。追記のたびに、出力された行をコピーして
  `docs/scanner_scan_history.md`へ貼り付ける手作業が発生する。

## 残る限界

- **記録簿は陳腐化検査の対象外である。** 登録簿・棚卸し表とは異なり、記録簿の
  各行は「その日時に実測した値」という過去の事実の記録であり、後から実体と
  食い違って「古くなる」性質の主張ではない。したがって機械的な陳腐化検査は
  設けていない。ただし、記録簿への追記自体が行われなければ、実行契機
  （文脈節で確認したCI経路）が機能し続けていても、その事実が記録簿には
  反映されないまま放置されうる。この追記漏れを検出する仕組みは本ADRの
  範囲外である。
- **CI経路（pytestのデフォルト探索）が明示的な設定ではなく副作用的に成立
  している点は、機械的な検査で守られるようになった。** `tests/test_check_scanner_registry.py`に
  `test_verify_sh_pytest_invocation_unrestricted`（`scripts/verify.sh`の
  pytest呼び出しが対象範囲を限定していないことを確認する）と
  `test_pytest_collects_scan_path_gate_test`（pytestのデフォルト探索が実際に
  `test_repo_registry_matches_current_scan`を収集することを、
  `--collect-only`のサブプロセス実行で確認する）を追加した（Refs #286）。
  `tests/`配下に`test_*.py`という命名規則のファイルを置けば自動的に収集
  される、というpytestの既定動作への依存という構造自体は変わっていないが、
  その依存が壊れた場合は、この2検査がpytestの失敗として検出する。
  **検査が守れる範囲**: pytest.ini等の追加によるtestpaths制限、
  `scripts/verify.sh`のpytest呼び出し行への対象範囲限定フラグの追加、
  対象テストの改名・削除・収集除外マーカーの付与など、収集経路を壊す
  変更全般。**検査が守れない範囲**: (1) 検査自体がpytestの一部として動く
  ため、pytest実行系そのものが起動できなくなった場合は本検査自体も動かない。
  (2) `.github/workflows/verify.yml`が`verify.sh`の呼び出し自体をやめた
  場合は、本検査の範囲外（`.github/workflows/**`はADR-003によりAIが編集
  しない対象であり、本検査もワークフロー自体は検査しない）。(3) 対象テスト
  （`test_repo_registry_matches_current_scan`）自身の判定ロジックが誤って
  いても、収集さえされていれば本検査は通る。判定ロジックの正しさはその
  テスト自身の責任であり、本検査の範囲外である。
- **記録簿の値は、走査対象範囲（git追跡ファイル全件）の変化にも影響される。**
  ファイル数が増減すれば検出総件数も変動しうるため、増減だけを見て「偽陽性が
  増えた／減った」と単純に解釈できるとは限らない。
