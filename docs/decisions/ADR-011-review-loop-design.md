# ADR-011: レビューループ（実行役×監査役の別プロセス連結）の設計

- 日付：2026-08-26
- 状態：採用

## 背景

現在、Claude Code（実行役）の出力を人間がコピーして別のClaude（監査役）に貼り、
その出力を人間がコピーして実行役へ戻す、という運用になっている。人間が判断せず
テキストを右から左へ運ぶだけの中継として介在している構造的な欠落を、
`docs/ai_loop_state/2026-08-26.md`「§3-I. 人間が実行役と指示役の間の伝送路になって
いる」として記録した。これは`ai-loop-implementation-plan_v8.md`（AI Loop実装計画書）
が一度もモデル化していない領域であり、本ADRはこの伝送路を廃したレビューループの
設計を、実測に基づいて決定する。

実測は`docs/ai_loop_state/audit_experiment_2026-08-26.md`（監査役の検出力実験）と
`ERRORS.md`「`--max-budget-usd`は支出の上限ではなく、ターン境界での打ち切りであり、
上限を大きく超えて課金されうる」の2箇所で行った。

## 決定

1. 人間を「伝送路」から外し、「承認者」として残す。コピー＆ペーストによる中継を
   廃止し、PR作成・マージ・mainへのpush・Issue作成の承認は人間が担う
   （ADR-001は変更しない）
2. 実行役と監査役を別プロセスとする。実行役はSonnet、監査役はOpus
3. 監査役は毎回新規セッションとし、`--resume`を使わない
4. 受け渡しはファイルとする。パイプは使わない。保存先は
   `~/comic_checker-agent-notes/review_loop/<session>/round_N/`とし、
   1ラウンドにつきinstruction / report / review / verdictの4ファイルを残す
5. 監査役の権限はWrite / Edit / NotebookEdit / Bashをdeny、
   Read / Glob / Grepは許可とする
6. 監査役の出力形式はVERDICT / CONTRADICTIONS / FOLLOWUPSの3節とし、
   FOLLOWUPSの内容をVERDICTに影響させない
7. VERDICTはAPPROVE_CONTINUE / REVISE / HALT_NEEDS_HUMAN / DONEの4値
8. 段階0（毎ラウンド人間が1キーで承認）から開始する。段階1（条件付き自動継続）
   以降へ進むかは、段階0の実測を見てから別途決定する
9. 停止条件を3種置く: ラウンド上限 / 同一VERDICTの2連続 / no-opハッシュ不変
10. 支出の制御は`--max-budget-usd`に依存せず、ラウンド上限と`--max-turns`で行う

## 各決定の根拠

決定5・6・8・10には、それぞれ対応する実測がある。

**決定5（監査役にRead/Glob/Grepを許可する）**: 「監査役の検出力実験」の
「交絡の切り分け」条件で、Read/Glob/Grepを完全に断っても偽装2点の検出結果は
変わらなかった（アクセス許可時と同じくREVISE・両偽装とも検出）。一方、コストは
アクセスを許可した条件の方が約3倍高かった（同記録「結果」表を参照）。それでも
アクセスを許可するのは、報告の独立検証を可能にするためである。今回の実験の
サンプルは2組（R-true・R-false）のみであり、**アクセスが不要であるという
一般化はしない**。報告書がdiff外のファイルに言及する場合は結果が変わりうる旨は
同記録「限界」節に明記した。

**決定6（VERDICT/CONTRADICTIONS/FOLLOWUPSの3節分離）**: 同記録「結果」表の
とおり、旧形式（VERDICT+FINDINGSの1本立て）ではR-true（虚偽の無い報告）も
REVISEと判定され、APPROVE_CONTINUEが一度も出なかった。3節に分離した新形式
では、6回の実行中3回すべて（R-trueの3反復）で正しくAPPROVE_CONTINUEになった
（誤検出は全条件・全6回で0件）。品質上の改善提案（FOLLOWUPS）が合否判定
（VERDICT）を汚染しない設計が、実測でその効果を示した。

**決定8（段階0から開始する）**: `docs/ai_loop_state/2026-08-26.md`
「§3-A. ループ本体が事実上停止している」が記録するとおり、`work_loop.sh`は
計画書のサンプルを大きく超える完成度で作り込まれながら、実運用はPR1件で
停止し、最後の実行結果自体が`is_error=true`のまま`success`と記録される矛盾を
抱えていた。作り込みの精度と実運用での安定性は別の問題であり、無人運転から
始めない理由になっている。

**決定10（`--max-budget-usd`に依存しない）**: `ERRORS.md`「`--max-budget-usd`は
支出の上限ではなく、ターン境界での打ち切りであり、上限を大きく超えて課金され
うる」の実測により、`--max-budget-usd 0.01`指定でも`total_cost_usd`が上限の
約8.3倍まで達することを確認した。このフラグは「予算超過後は次のターンへ
進まない」形でのみ機能し、1ターン内の支出そのものは止められない。したがって
支出の実効的な歯止めには、ラウンド数と`--max-turns`という、ターン単位で
機械的に数えられる上限を用いる。

## 却下した案

### 監査役のアクセスを完全に断つ

コストは下がるが（実測で約1/3）、報告がdiff外に言及した場合に独立検証が
できない。決定5参照。

### 単一プロセスで自己レビューさせる

自作物を自分で検査する構造であり、本プロジェクトが繰り返し失敗として記録して
きたパターンに該当する（`ai-loop-implementation-plan_v8.md`が指摘する「自己
採点のループはゲートではない」、および`ERRORS.md`「テストが通ることは、その
テストが何かを守っている証拠にならない」と同型の問題）。

### 段階2（無人運転）から着手する

`work_loop.sh`が高い完成度で作られながら実運用1件で停止した前例があるため
（`docs/ai_loop_state/2026-08-26.md`「§3-A」参照）、最小構成での実運用を
先行させる。

## 未決定として明示する事項

- 監査役に読ませる文脈の選定（`ERRORS.md`全文は114KBあり毎ラウンド投入は
  非現実的）
- 段階1へ進む条件
- `review_loop`と`work_loop.sh`の関係（統合するか併存させるか）
