# ADR-003: CI定義（`.github/workflows/**`）をAIの書き込み対象から外す

- 日付：2026-08-03
- 状態：採用

## 背景

`.claude/settings.json` は当初から `Edit(.github/workflows/**)` /
`Write(.github/workflows/**)` を `deny` していたが、実際にAIがそこへ書こうとした事例が
無く、**意図した制約なのか、単に列挙されただけなのかが確認されていなかった**。

Phase 2（VERIFY Gate）の未達分 ―― `verify.sh` をPRで回すCI ―― を追加する作業で初めて
実地に当たり、`Write` ツールが次のように拒否されることを確認した。

```
Write(.github/workflows/verify.yml)
→ File is in a directory that is denied by your permission settings.
```

同時に、この `deny` は **Edit/Write ツールの経路しか塞げない**ことも
`.claude/settings.json` の `_note_deny_scope` に既に記録されている。`tee` やヒアドキュメント
によるシェル経由の書き込みは通る。したがってこの `deny` は「不可能にする仕組み」ではなく
**「意図的な行為に変える仕組み」**である（`.githooks/pre-push` が `--no-verify` で迂回できる
のと同じ性質。ADR-001「補足：`deny` は人間を縛らない」と同じ立場）。

実際にこの運用でCIを1本追加し、成立することを確認した。**AIが全文を提示 → 人間が
エディタで保存 → AIが `diff` で一致を確認 → AIが commit・push・PR作成 → AIがActionsの
実行結果を実測して報告**という手順で、`ci/verify-on-pr`（PR #69）が緑になっている
（`188 passed`・`VERIFY PASSED`、未実測だった `setup-python` の `_tkinter` 同梱も
`tkinter 8.6` として実測で確認できた）。手順は回る。

## 決定

`.github/workflows/**` の Edit/Write `deny` を維持する。**CI定義の変更は人間が自分の
エディタで行い、AIは内容の提案・`diff` による照合・commit・push・PR作成・実行結果の
報告までを担う。**

理由は**非対称性**である。CIはAIの成果物を検査する側であり、検査される側が検査の定義を
書き換えられる状態は、`verify.sh` を `deny` している理由（実装計画書 Phase 2 の
「自己採点で空回りする」を防ぐ）とまったく同じ構造で崩れる。`verify.sh` を守っておいて、
それを呼び出すワークフローを自由に書き換えられるなら、守っている意味がない ――
`Run VERIFY Gate` ステップを消す、`continue-on-error: true` を足す、`on:` から
`pull_request` を外す、のいずれでも無効化できる。

## 却下した案

### 1. `deny` を外す

CI変更のたびに人間の手作業が発生するコストは避けられるが、上記の非対称性が崩れる。
CI定義の変更頻度は高くない（今回が2本目。次はPython 3.8ジョブの追加を予定）ため、
コストは小さい。

### 2. シェル経由（`tee`）で書く運用にする

技術的には可能であり、`_note_deny_scope` もそれを明記している。しかし**`deny` を回避する
手順を通常運用にすると、`deny` の意味が「AIが回避手順を知っているかどうか」に依存する**。
ADR-001 の `--no-verify` と同じ扱いとし、**回避は例外時の非常口として残すが、平常運用には
しない**。

### 3. `.github/workflows` 配下にAI用の別ディレクトリを作る

GitHub Actions はワークフローを `.github/workflows/` 直下からしか読まないため成立しない。

## 受け入れたリスク

1. **シェル経由の書き込みは塞げない。** AIが `tee` や `python` で書けば `deny` は効かない。
   許可プロンプトが出るので人間が気づけることに依存している（ADR-001 の
   「受け入れたリスク」と同じ構造）。
2. **CI変更のたびに人間の手作業が入る。** Python 3.8 ジョブの追加でも同じ手順が必要になる。
3. **AIが提示した内容を人間が貼り付ける際の写し間違い。** PR #69 では `diff` で全文を
   突き合わせ、末尾改行の欠落1件を検出した（内容自体は87行すべて一致）。
   **この `diff` 照合を手順に含めることで軽減する。目視で済ませない。**
4. **GitHub の Web UI からは誰でもワークフローを編集できる。** この `deny` はローカルの
   Claude Code セッションにしか効かない。

## 今後CI定義を変えるときの手順

1. AIが変更後の全文（または該当箇所）を提示する
2. 人間がエディタで保存する
3. **AIが `diff` で提示内容と一致することを確認して報告する**（目視で済ませない。
   PR #69 の末尾改行はこれで見つかった）
4. AIが commit → push → PR作成
5. **AIがActionsの実行結果を実測して報告する。** 緑・赤どちらでもログを引用し、
   推測で「通ったはず」と書かない（`ERRORS.md`「実行したが観測していない値も、報告に
   書いてはいけない」と同じ規律）
6. マージは人間が GitHub GUI で行う（ADR-001 の運用を維持）

## この決定が縛るもの

- **CIをAIに書かせたくなったとき**は、この非対称性を崩す判断になる。ADRを更新すること
- **将来 AI Loop を GitHub Actions に載せる**場合、ループ自身のワークフロー定義もこの
  `deny` の対象である。ADR-001「受け入れたリスク」3（CIからのpushは pre-push では
  止められない）と併せて読むこと
