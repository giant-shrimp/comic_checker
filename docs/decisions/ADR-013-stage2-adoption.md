# ADR-013: 段階1の見直しと段階2（案A）の採用（ADR-012決定2・決定4をsupersede）

- 日付：2026-08-28
- 状態：採用
- **`docs/decisions/ADR-012-stage1-decision.md`決定2（段階0.5の採用）・決定4
  （段階2へ進む条件）をsupersedeする。決定1（案Cを採用しない）・決定3
  （FOLLOWUPS混入欠陥の修正）は有効なまま**

## 背景

ADR-012（`docs/decisions/ADR-012-stage1-decision.md`）決定2は、「段階1として
`VERDICT`が`REVISE`のときのみ自動で次ラウンドへ進む『段階0.5』を採用する」
と決定した。この決定は「未決定として明示する事項」で自ら認めているとおり、
「`REVISE`時の挙動が未測定」という前提の上に立っていた。

その後の2回目試走（`docs/ai_loop_state/review_loop_trial2_2026-08-27.md`）は、
`REVISE`を誘発する構造として選定した題材（`docs/ai_loop_state/2026-08-26.md`
§3-Cの、本文と§5総評リストの2箇所に同じ主張が分散している構造）を使って、
意図的に`REVISE`が出るかを確かめる試走だった。結果は2ラウンドとも
`APPROVE_CONTINUE`だった。初回試走（`docs/ai_loop_state/
review_loop_trial_2026-08-26.md`、1ラウンド）と合わせて、**これまでの合計3
ラウンドで`REVISE`は一度も出ていない。**

さらに2回目試走は、ADR-012決定2が想定していなかった別の事実を明らかにした。

- `APPROVE_CONTINUE`が2ラウンド連続し、停止条件（ADR-011決定9）の「同一
  VERDICTが2ラウンド連続」（`exit 11`）で強制終了した
- round_2の`diff.txt`はround_1の`diff.txt`と**完全一致**しており、round_2では
  新規の変更が一切行われず、round_1の結果をそのまま維持しただけだった
  （`docs/ai_loop_state/review_loop_trial2_2026-08-27.md`「8.」参照）
- `review_loop.sh`の停止条件チェックはコード上「ラウンド上限→同一VERDICT2
  連続→no-opハッシュ不変」の順に独立した`if`文として並んでおり、round_2では
  no-opハッシュ不変（`exit 12`）の条件も成立していたはずだが、同一VERDICTの
  チェック（`exit 11`）が先に評価されるため、そちらが先に発火した
- 監査役の出力形式遵守（`scripts/review_audit_prompt.md`の仕様外見出し
  「検証した根拠（矛盾なしの裏付け）」の有無）が、round_1（無し）と
  round_2（有り）でセッション内でも不安定だった。`build_next_instruction()`
  （ADR-012決定3）は`FOLLOWUPS:`行のパターンマッチに依存しているため、この
  種の仕様外コンテンツはCONTRADICTIONS節の内側に出現する限り除去されない

本ADRは、これらの実測に基づいて段階1の方針を見直し、段階2（案A：起案役の
新設）を採用する。

**本ADRの位置づけ**: 本ADRは、これを含むPRをユーザがマージした時点で確定
する（ADR-012と同じ扱い）。

## 決定

1. **ADR-012決定2（段階0.5）をsupersedeし、実装しない。**
2. **案A（起案役の新設）を採用する。**
3. **停止条件の評価順を見直す。** `scripts/review_loop.sh`の停止条件チェック
   順序を、no-opハッシュ不変（`exit 12`）を同一VERDICT2連続（`exit 11`）より
   **先に**評価する順序へ変更する。**実装は本ADRに含めず、別タスクとする。**
4. **`build_next_instruction()`の`FOLLOWUPS:`依存に対処する。** 次ラウンド
   instructionの抽出範囲を、`FOLLOWUPS:`行より前を丸ごと残す現在の方式から、
   CONTRADICTIONS節の中身を箇条書き行（および「なし」相当の記述）に限定する
   方式へ変更する方向で対処する。**実装は本ADRに含めず、別タスクとする。**
5. **ADR-012決定4（累計10ラウンド）をsupersedeする。** 案Aを決定2で採用した
   ため、「案Aへ進む条件」という数値条件そのものが不要になる。

## 各決定の根拠

**決定1（段階0.5をsupersedeし実装しない）**: 実測に基づく。

- 初回試走（1ラウンド）・2回目試走（2ラウンド）とも`VERDICT`は
  `APPROVE_CONTINUE`のみで、**合計3ラウンドで`REVISE`は一度も出ていない**
- 2回目試走は`REVISE`を誘発する構造の題材を**意図して選定した**うえで、
  それでも出なかった（`docs/ai_loop_state/stage1_options_2026-08-27.md`・
  `docs/ai_loop_state/review_loop_trial2_2026-08-27.md`「7.」参照。実行役は
  題材が仕込んだ2箇所の見落としリスクを両方とも修正していた）
- 実行役が誠実に作業する限り、報告と実態の矛盾（`REVISE`の原因）は生じ
  にくく、`REVISE`は稀な事象と見られる

**限界（過度な一般化をしないこと）**: **3ラウンドは`REVISE`の発生率を推定
できる標本数ではない。** 「稀である」は暫定的な見立てであり、「起きない」
と断定しない。段階0.5をsupersedeするのは、それが前提としていた「`REVISE`
時に自動継続する」という機構自体が、以下の決定2が示す実測上のボトルネック
（`APPROVE_CONTINUE`時に次の指示が無いこと）を解決しないと判断したためで
あり、「`REVISE`が起きないから不要」という理由ではない。

**決定2（案Aを採用する）**: 2回目試走の実測から、ボトルネックの所在を
次のように特定できる。

- `APPROVE_CONTINUE`が2ラウンド連続し、`exit 11`で停止した
- round_2の`diff.txt`はround_1と完全一致、新規変更ゼロ
- つまり、**「作業が完了した後に次の指示が無い」ことがループの停止要因で
  あり、`REVISE`時の自動継続（段階0.5）ではそこを埋められない。** 段階0.5は
  `REVISE`（矛盾がある）ときにだけ自動継続する設計だが、今回の3ラウンド
  すべてで実際に起きたのは`APPROVE_CONTINUE`（矛盾が無い）状態でループが
  止まる、という段階0.5が対処範囲に含めていない事象だった

案Aは、起案役が次のinstructionを生成することで、このボトルネックを直接
埋める設計である。ADR-012決定2が案Aを見送った主根拠（「段階0の実測が
まだ1ラウンド1セッション分しかない」）は、初回・2回目の試走を経て
実測が3ラウンド2セッション分に増えたことで、一定程度解消されたと判断
する。

**決定3（停止条件の評価順）**: 2回目試走で、no-opハッシュ不変の条件が
成立していたと推定される状況で、同一VERDICT2連続の条件が先に発火し、
「round_2で実際は何も変更されていなかった」という、より根本的な事実が
`exit 11`のメッセージだけからは読み取れなかった（`diff round_1/diff.txt
round_2/diff.txt`を実行して初めて判明した）。no-opは「ループが実質的に
何もしていない」という、`docs/ai_loop_state/2026-08-26.md`「§3-A」が
`work_loop.sh`について記録した「静かに失敗するループ」と同型の、より
深刻な失敗モードである。したがって、根本原因に近いno-opハッシュ不変を
先に評価する順序へ変更し、診断情報としての精度を上げる。

却下した選択肢は「各決定の根拠」の後の「却下した案」節を参照。

**決定4（`FOLLOWUPS:`依存への対処）**: 2回目試走で観測された監査役の
出力形式不遵守（「検証した根拠」という仕様外見出し）は、`FOLLOWUPS:`より
前（CONTRADICTIONS節の内側）に出現したため、`build_next_instruction()`
（`FOLLOWUPS:`行だけを境界とする現在の実装）では除去されない。これは
ADR-012決定3が対処した「FOLLOWUPS節そのものの混入」とは異なる、
「CONTRADICTIONS節を偽装した仕様外コンテンツの混入」という新しい種類の
問題である。プロンプト側の指示をさらに厳格化するだけでは、本プロジェクト
が繰り返し確認してきたとおり「ルールは確率的、権限・機械的な抽出は
決定論的」という原則に反し、確実な対処にならない。したがって、抽出
ロジック側でCONTRADICTIONS節の中身を箇条書き行に限定する方向で対処する。

**限界**: この対処が監査役の出力を完全に無害化する保証は無い（監査役が
箇条書き形式自体を守らない可能性は残る）。実装の詳細（正規表現・抽出
条件の具体形）は本ADRでは決めず、別タスクで設計・実測する。

**決定5（ADR-012決定4のsupersede）**: 決定2で案Aを採用したため、「案Aへ
進む条件（累計10ラウンド）」という条件そのものが不要になる。参考として、
これまでの実測コストを記録しておく。

- 初回試走: `0.5353943` USD/ラウンド
- 2回目試走round_1: `0.4726194` USD
- 2回目試走round_2: `0.3707714` USD

これらは今後、案Aの実装によるコスト増分を検証する際のベースラインとして
使える。

## 却下した案

### 決定3で「現状維持」を選ばない

2回目試走で、根本原因（no-op）が停止条件のメッセージから読み取れなかった
という実害が既に1件観測されている。現状維持はこの実害をそのまま残す。

### 決定3で「`exit 12`の条件そのものを見直す（同一VERDICTとの複合判定にする）」を選ばない

両条件が同時に成立した場合の理由を1つのメッセージに統合する設計も考えられ
るが、既存の3停止条件がそれぞれ独立した`if`文であるという単純な構造
（`scripts/review_loop.sh`）を崩すことになり、実装・テストの複雑さが増す。
評価順の入れ替えだけで診断精度を改善できるなら、まずそちらを試すのが
最小の変更である。複合判定が必要かどうかは、順序変更後の実測を見てから
再検討する。

### 決定4でプロンプト側の指示強化のみで対処する

`scripts/review_audit_prompt.md`に「CONTRADICTIONS節には指定した箇条書き
以外を含めるな」という文言を追加するだけの対処も検討したが、本プロジェクト
の一貫した方針（規則は`CLAUDE.md`側、機械的に検査できるものは`verify.sh`側
という区別、`ai-loop-implementation-plan_v8.md`が指摘する「ルールと権限は
別物」）に照らし、プロンプトの指示だけでは確率的にしか効かないと判断した。
抽出ロジック側の対処（決定4本体）と併用することは妨げない。

## 未決定として明示する事項

- 起案役の実装設計（モデル・権限プロファイル・プロンプトの具体的な文面）は
  本ADRでは決めない
- 起案役のコストは未実測。`stage1_options_2026-08-27.md`の約42%増という
  見積りは、「起案役はopus・5ターン」「コストはターン数に比例する」という
  2つの未検証の仮定に依存している（同文書「5.」参照）
- `REVISE`は依然未測定（決定1の限界を参照）
- 停止条件`exit 10`（ラウンド上限）・`exit 12`（no-opハッシュ不変、単独での
  発火）・`exit 2`（実行役の呼び出し失敗）・`exit 13`（監査役の呼び出しが
  成立しなかった場合）は、いずれもこれまでの試走で未発火である
