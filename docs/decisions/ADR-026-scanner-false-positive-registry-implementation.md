# ADR-026: 走査器の偽陽性事前登録簿（ADR-024決定1）の実装

- 日付：2026-09-20
- 状態：採用

## 文脈

ADR-024（`docs/decisions/ADR-024-scanner-false-positive-registry.md`）は、
走査器（`scripts/check_no_personal_info.py`）の偽陽性を事前登録簿で抑制する
方式を決定し（決定1）、実装は別途とした。設計要件は次の4点だった。

- 登録簿はファイルと検出行の対応を記録する文書とし、走査器本体は変更しない。
- 同定は行番号に依存しない手段で行う（ファイルの追記・剪定で行がずれても
  対応関係を追跡できる必要がある）。
- 登録簿に無い新規の検出は、これまでどおり人間が判断できるよう機械的に
  検出する（登録簿は抑制するだけで、見逃しを作らない）。
- 登録簿自体の陳腐化（登録されているが実際にはもう検出されない項目）を
  検査する手段を持つ。これは棚卸し表の陳腐化検査（ADR-025）と同じ構造の
  問題である。

本ADRは、この4要件を満たす実装を行ったことを記録する。あわせてIssue #271
（敬称型の誤検出）を、走査器のパターン変更ではなく本登録簿によって解消する。

**実測（2026-09-20、本ADR作成のために実行）**: 全git追跡ファイルへ走査器を
（ファイルへ書き出さず）独立にかけたところ、検出のあったファイル数51・
検出総件数798・型別内訳はhome-path型25・email型11・honorific型762で、
2026-09-18の実測値と完全に一致した（差分0）。内容が同一の行が複数箇所に
出現する場合をハッシュで集約すると、一意な（ファイル, ハッシュ）の組は793件
（home-path型24・email型11・honorific型758）だった。

## 決定

1. **登録簿を`docs/scanner_false_positive_registry.md`に作成した。** 各行は
   ファイルパス・ハッシュ・型・理由の4項目を持つ表とし、行番号は持たない。
2. **同定はSHA-256ハッシュで行う。** 検出された行の内容全体をSHA-256で
   ハッシュ化し、先頭16桁（64ビット）に切り詰めた値を使う。
3. **抑制層を`scripts/check_scanner_registry.sh`として実装した。** 走査器を
   Python APIとして呼び出すだけで、走査器のファイル自体は変更していない。
   未登録検出・陳腐化登録のいずれも非ゼロ終了とし、出力には検出行の本文を
   含めない（ファイルパス・ハッシュ・型のみ）。実行権限は付与せず、
   `bash scripts/check_scanner_registry.sh`として呼ぶ運用とする。
4. **登録簿には、2026-09-20時点で確認された既知の偽陽性793件（ユニークな
   （ファイル, ハッシュ）単位）を登録した。** home-path型24件・email型11件は
   個別に真陽性でないことを確認した（後述）。honorific型758件は、Issue #271・
   ADR-024が確立した「本プロジェクトが実在の作品名を大量に扱う構造に由来する
   誤検出」という分類に基づき、クラス単位の偽陽性として登録した（個別の
   1行ずつの証跡は本ADRには残さない。理由は「限界」節を参照）。
5. **投稿前走査の標準手段を、生の走査器（`scripts/check_no_personal_info.py`）
   の直接呼び出しから、抑制層（`scripts/check_scanner_registry.sh`）へ
   切り替える。** 生の走査器は登録簿を一切参照しない構造（決定3が走査器
   自体を変更しないと定めたことの帰結）であるため、登録簿にどれだけ項目を
   追加しても、生の走査器の実行結果は変わらない。抑制層は内部で走査器を
   呼び出したうえで登録簿と突き合わせるため、対象ファイルに登録が無ければ
   生の走査器と同じ結果（検出があれば非ゼロ終了）になる。すなわち抑制層は
   生の走査器の**上位互換**であり、確認手段を1本化できる。
6. **抑制層の対象範囲に、git未追跡ファイル（`git ls-files --others
   --exclude-standard`）を、git追跡ファイル（`git ls-files`）に加えて含める。**
   新規に作成したファイルほど、まだ人の目やレビューを経ていないため投稿前
   走査が最も必要であり、追跡・未追跡を問わず対象にする必要があるため。
   `.gitignore`で除外されたファイルは対象に含めない（`--exclude-standard`が
   これを担う）。

## home-path型・email型の個別判断

- **home-path型（24件、ユニーク）**: 全件について、検出された値が
  `os.path.expanduser("~")`で実行時に取得した実ホームディレクトリの値と
  一致しないことを機械的に確認した（一致件数0）。内訳は次の3種。
  - 走査器自身のパターン定義（正規表現ソース）への自己ヒット1件
    （`scripts/check_no_personal_info.py`自身）。ADR-022が既に記録した
    自己ヒットの構造と同種。
  - 個人を特定しうる部分が既にプレースホルダ（`...`・`<user>`等）へ
    置換済みの記述2件（`docs/ai_loop_state/`・`docs/code_defects_2026-08/`
    配下の文書）。
  - テストフィクスチャの架空パス21件（`tests/test_check_no_personal_info.py`・
    `tests/test_gui_run.py`）。走査器自身のテストが、検出させるための
    架空パスを意図的に含む。
- **email型（11件、ユニーク）**: 全件が`tests/test_check_no_personal_info.py`・
  `tests/test_review_loop.py`のテストフィクスチャで、いずれもIETF予約ドメイン
  （`example.invalid`・`example.test`、RFC 2606）を使っている。実在のドメインに
  解決されない予約語であることが、偽陽性と判断する機械的な根拠である。

## ADR-025との関係（ハッシュ採用の判断の違い）

ADR-025は棚卸し表へのハッシュ列導入を却下した。しかし判断の理由は
「69行の表に新規列を1つ増やし、以後その列を維持し続けるコストが、既存の
見出し列を実体に同期させるコストより高い」ことであり、**棚卸し表には
見出し列という、ハッシュに依らない同定手段（ERRORS.mdの見出し行そのもの）が
既に存在した**ことが前提にある。

登録簿にはこれに相当する同定手段が無い。登録簿は走査器の検出行そのものを
記録する文書であり、検出行の内容（実在の個人名・作品名・敬称を含みうる）を
そのまま書けばADR-022の運用規約に違反する。したがって、登録簿における
同定手段は、内容を明かさずに内容の変化を検出できるハッシュ以外に選択肢が
ない。ADR-025とは前提条件（代替の同定手段の有無）が異なるため、同じ
「ハッシュ列は導入しない」という結論にはならない。

## 採らなかった案

- **行番号で同定する案**: 却下。ADR-024決定1の設計要件自体が「行番号だけに
  依存しない同定手段が要る」としており、ERRORS.mdの追記・剪定や、対象
  ファイル全般の編集で行番号は容易にずれる（ADR-025が別文書で既に実証した
  問題と同型）。
- **検出行の内容をそのまま登録簿に書く案**: 却下。ADR-022の運用規約
  （実在の作品名・敬称と同型の語彙・走査器のパターン定義そのものを
  文書に書かない）に反する。登録簿という文書自体が新たな漏洩経路に
  なりかねない。
- **走査器のパターンを絞り込み、既知の偽陽性を検出させない案**: 却下。
  ADR-017が既に「誤検出を減らす境界条件は実在人名の典型形も同時に除去する。
  誤検出と検出漏れがパターン側では分離できない」と結論づけている
  （ADR-024が踏襲）。本ADRもこの決定を覆さない。
- **完全なファイル内容のハッシュ（切り詰めない）を使う案**: 却下。
  登録簿1行あたりのハッシュ表記が64桁になり、793行の表の可読性を
  大きく損なう。本リポジトリの規模（ユニーク793件）では16桁（64ビット）で
  衝突確率は無視できる水準であり、桁数を伸ばす利益が可読性の代償に
  見合わない。

## 代償

- 登録簿は793行の表を持つ大きな文書になった。生成はpython3による機械的な
  ものであり手書きではないが、文書としての見通しやすさは、行数の少ない
  文書に比べて劣る。
- honorific型758件は、home-path型・email型のような個別の判断根拠を登録簿にも
  本ADRにも残していない。クラス単位（Issue #271・ADR-024が既に確立した
  「実在作品名の敬称字形」という構造的分類）での登録である。

## 残る限界

- **`.gitignore`で除外されたファイルは走査されない。** 決定6は追跡・未追跡の
  両方を対象にするが、`git ls-files --others --exclude-standard`は
  `.gitignore`に一致するファイルを対象から除く。走査対象をgit管理下に
  置かれた（追跡・未追跡を問わない）ファイルに限定しているためで、
  git管理外のファイル（例: ローカルの作業用ファイル）は本抑制層の対象外の
  ままである。
- **honorific型758件の個別検証は行っていない。** 該当ファイルの大半は
  マンガ作品名のコーパス・ラベリング用データ（`docs/holdout*_2026-08/`・
  `docs/regression_corpus_2026-08/`配下のJSON等）であり、走査器のテストと
  ソースコードの一部も含む。これらは実在の個人が私信としてやり取りする
  性質のファイルではないため、実在の個人名（作品名ではなく人物名）が
  紛れ込む可能性は構造的に低いと判断したが、758件すべてを1件ずつ確認しては
  いない。将来、これらのファイルに実在の人物名が敬称付きで追加された場合、
  その行の内容は現在の登録済みハッシュとは異なる値になるため「未登録検出」
  として機械的に検出される（ハッシュが内容に依存するため、内容が変われば
  自動的に登録簿の外に出る）。したがって当面のリスクは、今回登録した793件の
  中に既に個別確認していない真陽性が紛れている可能性に限られ、将来の新規
  混入は本登録簿の仕組みでカバーされる。
- **走査器自体の検出範囲外は、引き続き検出されない。** ADR-023が記録した
  「走査器はコミットのauthor / committerメタデータを見ない」という制約は、
  本ADRでは変わらない。登録簿はあくまで走査器の検出結果を後処理するもので
  あり、走査器の検出範囲そのものを広げるものではない。
- **登録簿自体の更新は引き続き人手に依存する。** 「未登録検出」「陳腐化登録」
  の報告を見て登録簿を編集する作業そのものは自動化していない。
- **走査器のテストは、走査器を作動させるフィクスチャを必要とするため、
  新しくテストを追加するたびにそのフィクスチャを登録簿に追加する必要が
  ある。** 走査器自身のテスト（`tests/test_check_no_personal_info.py`）・
  本登録簿の抑制層のテスト（`tests/test_check_scanner_registry.py`）は、
  いずれも走査器を実際に検出させるための架空のフィクスチャ（IETF予約
  ドメインを用いたメールアドレスの形等）を意図的に含む。これらは生の
  走査器に対しては恒久的に検出され続ける（決定5が定めた「生の走査器は
  登録簿を参照しない」という構造上、これは変わらない）。抑制層を投稿前
  走査の標準手段とすることで、登録済みのフィクスチャは通過するが、
  テストを新規追加した時点では、そのフィクスチャがまだ登録簿に無いため
  一時的に「未登録検出」として鳴る。この手順（新規テスト追加→検出→
  登録簿へ追加）は、テストを追加するたびに繰り返し必要になる運用上の
  帰結であり、自動化されていない。
- **フィクスチャの行を編集すると、登録簿のハッシュが陳腐化する。** ハッシュは
  検出行の内容そのものに依存するため、テストフィクスチャの文字列を1文字でも
  変更すると、登録簿の該当行は「陳腐化登録」として鳴るようになる。その際は
  登録簿のハッシュを、変更後の内容から再計算して更新する必要がある。これは
  棚卸し表の見出し列がERRORS.mdの見出し変更に追随する必要がある構造
  （ADR-025）と同型の維持コストである。
