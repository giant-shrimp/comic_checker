## 4. 判定手続き（論点2）

v4規則本文（`step98_a_labeling_rules_v4.json`）の `apply_order` を実際に読み出した
結果（後掲コマンドと出力を参照），適用順序は **R1'(1) → R3'(2) → R4(3) → R5(4) →
R2(5) → R6(6)** であり，本項に記載する順序と一致することを確認した。

擬似コード:

```
rules_in_order = [R1', R3', R4, R5, R2, R6]   # apply_order 昇順

trace = []
applied_rule = "なし"
for rule in rules_in_order:
    matched = evaluate(rule.condition, extract, wikitext)  # rule本文の条件をそのまま評価
    trace.append({rule_id: rule.rule_id, matched: matched})
    if matched:
        applied_rule = rule.rule_id
        expected_status = rule.result に従って決定する
        # （R3'のように「適用対象外の場合は元のラベルを維持する」という
        #   条件内分岐を持つ規則は，rule本文の result 記述をそのまま適用する）
        break
if applied_rule == "なし":
    # いずれの規則にも該当しない場合は，通常の読解判断（extract本文の直接的な記述等）
    # によりexpected_statusを決定する
    expected_status = 通常の読解による判断
```

- 評価は `apply_order` の昇順で行い，最初に条件を満たした規則の `result` を採用した
  時点で評価を打ち切る（それ以降の規則は評価しない）。`rule_trace`（§5参照）には，
  実際に評価した規則のみが記録される。
- R4の `priority_note`（「休載中または再開不定の記述がある場合，本文中の他の継続表現
  よりR4の判定を優先する」）は，**R4自身の条件判定（`matched` の算出）の中で適用される
  読解上の注意**であり，「規則間のどちらを先に評価するか」という `apply_order` のレイヤー
  とは別レイヤーである。`apply_order` はR1'→R3'→R4→R5→R2→R6という規則同士の評価順序を
  定め，`priority_note` はR4という個々の規則の条件を読解する際に，本文中の複数の継続/
  終了表現のうちどれを優先して読むかを定める。両者を混同しない。
- いずれの規則にも該当しない場合，`applied_rule` は文字列「なし」とし，通常の読解判断
  （extract本文の直接的な記述等）によりstatusを決定する。

## 5. 出力スキーマ（論点3・4）

出力先: `docs/holdout2_measurement_2026-08/holdout2_labels_v4.json`
（上位事前登録§5が定める出力先と同一）。

`labels[]` の各要素のフィールド定義:

| フィールド名 | 型 | 取りうる値 |
|---|---|---|
| `title` | string | 対象119件のタイトル文字列 |
| `expected_status` | string | 「連載中」／「完結」／「判定不能」 |
| `applied_rule` | string | 「R1'」／「R3'」／「R4」／「R5」／「R2」／「R6」／「なし」 |
| `evidence_summary` | string | 判断根拠を要約した自由記述文 |
| `confused` | boolean | `true` / `false`（§6の手続きに従い判定者が自己申告） |
| `rule_trace` | array of object | 下記参照 |

既存5フィールド（`title` / `expected_status` / `applied_rule` / `evidence_summary` /
`confused`）は第2回ラベル（`holdout2_labels_auto.json`）と名称・型・意味を同一に保つ。

**追加フィールド `rule_trace` の仕様**（判定トレース）:

- 型: オブジェクトの配列。配列の各要素は `{"rule_id": string, "matched": boolean}`。
- 記録粒度: **規則単位**（R1'・R3'・R4・R5・R2・R6のいずれか）。各規則の条件内部の
  サブ条件（例: R1'の「is_novel_primary」「漫画/コミカライズ等の不出現」
  「infobox終了系フィールド非null」の3小条件）はそれぞれ独立フィールドとしては記録
  しない。理由: サブ条件単位の記録は規則本文の記述形式（自然文の条件文）を機械的に
  分解する追加作業を要し，本文書が定める手続きの範囲を超える。規則単位の記録でも
  「どの規則を評価し，どこで該当したか／しなかったか」という論点3が求める判定トレース
  としては十分である。
- 記録範囲: `apply_order` 昇順で実際に評価した規則のみを，評価した順に配列へ追加する。
  最初に `matched: true` となった規則が配列の最後の要素になり，それ以降の規則
  （`apply_order` がより大きい規則）は評価しないため配列に含まれない。いずれの規則にも
  該当しなかった場合は，R1'からR6までの6要素全てが `matched: false` として記録される。
- 例（R4で該当した場合）:
  `[{"rule_id": "R1'", "matched": false}, {"rule_id": "R3'", "matched": false}, {"rule_id": "R4", "matched": true}]`
- 例（いずれにも該当しなかった場合）:
  `[{"rule_id": "R1'", "matched": false}, {"rule_id": "R3'", "matched": false}, {"rule_id": "R4", "matched": false}, {"rule_id": "R5", "matched": false}, {"rule_id": "R2", "matched": false}, {"rule_id": "R6", "matched": false}]`

`applied_rule` の「該当なし」は文字列「なし」とする（論点4，第2回ラベルの表記を踏襲）。

## 7. 作業分割と再開可能性（論点5）

**背景**: 第2回ラベル付け（`holdout2_labels_auto.json`）では，作業途中でコンテキスト
圧縮が発生し，1〜90件目の個別判断根拠が失われたため，全119件の読解をやり直す事態と
なった（`holdout2_labels_auto.json` の `process_note`，詳細は
`relabel_consistency_finding.md`）。v4再ラベル付けでは，この種の事態が起きても
やり直し範囲を最小化できるよう，区切りごとに中間保存する。

- **分割単位**: 30件区切り。区間は 1–30 / 31–60 / 61–90 / 91–119 の4区間とする
  （最終区間のみ29件）。
- **中間保存ファイル名**: `docs/holdout2_measurement_2026-08/holdout2_labels_v4_partial_{開始}-{終了}.json`
  とする（例: `holdout2_labels_v4_partial_1-30.json`，
  `holdout2_labels_v4_partial_91-119.json`）。各ファイルのトップレベル構造は最終成果物
  `holdout2_labels_v4.json` の部分集合（当該区間の `labels[]` のみを含む）とする。
- **再開手順**:
  1. 作業再開時，`docs/holdout2_measurement_2026-08/` に存在する
     `holdout2_labels_v4_partial_*.json` を列挙し，保存済みの区間を確認する。
  2. 保存済みの最終区間（例: `1-30` まで保存済みなら）の直後の区間（`31-60`）から
     判定を再開する。
  3. 保存済みの区間ファイルは読み取り専用として扱い，内容を書き換えたり再判定したり
     しない。既に保存された区間の項目を判定し直すのは，全区間の保存後に発見された
     手続き上の誤り（例: 規則の読み違え）を修正する場合に限り，その場合は本文書とは
     別に修正の経緯を記録する。
  4. 全4区間の保存が完了した時点で，4ファイルを結合して
     `docs/holdout2_measurement_2026-08/holdout2_labels_v4.json` を生成する。
- **前区間を再判定しないことの担保**: 保存済み区間ファイルの存在自体が「この区間は
  判定完了済み」の記録として機能する。再開時はステップ1の区間ファイル列挙によって
  完了済み区間を機械的に確認できるため，判定者の記憶や申告に依存しない。

## 9. 本事前登録で予測を行うか否か

本文書は手続きの事前登録であり，新たな予測値は**追加しない**。

理由: 上位事前登録 `prereg_rules_v4.md` §7が既に，再スポットチェック20件における一致件数
の点予測（17/20）・判定基準（kの算出方法・確定タイミング・不一致件数>kという判定式）・
追加の歯止め（confused件数30件超で上位事前登録§8の失敗条件を適用）を固定している。本文書が扱う
119件の再ラベル付け手続き自体（盲検条件・判定手続き・出力スキーマ・作業分割）について，
結果に関する新たな数値予測（例: v4適用でstatusが変化する件数の予測，confused件数の
予測等）を本文書に追加すると，予測値の管理主体が上位事前登録と本文書の2箇所に分散し，
どちらが優先するかという二重管理の懸念が生じる。上位事前登録§7(c)は，confused件数の
具体的な数値（k）についても「本事前登録の時点で定めることはできない」として，値そのもの
ではなく算出方法・確定タイミング・判定式のみを固定する設計を既に採っている。本文書も
同じ考え方を踏襲し，手続きの固定に限定して数値予測は行わない。
