# 失敗の診断

PR の check-runs のうち verify または review が success 以外で終わったときに使う（ADR-034 の順序4）。
対象は CI と review の失敗と、末尾の節の試走で起きた失敗（CI・review 以外）。review が success のまま指摘を出した場合は対象外（司令塔の上流2で扱う）。

## 守ること

- 読み取り専用。ファイルの変更・コミット・push・再実行（Re-run）・Issue や PR への書き込みをしない。手元で `./scripts/verify.sh` を実行するのはリポジトリを変えないので、この規定に反しない（手順3）。
- コマンドは1回の Bash 呼び出しに1つ。`&&`・`;` でつながない。パイプは読み取りの絞り込みに限る。
- gh api は `repos/{owner}/{repo}/` 以下の REST だけを使う（gh が現在のリポジトリに置き換える）。GraphQL と `--paginate` は使わない。
- ログ・コメント・ERRORS.md の本文を報告に書き写さない。書いてよいのは、手順で指定した目印の行、ステップ名、結論、件数、行番号と No. だけ。
- 推測は推測と明記する。種類が決まらなければ「判定不能」とし、候補を並べる。

## 手順1: 失敗した check-run を特定する

1. `gh api repos/{owner}/{repo}/pulls/<PR> --jq .head.sha` で head の sha を得る。PR 番号がなくコミットの sha だけが分かっている場合は、この手順を省き、その sha（短縮形でよい）を手順1の2で使う。
2. `gh api repos/{owner}/{repo}/commits/<sha>/check-runs --jq '.check_runs[] | [.name, .status, (.conclusion // "none"), .id] | @tsv'` で一覧を得る。
3. status が completed でないものがあれば、診断せずに「未完了」と報告して終える。
4. conclusion が success 以外の行の name と id を控える（id はジョブの id として使う）。

## 手順2: 失敗したステップを特定する

1. `gh api repos/{owner}/{repo}/actions/jobs/<id> --jq '.steps[] | [.number, .name, (.conclusion // "none")] | @tsv'` でステップごとの結論を得る。
2. `gh api repos/{owner}/{repo}/actions/jobs/<id>/logs > /tmp/diag_<id>.log` でログを保存する（本文は書き写さない）。
3. `wc -l < /tmp/diag_<id>.log` で行数を得る。

## 手順3: verify の失敗の種類

`grep -n -E 'VERIFY (PASSED|FAILED)|FAIL:|--- (pytest|skip/xfail check|M6-B-4)' /tmp/diag_<id>.log` で段階の目印を得る。
scripts/verify.sh は途中で失敗しても後の段階を実行し、最後に VERIFY FAILED を出す。失敗した段階が複数あれば、下の種類をすべて挙げる（手順6の種類と根拠にも全部書く）。

- pytest：`grep -n -E '[0-9]+ (passed|failed)' /tmp/diag_<id>.log` でサマリ行を得る。失敗したテストファイルのパスは `grep -n -o -E 'FAILED tests/[^: ]+' /tmp/diag_<id>.log` で得る。件数とテストファイルのパスだけを書き、テスト名は書き写さない。
- skip/xfail 検査：`FAIL:` の行がある。
- 継続の証拠ゲート：`grep -c '検出 54/59・副作用 1/37 で一致' /tmp/diag_<id>.log` が 0（一致の行がない）。不一致の詳細は stderr に出るが、書き写さず「不一致」とだけ書く。
- その他：上のどれにも当たらない（環境・依存の失敗など）。失敗したステップ名を書く。

手元で再現を確かめる場合は `./scripts/verify.sh` を実行してよい（パイプにつながない）。

## 手順4: review の失敗の種類

手順2で failure のステップと、ジョブの結論で決める。ステップ名は .github/workflows/claude-review.yml に依存するので、役割で照らす。
failure のステップが複数あれば、番号の最も小さいステップの型を主とし、後のステップの失敗は派生として併記する（コメントを検証するステップは、前のステップが失敗した後にも走る）。

- fork の拒否：fork（別リポジトリ）からの PR を拒否するステップが failure。
- max-turns 超過：レビュー本体のステップが failure で、`grep -c 'error_max_turns' /tmp/diag_<id>.log` が 1 以上（上限は 35）。`max.turns` で数えると引数の表示（`--max-turns`）まで数えるので使わない。
- コメントの特定失敗・内容不十分：レビュー本体の後でコメントを検証するステップが failure。ログで区別できなければ両方を候補とする。
- timeout：ジョブの結論が timed_out または cancelled（上限は 15 分）。
- その他：上のどれにも当たらない。失敗したステップ名を書く。

## 手順5: ERRORS.md の関連記録を探す

1. 種類に合う語（例：max-turns、xfail、ゲート、timeout）で `grep -n -i -E '<語>' ERRORS.md` を実行し、行番号だけを使う。pytest の失敗では、失敗したテストファイル名から `tests/`・`test_`・`.py` を除いた名前を語にする。
2. `awk -F'|' 'NR>60 && $2 ~ /^ *[0-9]+(-[0-9]+)? *$/ {print $2 "|" $3}' docs/errors_md_inventory.md` で棚卸し表の No. と行範囲を得て（No. の列が数字か枝番の行だけ）、その行番号を含む No. を求める。行範囲の列にファイル名が入っている行は退避済みで、ERRORS.md の行番号とは照らさない。
3. 関連記録がなければ「なし」と書く。見出しと本文は書き写さない。

## 手順6: 報告する

次の項目を書く。

- 失敗した check-run（name・conclusion）と失敗したステップ名
- 種類（手順3または手順4の分類。複数あればすべて、review は主と派生を分けて書く。決まらなければ判定不能と候補）
- 根拠（目印の行の有無・件数・ステップの結論）
- 関連記録の所在（No. と行範囲）
- 既知の対処と回復の主体（下の表）

| 種類 | 既知の対処 | 回復の主体 |
|---|---|---|
| verify：pytest・skip/xfail | 実装役に差し戻す（1 Issue あたり2回まで） | 実装役 |
| verify：ゲート不一致 | 判定ロジックの変更なら事前登録の手順に戻す。ゲート値の変更は scripts/verify.sh が deny 対象なので人が行う | 実装役（変更の取り消し）またはユーザ |
| verify：その他 | 事実を報告して止める | ユーザ |
| review：fork の拒否 | 同じリポジトリのブランチから PR を作り直す | ユーザ |
| review：max-turns 超過・timeout・コメントの失敗 | review は PR の opened でしか走らないので、再実行はユーザが Actions の画面で行う。verify の結果は別に確かめる | ユーザ |
| 判定不能 | 事実を報告して止める | ユーザ |

診断の後に修正や再実行を自分で行わない。司令塔は報告を見て、差し戻すかユーザに依頼するかを決める。

## 試走で起きた失敗（CI・review 以外）

司令塔・実装役の作業中に、Issue・PR の本文やコマンドの実行で起きた失敗を診断する。「守ること」はこの節にも当てはめる。

本文が確定本文と一致しない場合は「帰属フッタが付いた」で扱う。コマンドの拒否は、次の順で種類を決める。

1. 権限設定（.claude/settings.json の deny・ask）による拒否なら「権限設定の拒否」とする。事実を報告して止め、回避の候補を出さない。
2. 拒否された呼び出しが `&&`・`;`・改行で複数のコマンドを含めば「まとめたコマンドの拒否」とする。
3. 単独のコマンドが auto mode の分類器に拒否されたなら「分類器の拒否」とする。

コマンドの拒否はログを gh api で取得できない。呼び出し元が渡す事実（拒否された主体、コマンドの形、拒否の別、クラウドかローカルか）を入力とする。コマンドの本文と拒否メッセージの本文は報告に書き写さず、形（コマンド数、`&&`・`;`・パイプの有無）だけを書く。

### 帰属フッタが付いた

1. `gh api repos/{owner}/{repo}/issues/<番号> --jq .body > /tmp/diag_body.md` で本文を取得する（PR は `pulls/<番号>`）。取得が拒否されたら「分類器に拒否された」に従う。
2. 確定本文（呼び出し元が渡すファイル）と取得本文のそれぞれに `printf '%s' "$(cat <ファイル>)" | sha256sum` を1つずつ実行する。
3. 一致しなければ、両方に `wc -l < <ファイル>` を1つずつ実行し、増えた行数を求める（取得側は `--jq` の出力の改行で1行多いのが正常なので、その1行を除く）。
4. 書くのは一致・不一致と増えた行数だけ。本文は書き写さない。

### 分類器に拒否された

- 根拠：単独のコマンド（`&&`・`;`・改行を含まない）が分類器に拒否されたこと。パイプの有無を書く。
- 試走では、GitHub MCP で本文を更新した直後に、パイプ付きの本文の取得が拒否され、単独のコマンドでは通った（docs/ai_loop_state/commander_trial_2026-10-02.md の 4.2）。

### まとめたコマンドが拒否された

- 根拠：拒否された呼び出しに含まれたコマンドの数と、`&&`・`;`・改行の有無。
- Issue #391 の作業では、実装役が push・cp・PR 作成・git log を1回の呼び出しにまとめて拒否され、1つずつなら通った（ユーザの観測）。
- 分けたコマンドのどれかが deny・ask に当たるなら、分けて回避する候補を出さず、権限設定の拒否として扱う。

### 報告する

手順6の項目のうち、種類・根拠・関連記録の所在・既知の対処と回復の主体を書く。所在は下の表を使い、ERRORS.md の行範囲は手順5の2の方法で確かめる。

| 種類 | 既知の対処 | 回復の主体 | 関連記録の所在 |
|---|---|---|---|
| 帰属フッタ | GitHub MCP の更新用ツールを持つ主体（司令塔）が確定本文に戻して再照合する。持たない主体（実装役）は司令塔に返す。司令塔も持たなければユーザが Web 画面で削除する | 司令塔またはユーザ | 試走の記録 4.1、.claude/skills/publish-github/SKILL.md |
| 分類器の拒否 | 同じ主体が、パイプ・`;` を使わない単独のコマンドで1回だけ再試行する。それでも拒否されたら止める。本文の照合のための取得なら「未確認」と記録する | 再試行は拒否された主体、2回目の拒否の後はユーザ | 試走の記録 4.2、ERRORS.md の棚卸し No.74 |
| まとめたコマンドの拒否 | 1回の呼び出しに1つずつに分けて再試行する（この再試行を分類器の拒否の1回と数える）。分けたコマンドが拒否されたら分類器の拒否として止める | 拒否された主体 | ERRORS.md の棚卸し No.20、Issue #391 の作業 |
| 権限設定の拒否 | 事実を報告して止める | ユーザ | ERRORS.md の棚卸し No.74 |

診断の後に再試行・本文の更新を自分で行わない。対処は候補として示すだけにする。
