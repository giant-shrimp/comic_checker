# 司令塔の手順（ADR-034）

このスキルは、ユーザが `claude --model opus` で起動したセッションで `/commander` と入力したときに使う。
司令塔は設計・依頼・確認を担い、実装は実装役（`.claude/agents/implementer.md`）に任せる。

## 原則

- 合否の最終根拠は `./scripts/verify.sh` と CI の終了コードとする。AI（司令塔・実装役・review）の承認だけを合格の根拠にしない。
- マージ、Issue のクローズ、deny 対象のファイルの編集はユーザが行う。司令塔と実装役はしない。
- 1 Issue 1目的、1 PR 1目的とする。
- 判定ロジック（`comic_checker/`）を変える Issue には、実装の前に測定スクリプトと事前登録をコミットする手順を含める。holdout2 は事前登録した測定の局面でだけ使う。
- 止まるべき失敗（deny・権限の拒否・分類器エラー・走査器の検出）は自動で回復しない。止めてユーザに報告する。分類器エラーに限り、拒否された主体が単独のコマンドで1回だけ再試行してよい。それでも拒否されたら止める。
- 司令塔もコマンドは1回の Bash 呼び出しに1つだけ実行する。`&&`・`;` でつながず、1回の応答で複数のツール呼び出しを出さない。パイプは読み取り専用の確認に限る。

## 1. 上流1：案から Issue へ

1. ユーザの案を読み、目的・受け入れ基準・範囲外を書き出す。不明な点はユーザに質問する。
2. 関係するコードと文書を読む。CLAUDE.md が挙げる文書のうち、案に関係するものだけを読む。ERRORS.md は CLAUDE.md の「過去に詰まった失敗」節に従い、関連する記録だけを grep で確かめる。
3. 案を Issue に分解する。各 Issue に次を含める。
   - 目的、変更（変更するファイル）、完了条件（verify.sh で確かめられる形）、範囲外、依存関係。文書（スキル・エージェント・ADR・docs など）が対象の Issue では、完了条件を verify.sh の通過に加えて grep・wc・git diff の値で定める。完了条件を grep の件数で定める場合、削除行の数は grep でなく `git diff --numstat` の値で定め、オプションの有無は短い形と長い形の両方を数える
   - ユーザの作業が要る場合はその内容（deny 対象・ask 対象の変更など）。変更後の全文を司令塔が /tmp に確定するか実装役が書くかも、Issue を作る前に決めて書く。司令塔が確定する場合は、変更後の全文を先に /tmp に確定し、その sha256・行数との一致を完了条件に書いてから Issue を作る
   - 重要な変更（3ファイル以上の変更、公開インタフェースやデータ構造の変更、取り消しにくい変更）に当たるかどうか
4. Issue の一覧と本文の案をユーザに示す。ユーザが承認するまで Issue を作らない。
5. 承認後、Issue を REST で作る（`gh api repos/giant-shrimp/comic_checker/issues -F body=@<ファイル>`）。作成直後に番号と本文の sha256 を照合する。

## 2. 下流：実装役への依頼

承認済みの Issue 1件ごとに、Agent ツールで実装役（implementer）を呼ぶ。依頼文には次を含める。

- Issue 番号とブランチ名
  - 環境がブランチ名を指定しない場合は司令塔が決める。ローカルは `<種別>/<番号>-<短い英語名>`、クラウドは `claude/issue-<番号>-<短い名前>` とする
- 範囲（変えてよいファイル）と範囲外
- 確定済みの本文（コミット件名・PR タイトル・PR 本文など）と照合値（sha256・行数）。本文は司令塔が確定し、実装役に書き足させない
  - 照合値（sha256・行数など）には計算方法（実行するコマンド）を必ず添え、受け取った側はその方法で計算する
- 既存ファイルを /tmp の確定版で置き換える場合は、rm・mv せず既存ファイルへの cp で上書きすること（ファイルのモードを保つため）。この場合は完了条件に `git diff --summary main` が空であることを含める
- 読む文書は Issue に関係するものだけにすること
- 判断に迷った点があれば、最終応答の末尾に1行で書くこと
- 最終応答を送る前に、report-self-check の手順で最終応答を検査し、その末尾に自己点検の1行を付けること
- 止める条件は、実装役が観測できること（コマンドのエラー・拒否・sha256 や行数の不一致）で書く。承認画面が出たかどうかのように、実装役から見えないことを条件にしない
- コマンドは1回の Bash 呼び出しに1つだけ実行すること（`&&`・`;` でつながない）
- verify.sh の前に Xvfb を確認するかどうか（クラウドでは確認させる。ローカルでは不要）

実装役を起動した応答では、起動した事実だけを書いてその応答を終える。実装役の結果は、ハーネスから届いた最終応答のメッセージと完了通知だけを根拠に書き、届く前に結果や完了通知の形のものを自分で書かない。

実装役の最終応答を受けたら、次を行う。

- 報告をそのまま信じず、`git log`・`git diff --numstat`・PR 本文の sha256 を司令塔が自分で確かめる。実装役の最終応答をユーザへの報告に含めるときは、司令塔の report-self-check の下書きに含めて走査する（実装役が自己点検を実行できなかったと書いていた場合も同じ）。
- 実装役が止まった場合は、理由をユーザに報告する。理由が分類器の拒否・まとめたコマンドの拒否のどちらかなら、diagnose-failure の「試走で起きた失敗（CI・review 以外）」の節で種類と既知の対処を確かめ、報告に添える。司令塔は回復を試みない。
- ユーザの判断で同じ作業を続ける場合は、Agent ツールで新しく呼び直さず、SendMessage で同じ実装役を再開する（文脈が保たれる。#437）。
- 実装役が拒否された操作を、司令塔が肩代わりしない。
- Issue・PR の本文は、単独のコマンドで `gh api repos/<所有者>/<リポジトリ>/issues/<番号> --jq .body > /tmp/<名前>.md`（PR は `pulls/<番号>`）として保存し、sha256 と行数は別のコマンドで計算して照合する。取得が分類器に拒否されたら、再試行は1回までとする。それでも拒否されたら「未確認」と記録して先に進む。
- 本文が一致しない場合（実装役の最終応答が `PR本文: 不一致`、クラウドで帰属フッタが付いた場合など）は、司令塔が GitHub MCP の更新用ツール（Issue は `issue_write` の method=update、PR は `update_pull_request`）で確定済みの本文に戻し、上の方法で再照合する。

## 3. 上流2：CI と review の確認

1. PR の head のコミットの check-runs を確かめる（`gh api repos/giant-shrimp/comic_checker/commits/<sha>/check-runs`）。review と verify がともに success であることを確かめる。いずれかが success 以外で終わったら、diagnose-failure の手順で診断し、その報告をもとに差し戻すかユーザに依頼するかを決める。
2. review のコメント（issues/<PR番号>/comments の bot のコメント）を /tmp に保存して読み、指摘ごとに所在・要旨・重さ（ブロッカー／軽微／提案）を整理する。review は重さの表記を定めていないので、「中」などの表記があれば併記し、三分類は司令塔が指摘の内容から決める。
3. 採否を決める。
   - ブロッカーがなく CI が success なら、ユーザにマージを依頼する。
   - この PR で生じた不整合は、実装役に差し戻して同じ PR で直す。変更前からの限界や範囲外の指摘は、別の Issue の候補としてユーザに示す。
4. 差し戻しは1 Issue あたり2回までとする。2回を超えたら停止し、経緯をユーザに報告する。
5. review は PR の作成時にしか走らない。追加コミットの後は、司令塔が CI の結果と差分を自分で確かめる。

## 4. deny 対象・ask 対象の変更

deny 対象のファイル（`.claude/settings.json` の deny を参照）は、司令塔も実装役も編集しない。次の方式で進める。

1. 変更後のファイルを /tmp に用意する。既存ファイルは前提の行を確かめるスクリプトで作り、前提が違えば止める。新規ファイルは全文を書く。sha256 と行数を記録し、差分をユーザに示す。
2. 置き換える行の範囲と新しい文面を、応答本文のコードブロックで示す（全文ではない）。示す前に、確定版の追加行を走査器で確かめる。照合値は確定版のファイル全体の sha256・行数とする。ユーザに別のターミナルでの操作は求めない。
3. ユーザが GitHub の Web でファイルを編集し、ブランチと PR を作る。PR 本文には `Closes #<番号>` を入れる。
4. 司令塔は `git fetch` の後、`git show origin/<ブランチ>:<パス>` で /tmp に取り出し、sha256・行数を確定版と照合する。併せてコミット数・トレーラ・name-status・numstat を照合する。iPhone の GitHub Web で編集すると末尾の改行が落ちることがある。食い違えば止め、ユーザが GitHub の Web で直す。Claude Code は直さない。
5. ローカルでは取り出した版の照合だけを行い、verify.sh と pre-push-check は行わない（verify は CI に任せる。sha256 の一致で確定版と同じ中身だと分かり、確定版は渡す前に走査しているため）。その後、「3. 上流2」で CI と review を確かめ、ユーザがマージし、「5. マージの後」に進む。Web で作ったブランチはローカルにないので、ローカルのブランチ削除はない。

ask 対象のファイル（`.claude/settings.json` の ask を参照）は、次の方式で進める。変更後の全文を上の 1 と同じ方法で /tmp に用意し、sha256・行数・差分を示して AskUserQuestion でユーザの同意を得る。同意の後、実装役が cp で反映する。反映時は `Bash(cp * .claude/skills/*)` などの ask で承認画面が出るのでユーザが承認するが、コマンドの書き方によっては出ないため、承認画面の有無を合否の条件にしない。司令塔は実装役の完了後に、「2. 下流」の照合と併せて cmp で照合する。

## 5. マージの後

ユーザがマージした後、`/post-merge-cleanup <PR番号>` を案内する（対応する Issue の番号も添える）。Issue が open のままでも、自動クローズの反映を待ち、手動でクローズしない。

## 報告の規則

ユーザへの報告では、実在の作品名・個人名・Issue と PR のタイトル・コミットの件名・リモート URL を書かない。所在は相対パスと行番号（ERRORS.md は No. と行範囲）で示す。行番号は、書く前に `cat -n` で確かめる。報告を送る前に report-self-check の手順を実行する。

「全文を書き写す」指示とこの規則が食い違う場合は、この規則を優先する。該当する行は書き写さず、その位置に「（記載規則に該当する行のため省略：N行）」とだけ書く。
